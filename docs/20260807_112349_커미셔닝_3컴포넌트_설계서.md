## 1. 한 줄 요약

구성도(`docs/my_think/my_setting_manager_구성.md`)의 **Bridge Backend-Core** 하위 항목 중 셋을
SettingMain 안에 **서로를 import 하지 않는 3개 컴포넌트**로 세운다. 셋은 코드로 만나지 않고
**프로파일 문서(데이터)** 로만 만난다.

| 컴포넌트 | 지금 상태 | 만들 것 | 상류 대비 |
|---|---|---|---|
| **A. 캘리브레이션** | ❌ 501 (솔버는 이미 벤더링돼 있는데 안 쓰임) | ZNCC 프레임 매칭 · 스윕 잡 · 발행 | 상류 `sharp` → **ffmpeg** 로 대체 |
| **B. 센터라이징** | ⚠️ 동작하나 **게인 미적용** · park3d 는 아예 불가 | 조준 사슬(게인) · 소프트웨어 센터링 | 상류 `software-centering.mjs` 이식 |
| **C. 차량 3D 육면체** | ⚠️ 검출만 · `baseUrl` 빈 값이라 꺼져 있음 | 저장 · 오버레이 · 전용 화면 | 상류에 없는 부분(영속화·화면) 신설 |

**가장 값싼 발견 두 가지**가 설계를 크게 줄였다.

- `@baro/profile` **솔버가 이미 [SettingMain/src/vendor/baro-profile/](../SettingMain/src/vendor/baro-profile/) 에 있고 아무도 쓰지 않는다.**
  캘리브레이션이 501인 진짜 이유는 수학이 아니라 **JPEG 디코딩**이다. 만들 것은 솔버가 아니라 그 앞단이다.
- **사이드카가 `segments`(이미지 좌표 선분)를 이미 준다.** 3D 큐보이드를 우리가 투영할 필요가
  없다 — 받은 선분을 잇기만 하면 된다. `boxProjection` 모듈은 **만들지 않는다.**

## 3. "독립"의 정의 — 무엇을 금지하는가

"각각 독립적으로"를 장식이 아니라 **검사 가능한 규칙**으로 못 박는다. 규칙이 없으면 다음 사람이
"잠깐만 빌려 쓰지" 하고 한 줄 import 를 넣고, 그 순간 독립은 끝난다.

### 규칙

1. **`src/calibration/`·`src/centering/`·`src/vehiclebox/` 는 서로를 import 하지 않는다.**
   → *강제*: `test/componentIndependence.test.ts` 가 세 디렉토리의 소스를 스캔해 교차 import 를 잡는다.
2. 셋 다 **아래 층만** 쓴다: `vendor/baro-profile`(순수 계산) · `devices/`(드라이버) · `profiles/`(데이터) · `config/`.
3. 셋 각각 **자기 라우트 · 자기 저장소 · 자기 화면 · 자기 테스트 파일**을 갖는다.
4. 하나를 통째로 지워도 나머지 둘의 테스트가 통과해야 한다.

### 그럼 캘리브와 센터링은 어떻게 만나는가

**두 번 만난다. 둘 다 코드가 아니다.**

```
   ┌─ 캘리브레이션 ─┐                      ┌─ 센터라이징 ─┐
   │                │                      │              │
   │   verify 모드  │                      │  운영 조준   │
   └───────┬────────┘                      └──────┬───────┘
           │                                      │
           └──────────┬───────────────────────────┘
                      ▼
        vendor/baro-profile (순수 함수 · 이미 있음)
          applyCenteringGain · pixelToPtzDelta · hfovFromZoomPos
                                                   ① 계산의 만남

   캘리브레이션 ──publish──▶  profiles/  ──read──▶  센터라이징
                                                   ② 데이터의 만남
```

**① 계산의 만남**은 벤더링된 순수 함수다. 상류가 실기 112샘플로 고정한 계산이고, 베껴 쓰면 두 벌이
되어 반드시 갈라진다(벤더 문서 규칙 2번). 두 컴포넌트가 **같은 함수를 각자 부른다** — 서로를 부르지 않는다.

**② 데이터의 만남**은 프로파일 문서다. 캘리브레이션이 없어도 센터링은 선다 — 손으로 넣은
프로파일(`import`)이나 옆 카메라에서 복사한 것(`copy`)으로도 게인은 채워진다. 상류
`docs/calibration.md` §"창구는 `/api/profiles` 하나입니다"가 정확히 이 이야기다.

**컴포넌트 C 는 어느 쪽과도 만나지 않는다.** 사이드카는 자기 캘리브레이션 파일
(`baro_object3d_api/config/cameras/<id>.json`)을 쓰고, 그것은 우리 프로파일과 **다른 것**이다
(§12 에 이 미해결을 명시한다).

## 4. 공용 기반 — 프로파일 (M0)

세 컴포넌트 중 A·B **둘 다** 필요로 하므로 컴포넌트가 아니라 **기반**이다. 상류
`docs/calibration.md` §프로파일 생명주기 정책이 정본이고, 그 문서가 "여기 적힌 것과 다르게 동작하는
코드가 있으면 코드가 틀린 것"이라고 못 박았으므로 **그대로 따른다.**

### 저장 위치는 둘뿐

| 어디 | 무엇 | 성격 |
|---|---|---|
| `profiles/camera/<기기id>/rev-NNNN.camprof.json` (+ `.sha256`) | 발행본 | **불변** · 진실의 출처 · git 추적 |
| `config/config.json` 의 `cameras[].intrinsics` | 런타임 적용본 | 가변 · 이 프로세스가 실제로 물고 도는 값 |

그 밖(스윕 감사본·코드 내장 표)은 **출처가 아니다.**

### 신설/변경

```
SettingMain/src/profiles/
  profileTypes.ts     문서 스키마 (zoomHfov · centeringGain · provenance · quality · device)
  profileStore.ts     publish(max(rev)+1, tmp+rename, .sha256) · list · read(@N) · apply · retire
  publishGate.ts      fitRmsMedianPx ≤ 20 · 쓸 수 있는 표본 ≥ 50% · force 시 사유 기록
  profileDrift.ts     발행본 대비 런타임 적용본의 이탈 보고 (분모는 발행본)
SettingMain/src/api/routes/profileRoutes.ts
```

**타입 확장(둘 다 필요)** — [src/config/types.ts](../SettingMain/src/config/types.ts) 의
`CameraIntrinsics` 에 `centeringGain?: Array<{ z: number; k: number }>` 를 더한다. 지금은 `zoomHfov`
뿐이라 **게인을 담을 자리가 없다.**

### 못 박는 규칙 (상류에서 그대로 가져옴)

- **적용이 먼저, 발행이 나중.** 리비전은 발행 순간 불변이라 되돌릴 수 없지만 config 쓰기는 실패할 수 있다.
  → *강제*: `test/profileStore.test.ts` 가 "적용에 실패했으면 문서도 남지 않아야 한다"를 못 박는다.
- **판정은 최댓값이 아니라 중앙값**(`fitRmsMedianPx`). 상류가 2026-08-05 에 실측으로 바꾼 지점이다 —
  앵커 열하나 중 열이 좋은데 하나가 시끄럽다고 20분짜리 실측을 버리게 하면 안 된다.
- **우회는 막지 않되 기록한다.** `{force:true}` → 문서의 `quality.forced` 에 사유 배열.
  **화면에도 「그래도 발행」이 있어야 한다** — 우회로를 API 에만 두면 그것은 우회로가 아니다.
- **`PUT` 라우트를 두지 않는다.** 덮어쓸 수 있는 문을 만들면 불변 규칙이 관습으로 내려앉는다.
- 삭제는 파기가 아니라 **퇴역**(`.trash/<id>.<발행시각>` 으로 이동). 런타임 적용본은 건드리지 않는다.

## 5. 컴포넌트 A — 캘리브레이션

> **무엇을 답하는 기능인가**: "이 카메라는 클릭한 곳으로 얼마나 못 가는가, 그리고 각 줌에서 실제로 얼마나 넓게 보는가."
> 산출물은 곡선 **둘**이다 — `zoomHfov`(그리는 데) · `centeringGain`(조준하는 데). 하나로 합치면 안 된다.

### 파일 구성

```
SettingMain/src/calibration/
  jpegSize.ts          SOF 마커 스캔 → {width,height}   (~25줄, 순수 TS)
  frameDecode.ts       ffmpeg 로 JPEG → 그레이 래스터    ★ 상류 sharp 대체
  frameMatch.ts        ZNCC coarse→fine + 부엽 마진      (상류 frame-match.mjs 이식)
  sweepPlan.ts         줌 앵커 × 클릭 표적 (시드 z 규칙)
  cameraLock.ts        유언장 — 홈 자세를 디스크에 먼저 남긴다
  calibrationJob.ts    잡 러너 (start/status/stop · 홈 복귀 · 감사본)
  calibrationPort.ts   JobPort<CalibrationStartOptions> 구현 → 브리지에 꽂는다
```

**솔버는 만들지 않는다.** `buildCalibration`·`solveZoom`·`MIN_PEAK`·`MIN_MARGIN` 은 이미 벤더링돼 있다.

### ★ JPEG 디코딩 — ffmpeg (마스터 확정 2026-08-07)

상류는 `sharp` 를 쓴다. SettingMain 은 런타임 의존성 2개(MCP SDK·zod)를 유지하므로
**이미 하드 의존인 ffmpeg** 로 대신한다.

```
ffmpeg -hide_banner -loglevel error -f image2pipe -i pipe:0 -pix_fmt gray -f rawvideo pipe:1
```

**치수를 어떻게 아는가**가 이 설계의 유일한 까다로운 지점이다. rawvideo 출력에는 헤더가 없다.

- `ffprobe` 를 한 번 더 돌리는 것 → 왕복이 두 배가 된다.
- 강제로 `scale=1920:1080` → **금지.** 4K 스냅샷을 내리깎으면 서브픽셀 정밀도를 잃는다.
  우리가 재는 신호 전체가 겨우 수십 픽셀 폭이다.
- **채택**: JPEG 헤더의 `SOF0/SOF1/SOF2` 마커를 직접 읽어 `{width,height}` 를 얻는다(~25줄).
  그리고 **`data.length === width*height` 를 단언**한다 — 이 단언이 곧 "헤더 파서와 ffmpeg 가 같은
  그림을 봤다"는 증거다. 어긋나면 조용히 어긋난 좌표로 계산하지 않고 그 샘플을 버린다.

| 판단 | 근거 |
|---|---|
| 성능 | 샘플당 2회 spawn × ~80ms = 112샘플에 **약 18초**. 20분 스윕에서 무시 가능 |
| ffmpeg 없는 기계 | `capabilities()` 가 **캘리브레이션만** `ok:false` + 사유로 끈다. 조용히 죽지 않는다 |
| ZNCC 비용 | 상류도 상관 계산은 JS 다(sharp 는 디코딩에만 쓴다) — **연산 비용은 상류와 동일** |

### ZNCC 프레임 매칭 — 상류에서 그대로 옮길 것

상류 `frame-match.mjs` 를 TypeScript 로 이식한다. **알고리즘을 개선하지 않는다** — 아래는 전부
상류가 실측으로 피 흘려 얻은 것이다.

- **coarse(1/4) → fine(전해상도) + 포물선 서브픽셀 피팅.** 노출이 두 스냅샷 사이에 변하므로 SSD 가
  아니라 **영평균 정규화 상관**이어야 한다.
- **거친 단계의 1등은 판결이 아니라 제안이다.** 상위 후보 3개를 (충분히 떨어뜨려) 들고 가 전해상도에서 고른다.
- **`margin`(부엽 마진)이 `peak` 보다 중요하다.** 실측 프레임에서 0.898 짜리 매칭 10px 옆에 0.897 이
  있었고 **레퍼런스 OpenCV 와 우리 구현이 둘 다 틀렸다.** 점수는 아무것도 말하지 않았고 마진이 전부를 말했다.
- 게이트 넷: `peak ≥ 0.6` · `margin ≥ 0.02` · 교차축 잔차 ≤ 40px · 부호 일관성.
- `contrast`(RMS, 그레이 레벨) 를 함께 낸다 — **`dark`/`smooth`/`featureless` 는 처방이 다르다.**
  하나는 아침에 다시 오면 되고 하나는 카메라를 돌려야 한다.

### 스윕 잡

```
줌 앵커 14 × 클릭 8 (dx ±240/±480/±720, dy ±300)  = 112 샘플 (full)
줌 앵커 3  × 클릭 6                                 = 18 샘플 (verify)
```

**반드시 지킬 것 넷** — 넷 다 상류가 실제로 당한 사고다.

1. **full 은 보정 없이(raw) 조준한다.** 그러지 않으면 *자기가 도출하려는 보정을 통과해서* 카메라를 재게 된다.
2. **verify 는 설치된 보정을 통과해서 조준한다.** 답해야 할 질문이 "이 보정이 이 카메라에 맞나"이므로 보정이 루프 안에 있어야 맞다.
3. **줌 앵커는 기기 눈금이어야 한다.** cam-001 눈금(0~65535)을 자기 범위를 선언하는 기기(IDIS: 100~1200)에
   보내면 범위 밖 앵커가 `rc=0` 으로 **성공을 답하며 조용히 최망원에 클램프**되고, 요청값을 키로 쓰는 표가
   오염된 채 발행된다. 자기 범위를 선언하는 기기는 **자기 시드 표의 z 축**을 앵커로 쓴다.
4. **카메라를 반드시 돌려준다 — 실패·취소·프로세스 사망 전부.** 20분 스윕 도중 재시작이 들어오면
   `finally` 의 복귀도 같이 죽는다. 그래서 **시작 전에 홈 자세를 디스크에 남긴다**(유언장).
   복귀에 성공했을 때만 찢는다 — 실패하면 락을 남겨 다음 부팅이 대신 되돌린다.

**팬 심(0/36000) 주의**: JS 의 `%` 는 피제수 부호를 따르므로 `+36000` 재정규화가 필수다. 상류에서
실제로 잠복해 있던 버그이고, 심 근처 설치 카메라에서만 발현한다.

### 판정과 발행

- full 결과 → §4 게이트 통과 시 발행. 미달이면 **422 + 무엇이 미달인지 + 시끄러운 앵커**, 그리고 화면에 「그래도 발행」.
- `residual.beforePx` 는 **보정 전** 오차다. "보정 후 남는 오차가 아니다"를 응답에 명시한다 —
  섞으면 **캘리브레이션이 자기 자신을 축하하게 된다.**
- verify 는 `pass`/`fail` 외에 **`incomplete`** 를 낸다. 장면이 답하지 못한 줌을 통과로 부르는 것이
  이 기능이 낼 수 있는 최악의 결과다("16384 에서 멀쩡하다"고 들었는데 그 줌에서는 쓸 수 있는 프레임이 한 장도 없었다).

## 6. 컴포넌트 B — 센터라이징

> **무엇을 답하는 기능인가**: "클릭한 픽셀을 화면 중앙으로 가져온다 — 그리고 실제로 갔는지 말한다."

### 파일 구성

```
SettingMain/src/centering/
  aimChain.ts           픽셀 → (게인) → 팬/틸트 델타   (벤더 순수함수 조합)
  softwareCentering.ts  centerPoint 없는 드라이버용 계산 조준
  centeringService.ts   조준 → 정착 대기 → 착지 보고
  centeringPort.ts      center/centerBox 구현 → 브리지에 꽂는다
```

### B-1. 조준 사슬 — 살아 있는 결함을 고친다

```
클릭 픽셀 (x,y)
   │
   ├─ intrinsics.centeringGain 이 있는가?
   │     ├─ 예 → applyCenteringGain(x,y,zoomPos,table)   ← 벤더 순수함수
   │     └─ 아니오 → 그대로 (k=1)                         ← 지금의 동작
   │
   ├─ 드라이버에 centerPoint 가 있는가?
   │     ├─ 예 → driver.centerPoint(보정된 픽셀)          ← 펌웨어가 나머지를 한다
   │     └─ 아니오 → 소프트웨어 센터링 (B-2)
   │
   └─ waitForSettle → 착지 좌표 · settled 보고
```

`applyCenteringGain` 은 **이미 벤더링돼 있다.** 만들 것은 "그것을 부르는 자리"와 "표가 없을 때
지어내지 않는 규율"이다.

- **게인 표가 없으면 `k=1` 로 간다 — 내장 `CENTERING_GAIN_TABLE` 을 기본값으로 들지 않는다.**
  그 표는 cam-001 한 대의 곡선이다. 다른 렌즈에 씌우면 **개선이 아니라 악화**다
  (상류 실측: z16384 에서 참 게인 0.765 인데 1.11 을 유지하는 표를 쓰면 망원을 망친다).
- 응답에 `gain` 을 실어 **무엇이 적용됐는지 화면이 안다.** 조용한 보정은 조용한 미보정만큼 나쁘다.

### B-2. 소프트웨어 센터링 — `park3d-rpc` 를 살린다

상류 `software-centering.mjs` 의 원칙 그대로: 하드웨어에 없는 능력을 **리퍼런스 기하를 주입해**
계약까지 끌어올린다.

```
절대 PTZ 만 있는 기기  ──(pixelToPtzDelta 주입)──▶  픽셀 센터링 계약 충족
```

**성립 조건이 곧 게이트다:**

| 게이트 | 왜 |
|---|---|
| 이 기기의 **실측 `zoomHfov` 표**가 있어야만 켠다 | 화각을 모르면 픽셀을 각도로 못 바꾼다. 기본 곡선을 쓰면 조용히 엉뚱한 곳을 조준한다 |
| 표가 기기 줌 **범위를 덮어야** 한다 | 부분 표를 통과시키면 표 밖 줌에서 끝값 클램프로 **수 배 오조준**(상류 실측: 1점 x1 표 + x12 줌 = 12배 과회전) |
| 틸트 도달범위 밖은 **422 + 사람 문장** | 전량 클램프는 무이동이라 정착 대기가 10초를 매달린 뒤 **원인 불명 502** 가 된다 |

**순환측정이 아닌 이유**: 캘리브레이션이 재야 할 대상은 "운영에서 실제로 조준할 사슬"이다. 이 기기의
사슬이 우리 기하라면, 잴 것도 그 기하의 잔차 — 즉 이 기기의 광학이고, 그것이 정확히 산출물이다.

### B-3. 박스 줌

이미 [bridgeCoreProvider.ts:126](../SettingMain/src/core/bridge/bridgeCoreProvider.ts#L126) 에 있다.
**옮기기만 한다** — 계산은 건드리지 않는다. 가로·세로 중 **큰 쪽**을 쓰는 이유(작은 쪽이면 박스가 잘린다)도 그대로.

## 7. 컴포넌트 C — 차량 3D 육면체

> **무엇을 답하는 기능인가**: "지금 이 프레임의 차량들이 어디에 얼마만 한 크기로 어느 방향을 보고 서 있는가."
> **카메라를 움직이지 않는다** → 점유(lease)하지 않는다.

### 파일 구성

```
SettingMain/src/vehiclebox/
  object3dClient.ts     ← src/detectors/ 에서 이동 (아래 근거)
  vehicleBoxStore.ts    검출 영속화 (SQLite · 기기별 · 촬영시각)
  vehicleBoxService.ts  스냅샷 → 검출 → 저장 → 봉투
  vehicleBoxPort.ts     VehicleBoxPort 구현 → 브리지에 꽂는다
SettingMain/web/vehiclebox.html · vehiclebox.js
```

**`object3dClient.ts` 이동 근거**: 그 파일의 주석이 스스로 *"`DetectorName`(vpd·lpd·lpr)에 넣지
않았다 — 그 셋은 구성도의 API 계층이고 object3d 는 코어 능력(`vehicleBox`)을 채우는 사이드카다"*
라고 적고 있다. 지금 `src/detectors/` 에 있는 것은 그 문장과 어긋난 자리다. 이동하면 컴포넌트가
자기 완결이 된다. 오류 봉투(`DetectorError`)만 공유는 유지한다.

### ★ 오버레이 — 투영하지 않는다

**사이드카가 `segments` 를 이미 이미지 좌표로 준다.** 검출마다:

| 필드 | 내용 |
|---|---|
| `label` · `score` | 분류와 신뢰도 |
| `label_point` | 라벨 놓을 자리 (이미지 좌표) |
| **`segments`** | **3D 큐보이드 모서리를 이미지 좌표 선분으로 편 것** |
| `position_m` · `size_m` · `yaw_deg` | 미터 값. 기준계는 **카메라 바로 아래 지면이 원점, x 전방 · y 좌측** |
| `score_3d` | **항상 `null`** (이 모델은 신뢰도가 하나뿐) |

> **`segments` 개수를 가정하지 말 것.** 큐보이드는 12모서리(바닥 4 + 천장 4 + 수직 4)라 보통 12개지만
> **항상 12개는 아니다** — 투영이 화면의 3배를 넘어 날아간 모서리는 개별적으로 버려진다.
> 그리는 쪽은 **받은 선분만 잇는다.** 12개를 기대하고 인덱스로 면을 재구성하면 조용히 깨진다.

이 사실 하나가 `boxProjection.ts`(월드→픽셀 투영, 마운트 extrinsic 필요)를 통째로 없앴다.
우리는 마운트 높이·피치·롤을 **갖고 있지도 않다**(§12).

### 어휘의 경계 — 상류와 같게 유지한다

```
봉투    cameraId · capturedAt · count · model · latencyMs   ← 우리 어휘
측정값  detections[] · calibration                          ← 사이드카 어휘 그대로
```

측정값을 개명하면 사이드카 로그·오프라인 도구와 대조가 안 되고 좌표계 규약이 두 벌이 된다.
반대로 **호스트의 내부 사실**(사이드카 주소·캘리브 파일 경로)은 싣지 않는다 — 그건 측정이 아니라 배치다.

### 영속화 (상류에 없는 것 — 신설)

상류는 검출을 **던지고 잊는다**. 커미셔닝에는 "그때 뭐가 보였나"가 남아야 하므로 저장한다.

| 저장할 것 | 왜 |
|---|---|
| `captured_at` · `camera_id` · `ptz`(그때 자세) | 자세 없이는 같은 그림을 다시 못 본다 |
| `detections` (원문 JSON) | 개명하지 않는다는 규칙이 저장에도 걸린다 |
| `calibration` (적용된 것) | **무엇을 기준으로 잰 값인지가 곧 값의 의미다** |
| `model` · `latency_ms` | 모델이 바뀌면 값이 바뀐다 |

스냅샷 JPEG 자체는 저장하지 않는다(용량). 필요해지면 그때 정한다.

### 오류를 뭉개지 않는다

이미 [object3dClient.ts:97-128](../SettingMain/src/detectors/object3dClient.ts#L97) 이 하고 있고 유지한다.
`no_calibration`(422, 운영자가 5분이면 고침) 을 502 로 접으면 **"파일 하나 없음"이 "3D 서비스 죽음"으로 보고된다.**

### 신설

| 경로 | 용도 |
|---|---|
| `GET    /api/profiles/camera/:id` | 리비전 목록 + 현재 적용본 + 드리프트 |

## 10. 마일스톤과 검증

각 마일스톤은 **검증 가능한 성공 기준**을 갖는다. C 는 M0 를 필요로 하지 않으므로 순서가 자유롭다.

| # | 내용 | 성공 기준(검증) |
|---|---|---|
| **M0** | 프로파일 기반 + `centeringGain` 타입 확장 + `/api/profiles` | `profileStore.test.ts`: 적용 실패 시 문서도 안 남음 · `@N` 고정 조회 불변 · 게이트 422 사유 · force 시 `quality.forced` 기록 |
| **A1** | `jpegSize` + `frameDecode`(ffmpeg) | 실제 스냅샷 JPEG 로 `len === w*h` · 4K/720p 둘 다 · progressive JPEG 도 통과 |
| **A2** | `frameMatch`(ZNCC) | **상류 골든 대조**: 같은 프레임 쌍에 대해 상류 `frame-match.mjs` 와 착지 픽셀 ≤1px 일치 · 모호 케이스에서 `margin` 이 게이트에 걸림 |
| **A3** | `sweepPlan` + `cameraLock` + `calibrationJob` | 목 드라이버로 112샘플 스윕 · 취소 시 홈 복귀 · **프로세스 강제 종료 후 재기동이 유언장으로 복귀** · 시드 z 규칙 |
| **A4** | 발행 + 화면 | full → 게이트 → 리비전 · 미달 시 화면에 사유+「그래도 발행」 · verify 가 `incomplete` 를 낸다 |
| **B1** | `aimChain`(게인) | 게인 표 있을 때 k≠1 적용 · **표 없으면 k=1**(내장표 폴백 없음) · 응답에 `gain` |
| **B2** | `softwareCentering` | `park3d-rpc` 로 센터링 성립 · 부분 표는 거절 · 틸트 전량 클램프 시 **422 사람 문장**(10초 대기 후 502 아님) |
| **B3** | `centerBox` 이동 + 착지 표시 | 기존 `streamCentering.test.ts`·`zoomTable.test.ts` 무변경 통과 |
| **C1** | `object3dClient` 이동 + `vehicleBoxStore` | 오류 `code`별 상태코드 유지 · 저장 왕복 · `calibration` 원문 보존 |
| **C2** | 화면 + 오버레이 | **`segments` 개수 12 를 가정하지 않는다**(7개짜리 응답으로 테스트) · `score_3d:null` 처리 |
| **C3** | 실기 | 사이드카 기동 + `cameras/<id>.json` → 실제 프레임에서 차량 큐보이드 |
| **X** | 독립성 · 문서 | `componentIndependence.test.ts` 교차 import 0 · 세 컴포넌트별 `.md` |

### 실기 검증 전제 (미리 밝힌다)

| 전제 | 상태 |
|---|---|
| ffmpeg | ✅ PATH 에 8.1.1 |
| 캘리브 대상 카메라 **20분 점유** | ⛔ **마스터 승인 필요** — 운영 중인 물리 카메라를 고배율로 돌린다 |
| `object3d` 사이드카 기동 (파이썬 + GPU) | ⛔ 미기동. `baseUrl` 도 빈 값 |
| 사이드카 `config/cameras/<기기id>.json` | ⛔ 없으면 422. 이 파일은 **우리 프로파일과 다른 것**이다 |

목(mock) 검증은 전제 없이 전부 가능하다. **실기 없이 통과한 것을 "검증됨"이라 부르지 않는다** —
상류가 정확히 그 방식으로 "픽셀→각도는 선형"이라는 검증되지 않은 가정을 목→시뮬→문서로 자기일관되게 퍼뜨렸다.

## 12. 하지 않는 것 · 열린 질문

### 이번에 하지 않는 것

- **번호판 호밍** — 구성도에 있지만 이번 셋에 없다. 501 로 남는다.
- **완전한 카메라 캘리브레이션** — 방사·접선 왜곡 없음, 주점 오프셋 없음, 게인은 등방 스칼라.
  상류가 이 경계를 명시했고 우리도 넘지 않는다.
- **자체 기하로 3D 큐보이드 산출** — 마스터가 사이드카 소비를 택했다. 마운트 extrinsic 도 없다.
- **자동 재측정** — 어긋났다는 사실을 말하는 데까지만 한다. 카메라를 수십 분 점유하는 결정은 사람의 턴이다.
- **스냅샷 JPEG 영속화** — 용량 판단이 필요하다. 필요해지면 그때.

### 열린 질문 (마스터 결정 필요)

1. **캘리브레이션 실기 스윕 승인.** 운영 중인 물리 카메라를 20분간 점유하고 고배율로 돌린다.
   지금까지 이 저장소는 실카메라 PTZ **이동 명령을 미실행**으로 두었다(2026-07-31 결정). 그 결정을 여기서 푸는가?
2. **`object3d` 사이드카 기동 주체.** 파이썬 + GPU 런타임이다. 누가 어느 호스트에 띄우는가?
   `config/cameras/<기기id>.json` 은 누가 만드는가?
3. **사이드카 캘리브레이션과 우리 프로파일의 관계.** 지금 둘은 **서로를 모르고 카메라 집합조차 겹치지 않는다**
   (상류 §6 미해결 그대로). 우리 발행본 스키마의 `extrinsic` 이 마운트 높이·피치·롤·지면 기준면을 담지 못한다.
   이번에는 **뭉개지 않고 별개로 둔다** — 합치려면 스펙 버전 상승이 필요하다.
4. **프로파일 발행본을 git 에 추적하는가.** 상류는 추적한다(`profiles/` 가 커밋돼 있다).
   이 저장소도 같게 갈지, `config.json` 처럼 제외할지.
