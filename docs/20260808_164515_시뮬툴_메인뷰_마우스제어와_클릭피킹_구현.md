## 3. 설계 판단과 그 근거

### 3-1. 패널 계약을 그대로 두었다

`view.pick` 의 응답 `{hit, world, actorId}` 를 껍데기가 **기존 모양**으로 바꿔 넘긴다.

```
{hit, world, actorId}  →  { mode, camId: null, ground: hit ? world : null,
                            car: actorId ? { id: actorId } : null }
```

그래서 `simtoolCar.js` 의 `onViewportClick` 은 **한 줄도 바뀌지 않았다.** 메인 뷰인지
PTZ 인지는 패널이 알 필요가 없다 — 알게 하면 다섯 패널이 전부 그 분기를 갖는다.

### 3-2. 메인 뷰만 언리얼이 픽한다 — 두 경로가 공존한다

| 영상 | 픽 주체 | 이유 |
|---|---|---|
| 메인 뷰 | **언리얼** `view.pick` | 메인 뷰의 자세를 주는 `cam.*` 가 없다. 그리고 라인트레이스라 **평면을 가정하지 않아** 경사·구조물 위도 맞는다 |
| PTZ 카메라 | 우리 서버 `/api/sim/pick` | `cam.get` 자세로 기하를 푼다. 기존 그대로 |

메인 뷰에서는 **「지면 높이 z」 입력칸을 끈다** — 실제 지형에 맞으므로 평면 높이를 받을
이유가 없는데, 켜 두면 사람이 값을 넣고 반영됐다고 믿는다.

### 3-3. 포트 숫자를 화면에 적지 않는다

메인 뷰 판정은 **`view.get.streamPort` 가 준 값**과 맞춘다. `13600` 을 화면에 적어 두면
언리얼이 basePort 를 바꾸는 날 조용히 어긋난다 — `cam.list.streamPort` 로 PTZ 를 맞추는
기존 규율과 같다. 테스트가 이것을 지킨다(`simtool.js` 에 `13600` 리터럴 금지).

### 3-4. 클릭은 **뗄 때** 판정한다

한 벌의 몸짓이 둘로 갈린다 — **끌면 회전, 그냥 누르면 클릭.**
누를 때 클릭을 처리하면 **드래그 시작이 매번 클릭**이 되고, 「차량 배치」 모드에서는
그것이 차를 한 대씩 놓는다. 임계값은 4px(손떨림).

움직임·뗌은 **창 전체**에서 듣는다. 영상 밖으로 끌고 나가도 회전이 이어져야 하고,
밖에서 손을 떼도 드래그 상태가 남으면 안 되기 때문이다.

### 3-4-1. 【2026-08-08 변경】 회전은 **오른쪽 버튼**, 이동은 **WASD**

**마스터 지시**: 왼쪽이 아니라 오른쪽 버튼으로 끌 때 회전하게 할 것.
근거가 명확하다 — **왼쪽으로 끌면 브라우저가 `<img>` 를 드래그앤드롭으로 집어**
그 자리에서 조작이 끊긴다. `draggable="false"` 로 그것도 함께 막았다.

부수 효과가 좋다. **왼쪽이 순수한 클릭이 되어 「끈 것인가 누른 것인가」를 가릴 필요가
사라졌다** — §3-4 의 뗄 때 판정은 남겨 두었지만 왼쪽이 회전과 겹치지 않으므로 단순해졌다.
언리얼 뷰포트도 오른쪽 버튼으로 시선을 돌린다.

#### WASD — **방향 계산은 서버가 한다**

처음에 화면(`simtoolViewControl.js`)에서 `Math.cos/sin` 으로 방향 벡터를 만들었더니
**기존 테스트가 잡았다**:

> `카메라 기하를 화면에서 다시 계산하지 않는다 — 규칙은 서버 한 곳이다`
> (화면 스크립트에 `Math.(tan|atan2?|cos|sin)` 금지)

가드레일이 옳다. 방향 벡터도 **카메라 규약의 일부**이고, 특히 메인 뷰의 pitch 는
`cam.setTilt` 와 부호가 반대라 그 규약이 화면에도 있으면 언젠가 반드시 갈린다
— 이 프로젝트는 그 부호에 이미 한 번 물렸다(방향 패드가 거꾸로 돌았다).

그래서 `POST /api/sim/view/move {axis, distance}` 를 새로 두고, 계산은
`src/sim/simProject.ts` 의 `moveAlongView()` 가 한다(`/api/sim/pick` 과 같은 자리).

```
forward = (cos p · cos y,  cos p · sin y,  sin p)   ← pitch 포함 → 내려다보면 내려간다
right   = (−sin y,         cos y,          0    )   ← 항상 수평 → 좌우는 높이를 지킨다
```

- **서버가 `view.get` 으로 지금 자세를 직접 읽는다.** 화면이 들고 있는 값을 믿으면,
  다른 곳에서 시점을 움직였을 때 옛 값 위에 걸음을 쌓아 엉뚱한 자리로 간다.
- 위아래 전용 키는 두지 않았다(요청에 없었다). 지면을 뚫고 내려가도 **S 로 되돌아온다.**
- 키는 **`event.code`** 로 본다 — `event.key` 로 보면 **한글 입력 상태에서 WASD 가 통째로
  죽는다**('ㅈ'·'ㅁ'·'ㄴ'·'ㅇ').
- **입력칸에 글자를 넣는 중이면 손대지 않는다.** 좌표를 타이핑하다 'a' 를 눌렀는데
  카메라가 옆으로 가면 안 된다. 조합키(Ctrl·Alt·⌘)도 비켜 준다.
- 회전과 달리 **덮어쓰지 않고 흘려보낸다.** 누르고 있으면 반복이 오지만 왕복 한 번에
  한 걸음(1m)이라 대략 초당 5걸음이다 — 오는 족족 보내면 손을 뗀 뒤에도 한참 더 나아간다.

### 3-5. 오른쪽 버튼 — 팝업을 막고, 놓친 `mouseup` 을 회수한다

**증상(마스터 보고 2026-08-08)**: 영상 위에서 오른쪽 버튼을 누르면 브라우저 팝업이 뜨고
동작이 멎는다.

원인이 **두 겹**이다.

1. 팝업 자체. 영상 위에서는 쓸 일이 없다 → `contextmenu` 를 `preventDefault` 한다.
   **뷰포트 안에서만** 막는다 — 주소 입력칸 등 나머지는 브라우저 기본 그대로 둔다.
2. **더 나쁜 쪽**: 시점을 끄는 도중에 팝업이 뜨면 사람은 **그 메뉴 위에서 손을 뗀다.**
   그러면 `mouseup` 이 화면에 오지 않아 `pressed` 가 눌린 채로 남고, 이후 **버튼을 놓았는데도
   마우스만 움직이면 시점이 계속 돈다.**

2번은 팝업을 막아도 사라지지 않는다(창 밖에서 떼는 경우가 남는다). 그래서 이동마다
`event.buttons` 로 **지금 눌려 있는지**를 확인해 회수한다 — 왼쪽 버튼이 빠져 있으면 드래그를
그 자리에서 끝낸다.

### 3-6. 더블클릭 조준은 클릭 모드가 꺼져 있을 때만

브라우저는 `down·up(클릭1)·down·up(클릭2)·dblclick` 순으로 준다 — **dblclick 이 올 때는
클릭이 이미 두 번 처리된 뒤**다. 「차량 배치」 모드면 차가 두 대 놓이고 나서 시점이 돈다.

억누르는 장치를 만드는 대신 **겹치지 않게 두었다.** 「영상 클릭」이 「쓰지 않음」일 때만
더블클릭을 받고, 화면이 그 조건을 말한다.

## 4. ⚠ 5fps — 이 설계의 출발점

실측(`cam.streamStatus` main): `targetFps 5 · captureAvgMs 170`.
후처리(모션블러·블룸·DOF·SSR·AA)를 **이미 다 끈** 상태의 값이고 Lumen 품질도 절반이다.
**RPC 왕복이 아니라 영상 자체의 한계**라 스로틀링으로 못 고친다.

그래서 두 가지를 했다.

1. **보낸 값을 즉시 화면에 적는다**(「메인 뷰 시점」 칸).
   영상이 늦게 따라오므로, 숫자가 먼저 움직이지 않으면 사람은 "안 먹었다"고 판단하고
   **더 끌어서 과회전한다.**
2. **한 번에 한 요청만 띄우고 마지막 것만 살린다.**
   드래그는 초당 수십 번 이벤트가 난다. 큐에 쌓으면 손을 뗀 뒤에도 카메라가 계속 움직이고
   그 지연은 되돌릴 수 없다. 응답을 기다리는 동안 온 것은 **덮어쓴다** — 중간 값은 어차피
   지나가는 자세다. (`simtoolCam.js` 의 위치 슬라이더가 같은 이유로 `change` 만 보낸다.)

**결론**: 클릭 계열(배치·선택·조준)은 5fps 에서 문제없다. **드래그 회전만 부드럽지 않다.**
원래 질문("언리얼처럼 마우스로 제어")의 답은 **"조작은 되지만 부드럽지는 않다"** 이다.

## 5. 규약 함정 두 가지

### 5-1. `pitch` 는 양수가 **위**다

`cam.setTilt` 의 `tilt` 는 **양수가 하향**이다. 이름이 다른 것(`tilt` vs `pitch`)이 규약이
다르다는 표식이다. 환산은 `tilt = -pitch`.

그래서 **마우스를 아래로 끌면 `pitch` 를 뺀다.** 이 한 줄이 없으면 방향이 통째로 거꾸로
돈다 — `simtoolCam.js` 의 방향 패드가 같은 함정을 이미 겪었다. 테스트가 이 부호를 지킨다.

### 5-2. `fov` 는 잠금이다

언리얼 `SetFOV` 는 `LockedFOV` 를 건다 — **한 번 값을 주면 앱 재기동 전까지 기본 화각으로
못 돌아간다.** 휠을 한 번 굴린 사람이 원상복구를 못 하게 된다.

그래서 언리얼에 `fov: 0` = 잠금 해제를 넣었고(선행 문서 §2-1), 「화각 되돌리기」가 그것을
부른다. 이 버튼이 **기능이 아니라 안전장치**인 이유다.

## 8. 남은 것 · 알려진 한계

1. **거리 측정 탭은 아직 클릭을 받지 않는다.** `measure.setTargetPoint` 에 픽 좌표를 넘기면
   되지만 이번 범위 밖이다. 화면이 **그렇다고 적어 두었다**(되는 척하지 않는다).
2. **시점 캐시는 우리가 유일한 쓰기 주체라는 전제**다. 다른 곳에서 `view.set` 을 부르면
   화면의 숫자가 잠깐 어긋난다. 다음 조작의 응답이 곧 정본이라 **스스로 교정**되지만,
   교정 전 첫 드래그는 옛 값을 기준으로 시작한다. (연결 시 `probe()` 로 다시 읽는다.)
3. **드래그 감도는 `img` 상자 폭 기준**이라 레터박스가 크면 약간 둔해진다.
   감도의 문제일 뿐 **좌표는 어긋나지 않는다**(클릭은 별도 경로).
4. **5fps** — §4. 드래그 회전의 체감은 여기에 묶여 있다.
