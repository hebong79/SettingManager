## 1. 요약

`apps/backend-core`는 단순한 UE 시뮬레이터 프록시가 아니다. 웹 UI와 AI 에이전트가 같은 REST API로 카메라를 다루도록 만드는 **서버 측 단일 제어 평면**이다. 카메라 자격증명은 서버에만 보관하고, 드라이버 선택·PTZ 정착 대기·능력 확인·영상/스냅샷·센터라이징·캘리브레이션·프로파일 발행·번호판 호밍을 조립한다.

다만 **현재 SettingManager의 활성 카메라**는 `kind: "hucoms"`이므로 BackendCore를 경유하지 않는다. SettingManager는 Hucoms CGI에 직접 연결한다. BackendCore 경유는 SettingManager 카메라 설정을 `kind: "backend-core"`로 등록했을 때만 일어난다.

```mermaid
flowchart LR
    UI[baro_calory Frontend / AI] --> API[backend-core REST API]
    API --> CTRL[control-api.mjs]
    CTRL --> DRV[@baro/cctv-client 드라이버]
    DRV --> REAL[실카메라: Hucoms·IDIS 등]
    DRV --> SIM[UE 시뮬: Hucoms CGI]
    API --> CAL[calibration-manager]
    CAL --> PROF[@baro/profile 해법기·프로파일]
    API --> SCENE[simulator-api]
    SCENE --> RPC[UE /scene/* 씬 편집]
```

## 3. 카메라 제어 관련 소스: 존재함

### 3.1 드라이버와 실제 제어

| 파일 | 역할 |
|---|---|
| `packages/cctv-client/src/camera-driver.mjs` | 공통 카메라 계약과 역량 모델. |
| `packages/cctv-client/src/hucoms-camera-client.mjs` | Hucoms CGI로 PTZ 위치 조회·절대 이동·스냅샷·하드웨어 센터링을 수행한다. |
| `packages/cctv-client/src/idis-camera-client.mjs` | IDIS 계열 제어 구현. |
| `packages/cctv-client/src/device-registry.mjs` | 설정 기반 드라이버 생성/증강의 조립 지점. |
| `packages/cctv-client/src/ptz-settle.mjs` | 물리 카메라 이동 뒤 정착을 판정한다. |
| `apps/backend-core/src/control-api.mjs` | `GET/POST /api/ptz`, `POST /api/ptz/nudge`, `GET /api/snapshot`, `POST /api/center` 등을 HTTP로 연결한다. |

`POST /api/ptz` 및 `POST /api/ptz/nudge`는 카메라를 이동시키며, 일반적으로 정착 후 최종 좌표를 응답한다. `POST /api/center`는 픽셀 좌표를 받아 하드웨어 또는 소프트웨어 센터라이징을 수행한다.

### 3.2 UE 시뮬레이션에서의 경계

UE 시뮬레이터의 **PTZ는 Hucoms CGI 제어 평면**이다. 반면 `scene-control-client.mjs`의 `/scene/*` JSON REST는 주차면·차량·번호판 같은 **월드/씬 편집 평면**이다. 즉 `/scene/*` RPC는 PTZ를 대체하지 않는다.

| 기능 | 경로/프로토콜 | 관련 소스 |
|---|---|---|
| 시뮬 카메라 PTZ | Hucoms CGI | `hucoms-camera-client.mjs`, `control-api.mjs` |
| 시뮬 영상 | MJPEG/스냅샷 | `server.mjs`, `preview-snapshot.mjs` |
| 시뮬 씬 편집 | UE `/scene/*` JSON REST | `scene-control-client.mjs`, `simulator-api.mjs` |

## 4. 캘리브레이션: 운영 구현과 독립 도구가 모두 존재함

### 4.1 운영용 구현

| 파일 | 역할 |
|---|---|
| `apps/backend-core/src/calibration-manager.mjs` | 카메라 이동·스냅샷·정착 대기·샘플 수집·중단 시 home 복귀를 관리하는 운영 잡. `full` 및 `verify` 모드가 있다. |
| `packages/profile/src/calibration.mjs` | 샘플에서 실제 초점거리/펌웨어 초점거리, `zoomHfov`, `centeringGain`, 잔차를 계산하는 순수 해법기. |
| `packages/profile/src/camera-intrinsics.mjs` | 줌→HFOV 표와 센터링 게인 표의 보간·적용. |
| `apps/backend-core/src/profile-store.mjs` | 결과를 `profiles/camera/<id>/rev-NNNN.camprof.json` 불변 리비전으로 발행하고 conformance 사례를 만든다. |
| `apps/backend-core/src/control-api.mjs` | `/api/calibration/start`, `/status`, `/stop`, `/mint`를 제공한다. |

전체(`full`) 캘리브레이션은 줌 앵커별 클릭/이동/착지 샘플을 수집해 다음 두 곡선을 만든다.

| 산출물 | 목적 |
|---|---|
| `zoomHfov` | 표시·오버레이·월드/픽셀 투영에 쓸 실제 수평 화각 곡선 |
| `centeringGain` | 클릭한 대상이 중앙에 오도록 입력 픽셀 오프셋을 줌별로 보정하는 조준용 곡선 |

`verify`는 이미 적용된 보정의 잔차를 측정하는 모드다. 시뮬레이터는 기하학적으로 정확하다는 전제 때문에 `verifyOnly`로 구성될 수 있으며, 이 경우 결과를 발행(`mint`)하지 않는다.

### 4.2 오프라인/교차검증 도구

| 경로 | 용도 |
|---|---|
| `tools/centering_calib/measure_center.py` | PTZ 센터링 스윕 샘플 수집 |
| `tools/centering_calib/analyze.py` | 샘플 분석 및 센터링 오차/게인 검증 |
| `tools/centering_calib/verify_stream_fov.py` | 스트림과 스냅샷의 화각 일치성 확인 |

## 5. 센터라이징: 하드웨어와 소프트웨어 구현이 모두 존재함

### 5.1 하드웨어 센터라이징

Hucoms 드라이버는 카메라의 벤더 기능을 호출해 클릭 지점을 중앙으로 이동시킬 수 있다. 이 경로는 `HucomsCameraClient.centerPoint()`와 `POST /api/center`에 연결된다. 실기 펌웨어의 줌별 오차는 캘리브레이션 산출물 `centeringGain`으로 보정할 수 있다.

### 5.2 소프트웨어 센터라이징

`packages/cctv-client/src/software-centering.mjs`의 `applySoftwareCentering()`는 하드웨어 클릭 센터링이 없지만 절대 PTZ는 가능한 기기에 `centerPoint()`를 계산으로 증강한다.

동작은 다음과 같다.

1. 현재 PTZ와 현재 줌의 HFOV를 읽는다.
2. 클릭 픽셀을 PTZ 델타로 환산한다.
3. 필요하면 줌별 `centeringGain`을 적용한다.
4. 기기의 도달 범위로 부분 클램프한 절대 PTZ 이동을 보낸다.
5. `centering: "software"`, 적용 게인, 클램프 정보를 결과로 반환한다.

활성화 전제는 절대 PTZ 가능, 하드웨어 픽셀 센터링 부재, 유효한 실측 `zoomHfov` 표, 그리고 그 표가 기기 줌 범위를 덮는 것이다. 즉 무근거 기본값으로 임의 센터라이징을 켜지 않도록 설계되어 있다.

### 5.3 가상 PTZ

`packages/cctv-client/src/virtual-ptz.mjs`의 `VirtualPtzCamera`는 고정식 스냅샷 소스 위에 크롭 기반 pan/tilt/zoom을 만든다. 물리 카메라가 움직이는 기능은 아니지만, 상위에서는 동일 PTZ 계약으로 동작한다. 가상 PTZ는 크롭 창을 바꾸므로 이동이 즉시 정착하며 픽셀 센터링은 기하 계산으로 제공된다.

## 6. SettingManager와의 관계 및 영향

### 현재 상태

`SettingMain/config/config.json`의 활성 카메라 `simulator-1`은 `kind: "hucoms"`이다. 따라서 현재 SettingManager의 카메라 제어는 `SettingMain/src/clients/hucomsClient.ts`를 통해 시뮬레이터 Hucoms CGI로 직접 나간다. BackendCore의 포트/URL이 별도로 설정되어 있더라도, 활성 카메라가 `backend-core` 종류가 아니므로 사용되지 않는다.

### BackendCore 경유를 선택하는 경우

SettingManager에서 카메라를 `kind: "backend-core"`로 구성하면 `SettingMain/src/clients/driverFactory.ts`가 `BackendCoreClient`를 만들고, `SettingMain/src/clients/backendCoreClient.ts`가 BackendCore의 `/api/ptz`, `/api/snapshot`, `/api/simulator/slots`를 호출한다. 이 경우에만 BackendCore가 실제 카메라 제어의 중계/제어면이 된다.

### 통합 시 주의점

| 항목 | 영향 |
|---|---|
| 제어 소유권 | BackendCore에는 캘리브레이션·호밍 중 수동 PTZ 이동을 막는 busy guard와 카메라 잠금이 있다. SettingManager가 직접 Hucoms 제어를 병행하면 이 보호를 우회할 수 있다. |
| 좌표·정착 | 양쪽 모두 PTZ 정착 대기를 구현한다. 동일 물리 카메라를 동시에 제어하면 기준 좌표가 경쟁할 수 있다. |
| 화각/센터링 | SettingManager는 현재 줌을 raw 값으로만 다루며, BackendCore는 기기별 `intrinsics`와 센터링 게인을 가진다. BackendCore 결과를 사용할 때는 해당 프로파일을 정본으로 삼아 계산을 중복 구현하지 않는 편이 안전하다. |
| UE RPC | `/scene/*`는 PTZ 제어가 아니라 씬 편집이다. SettingManager에 이를 붙일 때는 BackendCore의 PTZ API와 별도 기능으로 모델링해야 한다. |
| 운영 위험 | 캘리브레이션과 호밍은 실제 카메라를 장시간 이동시킨다. 본 조사는 읽기 전용으로 수행했으며, 실행·이동 검증은 하지 않았다. |

## 7. 최종 판정

| 질문 | 판정 |
|---|---|
| BackendCore는 무엇을 하는가? | 카메라 제어와 자동화 작업을 하나의 서버 측 REST 제어면으로 조립·운영한다. |
