# Hucoms 명시적 이동 모드·좌표 동기화

## 개요

2026-08-02 구현은 장비 프리셋 이동을 캐시 상태로 추론하지 않고 사용자가 `preset` 또는 `coordinate`를 선택하도록 분리했다. `preset`은 항상 장비의 `gopreset`만 실행하며 좌표 캐시를 변경하지 않는다. `coordinate`는 사전에 동기화된 삼축 좌표가 있을 때만 `goptzfpos`를 실행한다. 좌표를 만드는 동작은 별도 `sync-coordinate` 명령으로 한정된다.

근거는 `_workspace/01_architect_plan.md`, `_workspace/02_developer_changes.md`, `_workspace/03_qa_report.md`와 현재 작업 트리의 실제 diff이다.

## 변경 클래스·함수

- `SettingMain/src/api/server.ts`
  - `handle`에 capability 조회, 장비 프리셋 목록, `.../:number/go`, `.../:number/sync-coordinate` 라우트를 추가했다.
  - `readDevicePresetMode`는 본문을 정확히 `{mode:'preset'|'coordinate'}`로 제한하고, `readEmptyDevicePresetBody`는 동기화 본문을 빈 객체로 제한한다.
  - `createDirectPresetClient`, `requireDirectPresetMover`, `toDevicePresetEntryView`로 직접 어댑터·응답 변환을 캡슐화했다.
  - `devicePresetBusy`가 카메라별 go/sync 동시 실행을 잠근다.
- `SettingMain/src/index.ts`: `DevicePresetRegistryStore`를 로드해 서버 의존성으로 주입한다.
- `SettingMain/src/clients/cameraDriver.ts`: 등록 목록/이름을 알 수 없는 capability·slot 공유 타입을 추가했다.
- `SettingMain/web/api.js`: `goDevicePreset`과 `syncDevicePresetCoordinate` API 함수를 추가했다.
- `SettingMain/web/control.js`: capability/목록 조회, 모드 select, 캐시 미동기화 안내, 진행 중 잠금, generation guard, 동기화 후 재조회 및 이동 후 PTZ 갱신을 구현했다.
- `SettingMain/web/index.html`, `app.css`: 접근 가능한 장비 프리셋 영역, 상태(`role=status`, `aria-live`, `aria-busy`), 이동 방식·동기화·새로고침 컨트롤과 스타일을 추가했다.
- `SettingMain/test/server.test.ts`: HTTP 경계에서 모드, strict body, 캐시 불변/미동기화 409, direct factory·capability no-call, UI 계약을 검증했다.

## 로직 의도와 계약

`POST /api/cameras/:cameraId/device-presets/:number/go`는 번호·Hucoms 종류·본문을 먼저 검증한다. coordinate 캐시가 없으면 direct client 생성, capability 조회, `goPreset`/`goPtz` 모두 전에 409 `COORDINATE_NOT_SYNCED`를 반환한다. 이후 capability와 busy를 검사한다. preset 성공 응답은 `mode: "preset"`이고 registry를 쓰지 않는다. coordinate 성공 응답은 캐시된 `ptz`로 한 번 이동하며 `mode: "coordinate"`다. 모드 간 자동 fallback이나 과거 `expectedMode` 계약은 없다.

`POST .../sync-coordinate`는 빈 JSON만 받고 같은 카메라 lock에서 `goPreset → waitForSettle(getPtz) → settled일 때 learn` 순서를 지킨다. 안정 좌표 확보 전에는 저장하지 않으며, `DevicePresetRegistryStore.learn`의 temp-file + rename 단일 commit으로 pan/tilt/zoom/`learnedAt`을 함께 교체한다. timeout은 504, 실패 시 기존 캐시를 유지하고 자동 재시도·재이동하지 않는다.

직접 CGI(`gopreset`, `getptzfpos`, `goptzfpos`)는 `HyucomsDirectPresetClient` 경계에만 남고 `setpreset`은 사용하지 않는다. `CameraDriver`, `BackendCoreClient`, 일반 `/api/presets`에는 장비 이동 명령을 추가하지 않았다. capability는 지원 여부와 안전한 번호 범위만 광고하며 실제 장비 등록 여부·이름 listing/naming은 `unsupported`/`unknown`이다.

## 영향도

- 저장/설정: `SettingMain/src/store/devicePresetRegistryStore.ts`의 JSON 레지스트리와 `learn` 원자 저장 시점이 동기화 성공에만 연결된다. `SettingMain/src/index.ts` 부트스트랩이 해당 store를 로드한다.
- API 소비자: 웹 `SettingMain/web/api.js`·`control.js`가 새 body/라우트를 사용한다. 저장 프리셋(`/api/presets`), PTZ(`/api/ptz`), discovery·stream·snapshot·simulator는 비범위다.
- 공유 타입: `DevicePresetCapability`, `DevicePresetSlot`은 `cameraDriver.ts`에 있으며 BackendCore/일반 드라이버는 이를 실행하지 않는다.
- 설정 포맷: 카메라 설정의 `kind`, `controlUrl`, 인증·timeout을 기존대로 사용하며 새 설정 키는 없다. 인증 query는 응답·로그에 노출하지 않는다.
- 형제 `AgentVLA/ParkAgent/SettingAgent`: 실제 소비자는 확인되지 않았고 API 변경을 전파하지 않았다. 해당 경로를 소비하는 코드가 발견되면 `expectedMode` 제거와 `{mode}` 본문, sync 라우트의 호환성을 별도 검토해야 한다.
- 공유 lock은 cameraId별이므로 다른 카메라 요청은 서로 막지 않는다. UI는 카메라 변경 generation guard로 오래된 응답이 현재 화면을 덮지 않게 한다.

## QA·검증 결과

1차 QA에서 cache-miss coordinate 요청이 direct capability client보다 늦게 거절되는 결함이 발견됐다. `server.ts` 순서를 수정하고 factory/capability 호출 0회 회귀 검증을 추가한 뒤 2차에서 통과했다.

- `npm run typecheck`: 통과
- `npm test -- --run` (또는 QA 표기 `npm run test`): 11 files, 213 tests 통과
- `npm run build`: 통과
- `git diff --check`: 통과(공백 오류 없음, CRLF 경고만)
- 실행 중 서비스에는 읽기 전용 `GET http://127.0.0.1:13030/api/cameras/real-camera-2/device-presets`만 수행해 200과 10개 항목을 확인했다. POST, PTZ, sync, `gopreset`, `goptzfpos`, `setpreset`은 실행하지 않았다.

인앱 브라우저가 제공되지 않아 클릭 기반 브라우저/E2E는 미검증이며, 실제 Hucoms 장비 이동·모션·펌웨어 동작도 물리 이동 위험 때문에 검증하지 않았다. 동시 요청 및 실패 주입 보강 테스트는 QA 권장사항으로 남아 있다.

## 비범위

장비 측 프리셋 등록·이름 변경, `setpreset`, 목록 자동 동기화, 주기적 학습, coordinate 누락 시 preset fallback, 실제 장비 firmware 계약 및 형제 Agent 수정은 포함하지 않는다.
