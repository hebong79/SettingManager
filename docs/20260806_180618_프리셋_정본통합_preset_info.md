# 프리셋 정본 통합 — 카메라 제어 화면 ↔ 옵션 DB 탭을 `preset_info` 하나로

- 날짜: 2026-08-06
- 요청: "카메라제어 페이지와 옵션페이지의 프리셋인포 서로 동기화 되게 해줘 (DB table 에도 동기화)"
- 결론: **정본을 `preset_info` 표 하나로 합쳤다.** 카메라가 `camera_info` 로 옮겨간 것과 같은 방향이다.

---

## 1. 무엇이 문제였나 — 정본이 둘이었다

| 화면 | 읽던 곳 |
|---|---|
| 카메라 제어 (`/`) | `config/presets.json` (파일, 메모리 배열로 캐시) |
| 옵션 → 프리셋 탭 (`/options`) | `preset_info` 표 |
| 주차면 탐색 (`/discovery`) | `preset_info` 표 (`DiscoveryDbStore`) |

같은 "프리셋"이라는 이름으로 **서로 다른 두 벌**이 있었다. 신고 화면이 그 증거다 — 제어 화면에는
`simulator-2` 의 `Preset1` 이 보이는데, DB 탭에는 `real-camera-1` 의 `Preset1`·`Preset2` 만 보였다.
한쪽에서 만든 프리셋이 다른 쪽에 없고, 어느 쪽이 맞는지 판단할 근거도 없었다.

**왜 표가 정본이어야 하는가:** `slot_setup`(커미셔닝 산출)이 `(cam_id, preset_id)` 외래키로
`preset_info` 를 가리킨다. 파일 쪽을 정본으로 삼으면 **주차면이 매달릴 곳이 없는 프리셋**이 된다.
게다가 탐색 화면은 이미 표를 쓰고 있었으므로, 파일을 없애는 쪽이 셋을 한 번에 맞춘다.

## 2. 설계 — 무엇을 바꾸고 무엇을 안 바꿨나

**바꾸지 않은 것이 핵심이다.** `presetRoutes.ts`(REST 라우트)와 `web/control.js`(화면)는 **한 줄도
건드리지 않았다.** `PresetStore` 의 메서드 이름·시그니처를 그대로 두고 **속만 파일 → DB 로 갈았다.**
그래서 "그 목록이 어디서 오는가"만 바뀌고 "그 목록을 어떻게 쓰는가"는 그대로다.

### 2-1. `src/store/presetStore.ts` — 파일 백엔드 → 표 백엔드

```ts
new PresetStore()          // 전: config/presets.json 을 읽어 메모리 배열
new PresetStore(db)        // 후: preset_info 표를 그때그때 질의
```

**캐시를 두지 않았다.** 모든 메서드가 호출 시점에 표를 읽는다. 카메라처럼 재수화 시점
(`ConfigStore.reloadCameras()`)을 관리하는 구조였다면 "DB 는 고쳤는데 화면은 옛 값"이 그대로
남았을 것이다 — 이번 요청이 정확히 그 증상이다. 프리셋은 호출 빈도가 낮아(화면 열 때·저장할 때)
매번 읽어도 값이 싸다. `load()` 는 그래서 사라졌다.

### 2-2. id 두 벌을 잇는 자리

| 밖(REST·화면) | DB |
|---|---|
| `Preset.id` = `"7"` | `preset_info.id` (**대리키**, 표 전체에서 유일) |
| `Preset.cameraId` = `simulator-2` | `camera_info.cam_uuid` |

**왜 `preset_id`(카메라 안 번호)가 아니라 대리키인가:** `/api/presets/:id/goto|PUT|DELETE` 는
**id 하나만으로** 한 줄을 찾는다. 탐색 화면이 쓰는 `p-3`(= `preset_id`)은 카메라를 함께 알아야
유일해진다 — `p-1` 이 카메라마다 하나씩 있으므로 이 자리에 쓰면 **엉뚱한 카메라의 프리셋으로
이동한다.** 대리키는 DB 탭에서 `cam_id`·`preset_id` 를 옮겨도(`movePreset`) 변하지 않는다는 이점도 있다.

### 2-3. `src/db/configPresets.ts` (신설) — 표 ↔ 서비스 사이

`configCameras.ts` 가 카메라에 대해 하는 일과 같은 자리다. `toPreset(row, camUuid)` 변환과
`presets.json` **1회 이관**(`importPresets` / `migratePresetsFile`)을 담는다.

이관 규칙은 카메라 때와 같다 — 이미 그 카메라에 **같은 이름**이 있으면 건너뛰고, 이관 뒤
**다시 읽어 좌표를 대조**한다. 대조가 어긋나면 **파일을 손대지 않는다**(되돌릴 원본을 남긴다).
성공하면 `presets.json` → `presets.json.bak-migrated` 로 이름만 바꾼다. 지우지 않는 이유는
그 파일이 `.gitignore` 대상이라 git 어디에도 사본이 없기 때문이고, **이름을 바꾸는 이유**는
남겨 두면 정본이 둘로 보이는 상태가 계속되기 때문이다.

### 2-4. `src/domain/preset.ts` — 배열 함수 제거

`listFor`·`addPreset`·`updatePreset`·`removePreset` 은 "목록을 통째로 받아 새 목록을 내는" 순수
함수였다. 저장소가 파일 하나라 배열이 곧 전부였기 때문이다. 표로 옮기면서 그 배열이 사라졌고,
남겨 두면 **아무도 안 부르는데 규칙만 두 벌**(도메인 배열판 + 저장소 SQL판)이 된다. 걷어내고
`normalizeName`(이름 규칙)만 남겼다. 좌표 자르기는 종전대로 `clampPtz` 가 한다.

### 2-5. 감수한 손실 — `Preset.updatedAt` 을 없앴다

`preset_info` 에는 갱신 시각 열이 없다. 선택지는 둘이었다:

1. 스키마 v5 로 `updated_at` 열 추가
2. 필드를 없앤다

**2번을 골랐다.** 근거: (a) 이 값을 쓰는 곳이 **하나도 없다** — 화면(`web/`)·MCP·다른 라우트 전수
확인. (b) `schema.ts` 주석이 문서(`my_db_table.md`)의 표를 "임의로 늘리지 않았다"고 못박아 두었다.
(c) 유지하려면 매 조회마다 값을 지어내야 하는데, 그건 "저장 시각"이라는 이름의 거짓말이 된다.

**영향**: `GET /api/presets` 응답에서 `updatedAt` 키가 사라진다. 쓰는 곳이 없어 화면 동작은 같다.

### 2-6. 함께 사라진 것

`PresetStore.removeByCamera()` — **이미 아무도 부르지 않던 죽은 메서드**였다(전수 확인). 표로
옮기면서 그 동작은 스키마가 구조적으로 보장한다: `preset_info.cam_id` 가
`camera_info(cam_id) ON DELETE CASCADE` 다. 죽은 코드를 위해 새 SQL 을 쓰지 않았다.

## 3. 테스트 — 실제 실행 결과

### 3-1. 신규: `test/preset.test.ts` **20/20 통과**

이 파일은 통째로 다시 썼다(옛 순수 함수가 사라졌으므로). **검증 방식이 중요하다** —
한쪽 API 로 쓰고 **반대쪽으로 읽는다.** 양쪽 다 같은 API 로 읽으면 정본이 둘이어도 통과한다.

| 묶음 | 검증 |
|---|---|
| 제어 → DB 탭 | 저장소로 추가하면 표에 줄이 생긴다 / `preset_id` 는 카메라 안에서 1부터 / `place_id` 는 카메라를 따라간다 / 지우면 표에서도 사라진다 |
| DB 탭 → 제어 | 표에 직접 넣은 줄이 **캐시 없이** 바로 보인다 / 표에서 고친 이름·좌표가 반영된다 / `movePreset` 후에도 `id` 가 그대로다 |
| 파일 시절 규칙 유지 | 범위 밖 좌표 자르기 / 같은 카메라 이름 중복 409 / 다른 카메라는 허용 / 자기 이름 유지는 중복 아님 / 이름만·좌표만 수정 / 빈 이름 거부 / 없는 id 404(옛 `p-1` 형식 포함) / 없는 카메라 거부 |
| 이관 | 좌표째 옮겨진다 / 두 번 돌려도 덮지 않는다 / 없는 카메라는 사유를 남기고 건너뛴다 / 깨진 줄은 건너뛰고 나머지는 옮긴다 |
| `toPreset` | 밖으로 나가는 id 가 대리키다(카메라 안 번호가 아니다) |

### 4-1. 이 저장소

| 대상 | 영향 |
|---|---|
| `presetRoutes.ts` · `web/control.js` | **없음 — 한 줄도 안 고쳤다.** 저장소 표면을 그대로 뒀기 때문이다 |
| `/api/presets` 응답 | `updatedAt` 키가 사라진다(§2-5). `id` 가 `"p-3"` → `"7"` 형식으로 바뀐다 — 화면에는 불투명한 값이라 동작은 같다 |
| 주차면 탐색 화면 | **이제 제어 화면과 같은 프리셋을 본다.** 원래도 `preset_info` 를 쓰고 있었으므로 코드 변경은 없지만, **보이는 목록이 늘어난다**(제어 화면에서 만든 것이 함께 보인다). §5 참조 |
| 옵션 DB 탭 | 코드 변경 없음. 표에 줄이 늘어난 것만 보인다. 빈 상태 문구가 이미 "카메라 제어 화면에서 만듭니다"였다 |
| `slot_setup`(커미셔닝) | **좋아진다.** 제어 화면 프리셋이 이제 주차면을 매달 수 있는 실재하는 줄이다 |
| `config/presets.json` | 이관 후 `.bak-migrated` 로 물러났다. 서비스는 더 이상 읽지 않는다 |

| `DiscoveryDbStore` | 코드 변경 없음. 같은 표를 다른 어휘(`p-N`)로 볼 뿐이다 |

## 5. 남은 위험

- **제어 프리셋과 탐색 프리셋이 이제 같은 목록이다.** 원래 다른 두 벌이었으므로, 탐색 화면을
  열면 제어 화면에서 만든 프리셋이 함께 보인다. 이것이 "동기화"의 뜻이므로 의도한 결과지만,
  탐색 쪽에서 **주차면이 딸리지 않은 프리셋**을 만나는 일이 새로 생긴다(빈 목록으로 정상 동작한다).
- **`updatedAt` 제거는 되돌리기 쉽지 않다.** 나중에 필요해지면 스키마 v5 로 열을 추가해야 한다.
- **이관은 이름으로 중복을 판정한다.** 파일과 표에 같은 이름이 다른 좌표로 있었다면 표 쪽이
  남고 파일 쪽은 건너뛴다(사유가 기동 로그에 남는다). 이번 실 데이터에는 그런 충돌이 없었다.
- **회귀 20건이 여전히 빨갛다.** 이번 변경과 무관한 옛 계약 기대이지만, 빨간 줄이 쌓이면
  새 실패를 못 알아본다. 별건으로 정리할 가치가 있다.
