### M2 — 라우트 분할 · VLA 제거 (`3afa38c`)

`server.ts` 가 라우팅·조립·본문 검증·프록시를 모두 떠안고 **542줄**이었다.

```
src/api/
├── server.ts                    542 → 72줄  (조립 + 디스패치만)
└── routes/
    ├── routeContext.ts           86  RouteContext·ServerDeps·공용 본문 해석
    ├── healthRoutes.ts            8
    ├── settingsRoutes.ts        105  설정 · 기기 CRUD · 연결 테스트
    ├── devicePresetRoutes.ts    137  장비 프리셋 capability·이동·좌표 동기화
    ├── ptzRoutes.ts              62  /api/ptz{,/absolute,/nudge,/center}
    ├── presetRoutes.ts           66  로컬 프리셋 + 주차면
    ├── mediaRoutes.ts            64  스냅샷 · MJPEG 스트림
    ├── discoveryRoutes.ts        89  BackendCore 프록시  ⚠ 폐기 예정(M5)
    └── independentCoreRoutes.ts  42  독립 코어          ⚠ 폐기 예정(M6)
```

**디스패치 계약**: 라우트 핸들러는 `true`(내가 응답했다) 또는 `false`(내 소관이 아니다)를 돌려주고,
`server.ts` 가 배열 **순서대로** 넘긴다. 소관이 아닌 것을 404 로 답해 버리면 뒤의 라우트가 영원히 닿지 못하므로,
이 구분이 계약의 핵심이다.

**폐기 예정 두 모듈에는 파일 머리에 사유와 폐기 시점을 적어 두었다** — 옮겨만 두고 고치지 않은 이유가
코드에 남아 있어야 다음 사람이 "왜 이대로 두었나"를 묻지 않는다.

### M3 진입 전 확인이 필요한 것

Q2 의 **"MCP 를 통한 remote 는 컴포넌트 같은 역할"** 이라는 결정을 설계에 반영하려면
한 가지가 더 필요합니다.

> 현재 설계서의 `RemoteCoreProvider` 는 **backend-core 의 REST 를 HTTP 로 직접** 호출합니다.
> "MCP 를 통한" 이 **MCP 서버를 경유해 backend-core 를 부른다**는 뜻인지,
> 아니면 **remote 코어 자체를 MCP 도구로 노출**한다는 뜻인지에 따라
> `RemoteCoreProvider` 의 전송 계층이 달라집니다.

어느 쪽인지 알려주시면 M3 의 포트 정의에 전송 추상화를 어느 수준까지 둘지 확정하겠습니다.
(계약 자체는 전송과 무관하게 설계되어 있어, 어느 쪽이든 포트 정의는 바뀌지 않습니다.)
