## 1. 개요 — 무엇이 왜 일어났고, 무엇을 바꿨는가

### 증상

사용자 화면에 **"영상을 받지 못했습니다 — 옵션 페이지에서 RTSP·시뮬레이터 URL 을 확인하세요"** 토스트가 떴다. 카메라 4대 전부 연결·PTZ·스트리밍이 되지 않았다.

**이 토스트 문구가 진단을 6개월치 엉뚱한 방향으로 끌 뻔했다.** RTSP 도 URL 도 문제가 아니었다. 네트워크는 정상이었다 — 실측으로 7개 엔드포인트가 TCP OPEN 이었고 `ffmpeg 8.1.1` 도 정상 동작했다. 화면이 사용자에게 준 유일한 단서가 **원인과 무관한 문장**이었다는 것이 이 사고의 두 번째 교훈이다(첫 번째는 §2 끝).

### 실측한 실제 응답 (:13030, 수정 전)

`/api/ptz`·`/api/stream`·`/api/snapshot` 모두 4대 전부:

```
400 {"error":"알 수 없는 카메라 종류입니다: undefined"}
```

### 한 문장 원인

**`camera_info` 표에 v2 에서 더해진 열 넷(`timeout_ms`·`kind`·`park3d_cam_id`·`intrinsics`)이 실제로는 붙지 않은 채 `user_version` 만 2 로 기록돼 있었고**, 그 결과 마이그레이션이 영원히 실행되지 않아 `kind` 가 `undefined` 로 읽혔다.

근본 원인의 근본은 **v2 스키마를 판 올림 없이 제자리에서 확장한 것**이다.

### 두 갈래의 수정

| 판 | 내용 | 성격 |
|---|---|---|
| **v3** | 마이그레이션이 반드시 실행되게 고치고, **같은 함정을 판 번호와 무관하게 잡는 안전망**(`verifySchema`)을 신설 | 사고 수습 + 재발 방지 |
| **v4** | 마스터 결정 "`cam_company` 와 `kind` 는 같다. 하나만 사용해줘" — `cam_company` 열을 DB 에서 실제로 삭제 | 설계 결정 반영 |

## 2. 진단 — 원인 체인

실측한 것과 코드에서 읽은 것을 연결하면 이렇게 이어진다.

```
setup.db: camera_info 가 10열인데 PRAGMA user_version = 2
        ↓
migrate() 의 `if (current === SCHEMA_VERSION) return;`  ← 조기 반환
        ↓
upgradeToV2() 가 영원히 호출되지 않는다 (열 넷이 붙지 않는다)
        ↓
toCameraConfig(row) 가 row.kind / row.timeout_ms 를 읽는다 → undefined
   (src/db/configCameras.ts:20-35 — 없는 열은 SQLite 가 아니라 JS 가 undefined 로 답한다)
        ↓
createDriver(camera) 의 switch 가 default 로 떨어진다
   (src/devices/driverFactory.ts:39-42)
        ↓
CameraDriverError('알 수 없는 카메라 종류입니다: undefined', 400)
```

**스트리밍까지 같은 지점에서 죽은 이유**는 코드 배치에 있다. `mediaRoutes.streamMjpeg()` 는 프레임 소스를 만들기 **전에** 드라이버를 만든다:

```
src/api/routes/mediaRoutes.ts:31-33
  const camera = findCamera(config, cameraId);
  const driver = createDriver(camera, config, deps.fetchImpl);   ← 여기서 400
  const source = createFrameSource(camera, driver, config.streaming);
```

즉 `createFrameSource()`(`src/media/frameSource.ts:27`)는 `streamUrl` 의 스킴만 보고 RTSP·HTTP-MJPEG·스냅샷 폴링을 가르므로 **RTSP 든 HTTP 든 상관없이 도달조차 하지 못했다.** 스냅샷 폴링 경로만이 드라이버를 실제로 쓰는데(`snapshotFrames(driver, …)`), 세 경로 전부가 그 앞줄에서 함께 죽은 것이다. 화면의 "RTSP·URL 을 확인하세요" 문구는 이 지점을 전혀 설명하지 못한다.

### 이 사고가 조용했던 이유

DB 에서 없는 열을 읽는 것은 **오류가 아니다.** `SELECT *` 는 있는 열만 답하고, JS 객체에서 없는 키는 `undefined` 다. 그래서 DB 계층·저장소 계층·설정 계층을 전부 통과한 뒤, **원인과 아무 관련 없어 보이는 자리**(드라이버 팩토리)에서 400 이 되어 나온다. 그때는 이미 "DB 가 원인"이라는 단서가 남아 있지 않다.

> **교훈 1**: 판 번호로 갈랐던 자리가 v2 열 넷을 통째로 빠뜨린 자리다. 이 문장은 지금 `src/db/database.ts:70-71` 주석에 그대로 박혀 있다 — 다음 사람이 조기 반환을 되살리지 않도록.

## 3. v3 — 마이그레이션 실행 보장과 재발 방지

### 3-1. 바꾼 것

| 파일 | 변경 |
|---|---|
| `src/db/schema.ts` | `SCHEMA_VERSION` **2 → 3**, 머리말에 안전망의 위치를 기록 |
| `src/db/database.ts` | `migrate()` 조기 반환 제거 · `upgradeToV2()` 무조건 호출 · **`verifySchema()` 신설** |
| `test/database.test.ts` | 회귀 테스트 11건 추가 |

### 3-2. `migrate()` — 구조가 바뀐 두 자리 (`src/db/database.ts:56-89`)

**(가) 조기 반환 삭제.** `if (current === SCHEMA_VERSION) return;` 을 없애고 판 올리기 전체를 `if (current < SCHEMA_VERSION) { … }` 로 감쌌다. `current > SCHEMA_VERSION` 던지기(`:58-62`)는 문구·조건·위치 모두 그대로 두었다 — 옛 코드가 새 파일을 여는 것은 여전히 막아야 한다.

**(나) 판 번호 분기 삭제.** `if (current >= 1) upgradeToV2(db);` → `upgradeToV2(db);` **무조건 호출**.

왜 이것이 옳은가: `upgradeToV2()`(`:104-116`)는 이미 `PRAGMA table_info` 로 **열이 있는지**를 스스로 묻는다. 표가 없는 새 파일에서는 `existing.size === 0` 으로 그냥 빠져나가고(`:106`), 이미 있는 열은 건너뛴다(`:114`). 즉 **판 번호는 애초에 이 함수에 필요 없는 정보였고**, 그 불필요한 조건이 사고의 원인이었다.

### 3-3. 신규 — `verifySchema()` (`src/db/database.ts:152-179`, 비공개)

**역할**: 열기 시점에 **의도와 현실을 직접 맞대 본다.**

| 축 | 동작 |
|---|---|
| 기대 | `:memory:` 에 **`SCHEMA_SQL` 만** 태운 일회용 기준 DB. "코드가 만들려던 모습"을 SQLite 가 스스로 답하게 한다 |
| 실제 | 지금 연 DB |
| 뽑는 것 | 양쪽에서 `sqlite_master` 의 표·**뷰** + 각각의 `PRAGMA table_info` 열 이름 |
| 문제 삼는 방향 | **기대에 있는데 실제에 없는 것만.** 없는 표/뷰, 있는 표의 없는 열 |
| 무시하는 방향 | **실제에만 있는 여분의 표·열은 보지 않는다** (§8-3 의 경고를 반드시 읽을 것) |
| 던지는 것 | `DatabaseError`(statusCode 500), 메시지에 **빠진 이름을 그대로** 싣는다 |
| 부르는 자리 | `migrate()` 의 맨 끝, **판을 올렸든 안 올렸든 항상**(`:88`) |

**왜 기대 목록을 손으로 적지 않는가**: 손으로 적은 목록은 낡는다. `SCHEMA_SQL` 에서 뽑으면 목록 자체가 낡을 수 없고, 새 열을 `SCHEMA_SQL` 에 넣는 순간 기대에 자동으로 들어온다.

**왜 고치지 않고 던지기만 하는가**: 보정까지 하면 "무엇이 왜 어긋났는가"를 아무도 다시 보지 않게 되고, 대조가 **두 번째 마이그레이션 엔진**이 된다. 고치는 것은 마이그레이션의 일이고, 검사하는 것은 대조의 일이다 — 이 역할 분담이 이 함수의 존재 이유다.

**왜 열 이름만 보고 자료형·`NOT NULL`·`CHECK` 는 안 보는가**: `ALTER TABLE ADD COLUMN` 은 `CHECK` 를 붙일 수 없다(§8-2). 제약까지 대조하면 **정상적인 옛 파일이 전부 열리지 않는다.** 데이터를 잃지 않는 쪽을 골랐고, 그 대가가 §8-2 다.

**`sqlite_sequence` 를 양쪽에서 뺀 이유**(`:195`): `AUTOINCREMENT` 표(`preset_info`·`parking_evnt`)를 만들면 SQLite 가 스스로 만드는 장부다. 기준 DB 에는 항상 생기지만 실제 파일에는 없을 수 있어, 걸러 내지 않으면 진짜 문제 옆에 거짓 경보가 한 줄 더 붙는다.

### 3-4. 왜 마이그레이션 프레임워크를 짓지 않았나

판별 파일 분리·다운그레이드·이력 표를 갖춘 프레임워크는 표 7개짜리 단일 서비스에 과하다(CLAUDE.md 2번). 그리고 그것으로도 이번 버그는 못 막는다 — **사람이 단계를 안 쓰면 프레임워크도 조용하다.** `verifySchema()` 는 원인과 무관하게 그 결과(의도와 현실의 어긋남)를 잡으므로, 판을 안 올리든 단계를 빠뜨리든 같은 자리에서 걸린다. 값은 기동 시 1회 + 테스트당 1회의 `:memory:` DB 하나다.

## 4. 데이터 복구 — **설계 가정이 실측에서 뒤집혔다** (반드시 읽을 것)

계획(01 문서, `3-5`)은 백업 파일 `config/config.json.bak-cameras` 를 근거로 **`real-camera-2` 를 `backend-core` 로 되돌리라**고 지시했다. 그 백업 파일의 내용은 실제로 그렇게 적혀 있다 — **실측으로 확인**했다:

```
real-camera-1  kind=hucoms        http://192.168.0.153:80
real-camera-2  kind=backend-core  http://192.168.0.154:80    ← 계획의 근거
simulator-1    kind=hucoms        http://192.168.0.22:8081
simulator-2    kind=hucoms        http://192.168.0.125:13510
(4대 모두 timeoutMs=5000, intrinsics 없음)
```

**그런데 살아 있는 장비에 물어보니 그 가정이 틀렸다.** 리더가 실제 HTTP 로 확인한 결과:

| 시도 | 결과 |
|---|---|
| `real-camera-2` 를 `backend-core` 로 저장 | `502 backend-core endpoint http://192.168.0.154/api/ptz가 HTML HTTP 404을 반환했습니다` |
| `real-camera-2` 를 `hucoms` 로 저장 | **`200 {"pan":2058,"tilt":1487,"zoom":1000}`** — 실제 장비 응답 |

→ **백업 파일의 `kind` 가 낡은 값이었다.** `hucoms` 로 확정했다.

`simulator-2` 도 마찬가지였다. 백업은 `hucoms` 라고 적었지만 실제로는 **Park3D RPC 호스트**였다:

| 시도 | 결과 |
|---|---|
| `hucoms` | 404 |
| `backend-core` | `errors.com.epicgames.httpserver.route_handler_not_found` (언리얼 엔진의 응답) |
| `park3d-rpc` | camId 만 없다는 오류 → **종류는 맞다** |

그 호스트에 카메라가 2대 있음을 확인했다(camId 1·2 는 응답, 3 은 "카메라 없음"). 마스터 결정으로 **camId 1·2 를 각각 별도 카메라로 등록**했다 — `simulator-2` = camId 1, 신규 `simulator-3` = camId 2 (`cam_id=5`).

> **교훈 2 — 백업 파일은 정본이 아니다. 살아 있는 장비가 정본이다.**
> 백업 4건 중 **2건의 `kind` 가 틀렸다.** 백업은 "그때 파일에 적혀 있던 값"이지 "그때 장비가 그랬다"가 아니다. 설계자와 검증자가 이것을 「확인 필요 D — 01 계획의 3-5 가 미적용」으로 보고했는데(`05_architect_plan_v4.md` 확인 필요 D, `07_qa_report_v4.md` 6절), **미적용이 아니라 실측 근거에 따른 의도적 확정**이다. 계획을 따르지 않은 것이 아니라, 계획의 전제가 실측으로 반증되어 폐기된 것이다.

## 5. v4 — 마스터 결정: `cam_company` 를 지우고 `kind` 하나만 남긴다

> "cam_company 와 kind 는 같다. 하나만 사용해줘" (마스터, 2026-08-06)

### 5-1. 왜 하나로 합칠 수 있었나

실 운용 5대에서 두 값이 사실상 1:1 이었다 — 휴컴스 ↔ `hucoms`, 언리얼 Park3D 시뮬 ↔ `park3d-rpc`. **유일한 반례가 `simulator-1`**(제조사 `시뮬레이터` / 프로토콜 `hucoms`)이었는데, 실측 PTZ 200 으로 `hucoms` 가 맞음을 확인했다.

**감수한 손실**: 제조사를 따로 적을 자리가 사라진다. `simulator-1` 은 이름(`UE 시뮬 1 (8081)`)에 시뮬이라는 정보가 남는다. 이 판단과 근거는 `src/db/schema.ts:26-33` 머리말 7번에 기록돼 있다.

### 5-2. 신규 — `dropCamCompany()` (`src/db/database.ts:132-135`, 비공개)

```ts
function dropCamCompany(db: DatabaseSync): void {
  const columns = new Set((db.prepare(`PRAGMA table_info("camera_info")`).all() as unknown as Array<{ name: string }>).map((row) => row.name));
  if (columns.has('cam_company')) db.exec('ALTER TABLE camera_info DROP COLUMN cam_company');
}
```

| 축 | 내용 |
|---|---|
| **판단 기준** | **판 번호가 아니라 열이 있는지.** `upgradeToV2()` 와 의도적으로 같은 관례다 — §2 의 교훈 1 이 코드 관례로 굳은 자리 |
| **멱등** | 이미 지운 파일·처음부터 없는 새 파일에는 아무 일도 하지 않는다 |
| **표가 없을 때** | `PRAGMA` 가 빈 배열 → `has()` 가 false → 그냥 빠져나간다. 뒤이은 `SCHEMA_SQL` 이 13열로 만든다 |
| **부르는 자리** | `migrate()` 판 올리기 블록 안, `upgradeToV2(db);` 다음, `db.exec(SCHEMA_SQL)` 앞(`:72-74`). `CREATE TABLE IF NOT EXISTS` 는 이미 있는 표에 아무 일도 하지 않으므로 앞뒤 어디든 결과는 같지만, **"이미 있는 표의 열을 손보는 일"을 한자리에 모았다** |
| **실패했을 때** | 판 올림과 **같은 트랜잭션** 안이다(`BEGIN` … `PRAGMA user_version = 4` … `COMMIT`). 던지면 판 올림까지 롤백되고 `DatabaseError('DB 스키마 생성에 실패했습니다')` 로 시끄럽게 실패한다 — "조용히 실패하고 판만 오른다"는 성립하지 않는다 |
| **되돌릴 수 없다** | `DROP COLUMN` 은 값을 함께 들어낸다 |

**왜 `DROP COLUMN` 이 가능한가**: SQLite 는 그 열을 PRIMARY KEY·UNIQUE·인덱스·뷰·CHECK·외래키·생성열이 참조할 때만 거부한다. `cam_company` 는 어디서도 참조되지 않는다 — 이 표의 유일한 인덱스 `idx_camera_place` 는 `place_id`(`schema.ts:77`), 뷰 `floor_ROI` 는 `slot_setup` 에서 뽑고(`:122-131`), CHECK 셋은 `cam_type`·`kind`·`intrinsics` 에 걸려 있다(`:67`·`:71`·`:75`). 새 파일 모양과 ALTER 로 보강된 옛 파일 모양 **양쪽에서 실측**했다.

### 5-3. 삭제 — `companyOf()` (`src/db/configCameras.ts`)

`kind` 로부터 제조사 문자열을 유추하던 함수다. 유일한 호출자가 `toCameraRow()` 의 `cam_company:` 대입이었고 이번 변경으로 고아가 되어 **함께 지웠다**(CLAUDE.md 3번 — 내 변경이 만든 고아는 지운다).

남겨 두면 안 되는 이유가 하나 더 있다: "제조사를 유추하는 함수"가 제조사 열이 없는 코드베이스에 떠 있으면, 다음 사람이 그 열을 되살리려 든다.

### 5-4. `simulator-1` 을 위한 데이터 작업은 **하나도 없었다**

`kind` 는 이미 `hucoms` 였고, 제조사 `시뮬레이터` 는 `DROP COLUMN` 이 **열째로 들어내므로** 값이 함께 사라진다. 별도 `UPDATE` 문·스크립트·수동 조작이 필요 없었다 — 마이그레이션 한 번이 전부다. 이 사실은 테스트 `[4-3]` 이 증명한다.

### 5-5. `verifySchema()` 는 손대지 않았다 — 양방향 대조로 바꾸지 않은 이유

우려는 "대조가 여분 열을 안 보므로 드롭이 실패해도 안 잡힌다"였다. 그러나:

- 드롭은 판 올림과 같은 트랜잭션 안이라 던지면 판까지 롤백된다(§5-2).
- 양방향으로 바꾸면 **`verifySchema()` 는 고치지 않고 던지기만 하므로**, 여분 열이 하나 있는 DB 는 서비스가 **아예 기동하지 않는다.** 코드 안에 회복 경로가 없어 사람이 `sqlite3` 로 직접 손대야 한다.
- 남은 여분 열의 실제 피해는 사실상 0 이다(`NOT NULL DEFAULT ''` 라 INSERT 가 열 이름을 안 대도 들어간다).
- **무해한 상태를 기동 불능과 맞바꾸는 셈**이라 그대로 두었다.

대신 그 자리를 **테스트 `[4-1]` 하나로 막는다.** 이것이 §8-3 의 경고로 이어진다.

## 8. 미해결 · 별건 (숨기지 않는다)

### 8-1. ⚠ `simulator-2`·`simulator-3` 의 스트림 URL 이 어긋나 있다 — **지시 대기 중**

두 카메라가 **똑같이 `http://192.168.0.125:13602/stream`** 을 가리킨다(§7-1 실측). 이 값은 작업 중 사용자가 UI 로 직접 고친 것이다.

리더가 실제 프레임을 눈으로 대조한 결과:
- `:13601` 과 `:13602` 는 **서로 다른 화면**이다 (13601 = 넓은 구도, 13602 = 확대 구도).
- PTZ 줌 값(camId 1 = 1.62, camId 2 = 2.90)과 대조하면 **13601 → camId 1, 13602 → camId 2**.

따라서 현재 `simulator-2` 는 **PTZ 로는 camId 1 을 움직이면서 화면은 camId 2 를 보여주는 어긋난 상태**다. 사용자에게 보고했고 **지시를 기다리는 중**이다. 이 문서 시점에 고쳐지지 않았다.

### 8-2. 옛 파일(=운영 DB)에는 `kind`·`intrinsics` 의 CHECK 제약이 없다

`ALTER TABLE ADD COLUMN` 은 `CHECK` 를 붙일 수 없다(기존 줄 검사가 필요하므로). 그래서 **보강된 옛 파일과 새로 만든 파일의 제약이 다르다.** 검증자 실측:

```
옛(ALTER 보강) 파일  kind='엉터리'     : 들어갔다 (제약 없음)
새 파일             kind='엉터리'     : 거절 (CHECK constraint failed: kind IN (…))
```

- **HTTP 경로는 막혀 있다** — `dbRoutes.merged()` 의 `KINDS` 화이트리스트(`src/api/routes/dbRoutes.ts:230, 239`)와 `intrinsicsJson()`(`:256-261`)이 거른다.
- **남는 위험**: 누가 `sqlite3` 로 직접 UPDATE 하면 DB 가 막지 않는다.
- 고치려면 표를 다시 만들어 옮기는 마이그레이션이 필요하고 **이번 범위 밖이다.** `DROP COLUMN` 은 이 상태를 바꾸지 않는다(실측 확인). 테스트로 굳히지도 않았다 — 현재 동작을 "옳다"고 못박는 셈이 되기 때문이다.

### 8-3. **⚠⚠ `verifySchema()` 는 여분 열을 문제 삼지 않는다 — 안전망은 테스트 `[4-1]` 하나뿐이다**

검증자가 실측으로 확인했다. `database.ts` 에서 **`dropCamCompany(db);` 한 줄만 지우면**:

- `user_version` 은 **4 로 올라가고**
- `cam_company` 열은 **그대로 남는데**
- `verifySchema()` 를 포함해 **103건이 전부 통과한다.**

이 사고를 잡는 것은 저장소 전체에서 `test/database.test.ts` 의 **`[4-1]` 한 건**뿐이다. 실패 문구:

```
AssertionError: expected [ 'cam_id', 'cam_name', …(12) ] to not include 'cam_company'
 ❯ test/database.test.ts:579:27
```

> **그 테스트를 지우거나 `toHaveLength(13)` 만 남기고 느슨하게 고치면, 같은 사고가 CI 를 조용히 통과한다.** `toHaveLength(13)` 은 "다른 열 하나를 잃고 `cam_company` 는 남은" 파일과 정상 13열 파일을 구분하지 못한다. `[4-1]` 은 앞으로 손대지 말아야 할 자리다.

### 8-4. 기존 테스트 20건 실패 — **이번 변경 전부터, 무관함을 두 번 확인**

| 파일 | 건수 | 원인 |

백업 `config.json.bak-cameras` **4대 모두에 `intrinsics` 가 없었다**(실측 확인). 즉 브리지 박스줌이 꺼져 있는 것은 **이관 전부터의 상태**이며 이번 수정으로 켜지지 않는다. 줌→화각 표를 채우는 일은 **별건**이다.

### 8-6. `docs/my_think/my_db_table.md` 와 실제가 달라졌다

`:26` 의 `cam_company : 제조회사 ( 휴컴스, 아이디스 등 )` 는 **마스터의 원 설계 문서**다. `cam_company` 삭제로 그 문서의 `camera_info` 정의와 실제가 어긋났다. 지난 기록을 소급해 고치지 않는 원칙에 따라 **손대지 않았고**, 대신 `src/db/schema.ts:26-33` 머리말 「문서와 다른 점」 7번에 그 사실과 근거를 기록했다. **문서 자체를 고칠지는 마스터 판단.**

### 8-7. `routeCatalog.ts:134` notes 가 여전히 사실과 다르다

`'cam_name·cam_type·place_id 만. **접속정보는 config.json 이 주인이다.**'` — 이번에 `cam_company` 라는 단어만 지웠다. 그러나 `merged()` 는 `url`·`user_id`·`password`·`rtsp_url`·`kind`·`timeout_ms`·`park3d_cam_id`·`intrinsics` 도 받고(`dbRoutes.ts:219-237`), **접속정보의 주인은 이제 config.json 이 아니라 DB 다.** 외과적 변경 원칙에 따라 이번 결정과 무관한 부분은 고치지 않았다. **별건**이며, 어떤 테스트도 이 드리프트를 잡지 않는다(`08_doc_impact.md` §3).

### 10-2. 되돌리는 방법

1. **개발 서버를 정지한다**(`:13030`). 정지 확인까지.
2. `config/setup.db` · `setup.db-wal` · `setup.db-shm` **세 파일을 모두 지운다.**
   `VACUUM INTO` 스냅샷은 단독으로 완전하므로, 옛 `-wal`/`-shm` 을 남기면 **다른 DB 의 저널을 붙이는 꼴**이 된다.
3. bak 파일을 `setup.db` 로 복사한다.
4. **소스도 함께 되돌려야 한다.** 판 4 로 올라간 파일은 옛 코드로 열 수 없다 — `migrate()` 의 `current > SCHEMA_VERSION` 이 `DatabaseError` 로 던진다(`database.ts:58-62`). 반대로 판 3 짜리 백업을 v4 코드로 열면 **드롭이 다시 실행되어 그냥 v4 가 된다**(멱등).

즉 **"DB 만 되돌리기"는 판을 내리는 방향으로만 안전하고, 코드를 되돌릴 때는 DB 도 함께 되돌려야 한다.** 자세한 절차는 `_workspace/08_doc_impact.md` §7.
