## 1. 한 줄 요약

실카메라 연결은 **네 겹**이다 — ① DB `camera_info` 가 접속 정보의 정본이고, ② 라우트는 `CameraDriver` 계약 하나만 보며, ③ 벤더 드라이버(휴컴스 · IDIS)가 그 뒤에 **나란히** 서고, ④ **제어 평면(HTTP CGI)과 영상 평면(RTSP)은 서로 다른 주소·포트를 쓰는 별개의 길**이다.

이 문서에서 가장 조심할 두 가지:

- **`kind` 는 프로토콜이지 실물/시뮬 구분이 아니다.** `simulator-1` 은 `kind=hucoms` 지만 UE 시뮬이다.
- **휴컴스와 IDIS 는 틸트의 부호·원점이 반대이고 줌 눈금의 뜻이 다르다.** 이걸 모르면 조준이 수 배 어긋난다(§6).

## 3. 지금 등록된 카메라 — 무엇이 실물이고 무엇이 시뮬인가

`[DB camera_info 전수, 2026-08-06 23:19]`

> **주소는 자리표시자다.** 이 저장소는 공개돼 있고, `.gitignore` 가 `setup.db`·`config.json` 을
> 막아 둔 이유가 "실제 접속 정보(카메라 IP·계정·비밀번호)는 커밋하지 않는다" 이기 때문이다.
> 문서가 그 규칙을 우회하면 막아 둔 의미가 없다.
>
> **실제 값의 정본은 DB `camera_info` 다** — 옵션 화면의 `DB` 탭이나
> `GET /api/db/cameras` 로 본다. 구조를 설명하는 데 실제 IP 값은 필요하지 않고,
> 아래 표에서 중요한 것은 주소가 아니라 **어느 기기가 실물이고 어느 것이 시뮬인가**다.

### 3-1. ⚠ `kind=hucoms` 인 것이 실물이라는 뜻이 아니다

`simulator-1` 이 그 반례다 — `kind` 는 **어느 프로토콜로 말을 거는가**이지 상대가 실물인지 시뮬인지를 담지 않는다 `[코드 config/types.ts:3~18]`.

**세 기기를 실물/시뮬로 가르는 유일한 실용 신호는 영상 URL 의 스킴**이다: 실카메라 2대는 `rtsp://…:554/…` 이고 시뮬은 `http://` 직결 포트다. 다만 이것도 규약이지 강제가 아니다 — **DB 어디에도 "이 기기는 실물이다"라는 칸이 없다.**

### 3-2. IDIS 는 **로스터에 한 대도 없다**

`kind = 'idis'` 인 행은 `[DB]` 상 **0건**이다. 사실은 이렇다:

- ✅ 드라이버·전송·좌표변환·Digest 인증·DB 열(`insecure_tls`)·옵션 화면 체크박스까지 **코드 경로가 완비돼 있다** `[코드 devices/idis/ 9파일]`.
- ❌ **실기 검증은 한 건도 없다.** 전 테스트가 목(mock) 기반이다 `[docs/20260806_222856 §9]`.
- 즉 **"IDIS 카메라가 연결돼 있다"는 서술은 거짓**이고, **"IDIS 카메라를 등록하면 붙을 준비가 돼 있다"가 사실**이다.

### 4-2. 제어 평면과 영상 평면은 **별개의 길**이다

이 문서에서 두 번째로 중요한 그림이다.

```mermaid
graph LR
    subgraph P1["제어 평면 — 무엇을 명령하는가"]
        C1["camera_info.url<br/>http://<카메라1-IP>:80"]
        C2["HTTP CGI<br/>휴컴스 ptzf_status.cgi<br/>IDIS webSetup.cgi"]
        C3["좌표 읽기 · 이동 · 스냅샷"]
        C1 --> C2 --> C3
    end

    subgraph P2["영상 평면 — 무엇이 보이는가"]
        S1["camera_info.rtsp_url<br/>rtsp://<카메라1-IP>:554/stream1"]
        S2["ffmpeg 로 MJPEG 전사"]
        S3["브라우저 img 태그"]
        S1 --> S2 --> S3
    end

    WARN["⚠ 둘이 같은 카메라인지<br/>자동 보장이 없다"]
    P1 -.-> WARN
    P2 -.-> WARN
```

**그림이 말하는 것**: 두 평면은 **주소도 포트도 프로토콜도 다르다.** 실카메라에서는 `:80`(HTTP CGI)과 `:554`(RTSP)이고, 서버가 둘을 잇는 유일한 근거는 `camera_info` 한 줄에 나란히 적혀 있다는 사실뿐이다.

**어긋나면 어떻게 보이는가**: PTZ 숫자는 정상적으로 바뀌는데 **그림이 절대 안 바뀐다.** 통신 로그에는 오류가 하나도 남지 않는다. 2026-07-31 에 시뮬에서 실제로 났던 사고이며 `[docs/20260731_200035 §3]`, **실카메라에서는 IP 를 잘못 짝지으면 같은 증상이 난다.**

> **IDIS 를 등록할 때 이 평면에서 걸리는 함정 셋** `[실측 DC-S6261XT 2026-07-29, cameras.md]`
>
> 1. **`trackID` 번호를 믿지 마라.** 매뉴얼의 "1=H.264, 2=MJPEG" 는 규약이 아니라 어느 기기의 프로파일 구성이었다 — **실측기는 정반대**로 `trackID=1` 이 MJPEG 1920×1080@15, `trackID=2` 가 H.264 640×360@15 였다(ffprobe 실측). **번호가 아니라 `ffprobe` 로 확인할 것.**
> 2. **IDIS 는 RTSP 실데이터 세션을 하나만 준다.** DESCRIBE(ffprobe)는 추가 세션에도 응답하지만 **데이터는 먼저 잡은 세션에만 온다** — 즉 `ffprobe` 로 확인하는 동안 스트림을 켜 두면 한쪽이 빈다.
> 3. **전송 스킴은 기기가 정한다.** 실측기는 **80 만 열고 443 은 무응답**이다. 거부가 아니라 **무응답**이라, 잘못 잡으면 실패가 빠르게 나지 않고 **타임아웃까지 매달린다** — §5-3 의 "명시적 `setTimeout`" 이 이것 때문에 필요하다.
>
> 이 서비스는 RTSP URL 을 **조립하지 않고** `rtsp_url` 에 적힌 전체 URL 을 그대로 쓴다 `[코드 media/rtspUrl.ts]`.

**그림이 말하는 것 — 그리고 그림의 붉은 부분**:

- 라우트는 벤더를 모른다. `CameraDriver` 계약 하나만 보고, 분기는 `driverFactory.createDriver()` **한 곳**에만 있다 `[코드 devices/driverFactory.ts:12~56]`.
- **단 하나의 예외가 장비 프리셋이다.** `devicePresetRoutes` 는 `CameraDriver` 를 거치지 않고 `HucomsPresetClient` 를 **직접** 만들어 부른다 `[코드 devicePresetRoutes.ts:93~100]`. 이유는 이 기능이 계약 밖(장비 내장 프리셋 번호 1~255)이고, 일부 장비가 LF-only 헤더를 보내 `insecureHTTPParser` 를 **이 클래스 요청에만** 한정해야 하기 때문이다 `[코드 hucomsPresetClient.ts:17~21]`.
- 그 예외의 대가: 이 라우트는 `camera.kind !== 'hucoms'` 이면 **501** 이다 `[코드 devicePresetRoutes.ts:23,34]`. **IDIS 는 드라이버에 `listPresets`·`gotoPreset`·`setPreset`·`removePreset` 이 전부 구현돼 있는데도 HTTP 로 닿을 수 없다**(§10-2).

> **장비 프리셋 번호의 상한이 근거마다 다르다.** 코드는 `1..255` 로 막고 `PresetSupported: Yes` 를 상한 미상으로 보아 255 를 쓴다 `[코드 hucomsPresetClient.ts:36,148~150]`. 그러나 상류 실측 표는 **휴컴스 프리셋을 `1~128`** 로 적는다 `[실측 cameras.md §역량 표]`. **충돌은 아니다** — 코드가 먼저 `capabilityptz.cgi` 로 기기에 물어보고, 기기가 숫자를 답하면 그 값이 이긴다. 다만 **`Yes` 만 답하는 기기에서는 129~255 가 실제로는 없을 수 있다** `[미확인]`.

**이 설계의 유일한 함정**: DB 를 고쳐도 메모리의 `config.cameras` 는 옛 값이다. 그래서 카메라를 쓰기한 라우트는 **반드시 `configStore.reloadCameras()` 를 부른다** `[코드 dbRoutes.ts:92,127,138]`. 안 부르면 **방금 바꾼 IP 가 아니라 이전 주소로 다음 PTZ 명령이 나간다.**

| 어디에 사는가 | 무엇이 |
|---|---|
| `camera_info` (DB) | 카메라 전부 — id·이름·kind·제어 URL·계정·비밀번호·RTSP URL·타임아웃·장소·`insecure_tls`·`intrinsics` |
| `config.json` | 서버 host/port, 스트리밍(ffmpeg·fps·화질·기동 타임아웃), 코어 제공자, 검출기 URL, `activeCameraId` |
| `preset_info` (DB) | SettingManager 자체 프리셋(이름 + 좌표) |
| `config/device-preset-registry.json` | 장비 내장 프리셋의 **우리 쪽 이름·학습 좌표** — 장비가 이름을 주지 않기 때문 |

**그림이 말하는 것**: 실카메라의 영상은 **ffmpeg 를 반드시 거친다.** `ffmpeg` 를 PATH 에서 못 찾으면 스트림은 502 로 실패한다 — 그 사유가 문구에 그대로 실린다 `[코드 frameSource.ts:97~100]`.

**두 ffmpeg 플래그가 왜 짝인가 — 실카메라에서 잰 숫자** `[실측 baro_calory/docs/cameras.md §RTSP 타임스탬프는 믿지 않습니다, 2026-07-29]`:

> **휴컴스 실기(`153`)**: 시작 구간 채움으로 첫 프레임이 십수 회 반복되어 **표본 중복 64%**. 두 플래그를 넣은 뒤 **64% → 0%**.

RTP 타임스탬프가 실제 프레임률과 다르면 기본 CFR 동기화가 빈 자리를 **복제 프레임**으로 채운다 — 대역폭이 같은 그림에 쓰이고, 화면은 "움직이는데 안 움직이는 것처럼" 보인다.

**RTSP 경로 `stream1` 의 근거**: `stream1`/`stream2` 는 **휴컴스 계열에서 실측 검증된 경로**다 `[실측 cameras.md §RTSP 경로는 벤더 규약입니다]`. 다만 그 문서는 **포트를 적지 않는다** — 이 저장소의 `:554` 는 `camera_info` 에 등록된 값이다 `[DB]`. 그리고 **경로는 벤더 규약이지 범용 규약이 아니다**: 전역 `stream1` 을 모든 기기에 적용했다가 어긋난 사건이 상류에 있다.

## 6. 좌표 규약 — **여기를 빠뜨리면 조준이 수 배 어긋난다**

계약 좌표는 **Hucoms 논리 좌표계**다. 어느 벤더든 API 표면에서는 이 좌표만 쓰고, 변환은 드라이버 안에 갇혀 있다.

| 축 | 계약 (API 표면) | 단위 | 범위 밖 처리 |
|---|---|---|---|
| `pan` | `0 ~ 35999` | 0.01° | **감긴다**(원) — 36000 → 0 |
| `tilt` | `−2000 ~ 9000`, **+ 가 아래**, 0 = 수평 | 0.01° | 잘린다 + `limited[]` 로 보고 |
| `zoom` | `0 ~ 65535` | **불투명 raw** | 잘린다 + `limited[]` 로 보고 |

### 6-1. 휴컴스 ↔ IDIS — 같은 이름, 다른 뜻

**이 표가 이 문서에서 가장 중요하다.**

| 축 | 휴컴스 (= 계약과 동일) | IDIS 와이어 | 변환 `[코드 idisCoords.ts]` |
|---|---|---|---|
| **pan** | `panpos 0..35999` 무부호 | `absPan −18000..18000` `[매뉴얼 §56]` | 와이어→계약 `((absPan%36000)+36000)%36000` · 계약→와이어 감아서 `>18000` 이면 `−36000`. **자르지 않고 감는다** |
| **tilt** | `tiltpos −2000..9000`<br/>**+ 가 아래**, **0 = 수평** | `absTilt`<br/>**+ 가 위**, **0 = 수직 아래** `[실측 DC-S6261XT 2026-07-29]` | **`9000 − x`**(자기역함수). 보내기 전 `[0, 9000]` 로 자른다 |
| **zoom** | `zoompos 0..65535`<br/>**불투명 raw** — "0 = 광각" | `absZoom` = **배율 × 100**<br/>**"100 = 광각"** | 숫자는 항등 통과. 보내기 전 `[100, 1200]` 로 자른다 `[실측 — 이 모델의 광학 x12]` |
| **centerPoint** | 1920×1080 절대 픽셀 (펌웨어가 처리) | `pointPan`·`pointTilt` `0..100000` `[매뉴얼 §58]` | `round(x/1920 × 100000)` (쓰기 전용) |

**틸트는 부호도 원점도 반대다.** 다행히 두 범위가 정확히 겹쳐 `9000 − x` 한 식으로 양방향이 닫힌다.

> **독립 교차검증** `[실측]` — `absZoom=100` 에서 5°씩 움직여 상호상관으로 화면 이동을 재면 tilt 37.6 px/°, pan 29.6 px/° 다. 카메라가 수평에서 40° 내려가 있다면 팬의 화면 변위는 `cos40° = 0.766` 배라 38.6 px/° 가 되어 틸트와 **3% 안에서 일치**한다. **원점이 수평이었다면 이 일치가 나오지 않는다.**

**줌은 눈금의 뜻이 다르다.** 숫자 범위가 계약 안에 들어가므로 항등 통과가 계약 위반은 아니지만, 이 차이를 무시하고 Hucoms 기본 화각 곡선을 폴백으로 들면 **화각이 약 5배 틀린다** `[실측 사고]`. 그래서 IDIS 드라이버는 `intrinsics` 를 **절대 지어내지 않는다**.

### 6-2. 보내기 전에 자른다 — 기기는 성공이라 답하면서 다른 데로 간다

| 벤더 | 보낸 값 | 기기의 답 | 실제 결과 |
|---|---|---|---|
| 휴컴스 | 범위 밖 | **`[미확인]`** | **기록이 없다** — 아래 주 참조 |
| IDIS | `absTilt = 12000` | `returnCode=0` | 9000 에서 클램프 |
| IDIS | **`absTilt = −3000`** | **`returnCode=0`** | **오토플립 — 팬을 180° 돌려 해결한다** `[실측]` |
| IDIS | `absZoom = 3000` | `returnCode=0` | 1200 |
| IDIS | `absPan = −18000` | `returnCode=0` | 18000 (원이라 같은 방향) |

**오토플립이 특히 위험하다 — 성공 응답을 받고 정반대를 본다.** 계약이 허용하는 `tilt = −2000`(수평 위 20°)이 그대로 나가면 `absTilt = 11000` 이 되어 이 갈래에 빠지므로, `tiltToWire` 가 뒤집은 뒤 실측 도달 범위로 자른다. 참고로 **휴컴스는 `tiltpos = −2000`(수평 위 20°)에 실제로 도달할 수 있다** `[실측 baro_calory/docs/cameras.md §좌표 규약]`.

> **휴컴스 행을 `[미확인]` 으로 둔 이유 — 앞선 문서를 정정한다.** `docs/20260731_200035 §6` 은 "기기는 범위 밖 요청에 성공이라 답하며 조용히 다른 데로 간다(baro_calory 실측)"라고 적었으나, **`baro_calory/docs/cameras.md` 를 다시 읽어 보면 그 실측은 IDIS 절에만 있고 휴컴스에 대응하는 기록이 없다.** 같은 문서의 역량 표에서 휴컴스의 `미구현 액션의 응답` 칸은 `—`(미기록)다. **휴컴스도 그럴 것이라는 추정은 근거가 없으므로 여기서는 `[미확인]` 으로 둔다.** 다만 코드는 어느 쪽이든 안전하다 — `HucomsClient.goPtz` 가 보내기 전에 `clampPtz` 를 건다 `[코드 hucomsClient.ts:45~46]`.

### 6-3. ⚠ 알려진 구멍 — IDIS 에서는 `limited[]` 약속이 깨진다

`/api/ptz/absolute` 의 `limitedAxes()` 는 **계약 상수**(`0..65535`)로 판정한다 `[코드 domain/ptz.ts:61~69]`. 그래서 IDIS 기기에 `zoom: 3000` 을 보내면 **응답은 `limited: []`** 인데 드라이버는 1200 으로 자른다 — **"잘린 축은 숨기지 않는다"는 약속이 이 기기에서만 깨진다.** 기기별 도달범위 도입은 도메인·라우트·화면에 걸친 별건으로 미결이다 `[docs/20260806_222856 §4-4]`.

### 7-3. PTZ 절대 이동 + **정착(settle) 대기**

```mermaid
sequenceDiagram
    autonumber
    participant W as 브라우저
    participant SM as SettingManager
    participant D as 드라이버
    participant CAM as 실카메라

    W->>SM: POST /api/ptz/absolute {pan, tilt, zoom, speed?}
    SM->>SM: 세 값이 모두 숫자인가 - 아니면 400
    SM->>SM: limitedAxes - 자르기 **전에** 무엇이 잘릴지 기록
    SM->>D: goPtz(target, speed)
    D->>D: clampPtz - 팬은 감고 틸트·줌은 자른다
    D->>CAM: goptzfpos + panspeed/tiltspeed/zoomspeed
    CAM-->>D: 200

    Note over SM,CAM: 카메라는 "이동 완료"를 알려주지 않는다
    SM->>D: waitForSettle
    D->>CAM: getptzfpos
    CAM-->>D: 좌표 A
    loop 250ms 간격 · 최대 10초
        D->>CAM: getptzfpos
        CAM-->>D: 좌표 B
        D->>D: pan 순환거리 ≤ 10cd · tilt ≤ 10cd · zoom ≤ 10raw 인가
    end

    alt 연속 두 번이 허용오차 안
        D-->>SM: {ptz, settled:true}
    else 10초 초과
        D-->>SM: {ptz: 마지막 값, settled:false} - **던지지 않는다**
    end
    SM-->>W: 200 {ptz, limited[], settled}
    alt limited 가 비어 있지 않음
        W-->>W: 상태줄 - 어느 축이 한계에 닿았는지
    else settled=false
        W-->>W: 상태줄 - 아직 이동 중입니다
    end
```

**정착 판정 규칙** `[코드 waitForSettle.ts · domain/settle.ts]`

| 항목 | 값 | 왜 |
|---|---|---|
| 폴링 간격 | 250ms | — |
| 허용오차 | pan·tilt **10cd(0.1°)** · zoom **10 raw** | — |
| 판정 | **연속 두 번 읽은 값**이 허용오차 안 | 명령 직후 읽으면 이동 중간값이 잡힌다 (실측: 시뮬에서 pan 1296 → 목표 1496 인데 직후 읽기가 1446) |
| 팬 비교 | **순환 거리** `min(d, 36000−d)` | 없으면 0/36000 심 근처에서 영원히 안 멈춘다 |
| 상한 | 10초. 초과 시 **던지지 않고** `settled:false` | 마지막 좌표도 쓸모 있는 정보다. 던지면 화면이 "어디에 있는지조차" 못 보여준다 |

**실측 이동 시간** `[실측 DC-S6261XT 2026-07-29]`: 팬 5° 이동에 **약 400ms**(200ms 에는 미도달, 400ms 에 도달). 폴링 간격 250ms 는 이 규모의 이동을 최소 2회 안에 잡는다.

> ⚠ **줌에는 기기 자체의 스텝 그리드가 있다** `[실측]` — 명령값과 몇 단위 어긋난다(`499` 를 보내면 `490` 에 선다). 정착 판정의 zoom 허용오차가 **10 raw** 인 것이 이 어긋남을 흡수한다. **그리드 간격이 10 을 넘는 기기에서는 줌이 영원히 "정착하지 않은" 것으로 보일 수 있다** `[미확인]` — 그 경우 `settled:false` 로 나오지 마지막 좌표는 정상이다.

> **`nudge`(방향 버튼)는 정착을 두 번 기다린다** `[코드 ptzRoutes.ts:39~46]`. ① **기준 자세**도 멈춘 값이어야 하고 ② 착지도 멈춘 뒤에 읽는다. 기준을 안 기다리면 중간값에 델타를 더하게 되어 **목표가 매번 뒤로 밀린다** → "눌러도 안 움직인다".

### 7-7. IDIS Digest 401 → 재시도 왕복

```mermaid

        T-->>D: 그대로 반환 - 재시도 없음
    else 401 + WWW-Authenticate
        CAM-->>T: 401 Digest realm=WEB SERVER · nonce=… · qop=auth · algorithm=MD5
        T->>T: 챌린지를 읽어 **기기가 요구한 방식**을 고른다
        alt Digest
            T->>T: HA1=md5(user:realm:pass) · HA2=md5(METHOD:uri)<br/>response=md5(HA1:nonce:nc:cnonce:qop:HA2)<br/>**uri 는 path+query — HA2 와 uri= 에 같은 값**
        else Basic
            T->>T: base64(user:pass)
        else 우리가 모르는 방식 · algorithm≠MD5 · qop 에 auth 없음
            T-->>D: 401 을 그대로 올린다 / 던진다<br/>**조용히 MD5 로 계산하지 않는다**
        end
        T->>CAM: ② 같은 요청 + Authorization 헤더<br/>POST 면 본문도 재전송 · 쿼리로 새지 않는다
        alt 성공
            CAM-->>T: 200 returnCode=0&…
            T-->>D: IdisResponse
        else 또 401
            CAM-->>T: 401
            T-->>D: 401 - **한 번만 재시도한다**
        end
    end
```

**그림이 말하는 것**: **인증 방식을 우리가 고르지 않는다.** 매뉴얼은 `RFC2617` 이라고만 적어 Basic 도 포함되지만 실측기는 **Basic 에 401** 이었다 `[실측 DC-S6261XT]`. 그래서 챌린지를 읽어 방식을 고르고, 모르는 방식이면 **임의로 Basic 을 시도하지 않는다.**

`MD5-sess`·`SHA-256` 은 `[미확인]` 이라 **조용히 MD5 로 계산하지 않고 던진다** — 잘못된 response 를 보내면 401 만 돌아와 원인이 인증 방식이라는 사실이 어디에도 드러나지 않는다 `[코드 digest.ts:50~70]`.

## 8. 오류·상태 처리 요약

| 상황 | 응답 | 어디서 결정되나 |

| IDIS 인증·권한 거절 | `502` (**401 이 아니다**) | `IdisAuthError` — 401 을 그대로 내보내면 사용자 **자신의** 세션이 끊긴 것처럼 보인다 |
| 기기가 그 기능을 하지 않음 | `501` (확정 답 — 재시도 안 함) | `IdisUnknownActionError` · `devicePresetRoutes` · `CoreUnsupportedError` |
| 도달범위에서 잘림 | `200` + `limited[]` | `limitedAxes` (⚠ IDIS 에서는 §6-3) |
| 10초 안에 안 멈춤 | `200` + `settled:false` | `waitForSettle` |
| 연결 테스트 실패 | `200` + `ok:false` | `dbRoutes` |
| 스트림 첫 프레임 실패 | `502` + 사유 | `mediaRoutes` (헤더 전송 전에만 가능) |
| 그 밖 | `500` | `api/server.ts` `fail()` — 분류되지 않은 것만 |

**조용히 실패하는 경로는 없다.** 오류를 상태코드로 옮기는 지점이 `api/server.ts` `fail()` **한 곳**이다 `[코드 server.ts:70~84]`.

## 10. 아직 안 되는 것 · 하지 않는 것

### 10-1. IDIS — 코드는 완비, **실기 검증은 0**

실기가 확보되면 가장 먼저 확인할 것 `[devices/idis/README.md 「실기 미검증 목록」]`:

1. **틸트 원점과 부호** — 아래를 보라 했을 때 실제로 아래를 보는가 (지금 `9000 − x` 는 **DC-S6261XT 한 대의 실측**이다)
2. **줌 상한** — `absZoom` 최댓값은 **모델마다 다르다**(현재 1200 고정)
3. 분류표의 `[미확인]` 행 — 특히 `ptzMoveToPoint&mode=1` 이 정말 301/304 를 주는가
4. `videoSnapshot` 의 Content-Type — §25 는 `image/webp` 라 적혀 있다
5. `modelInformation` 이 정말 **POST** 로 동작하는가 — 목(mock)은 GET/POST 를 가리지 않아 **절대 드러나지 않는다**
6. RTSP `trackID=N` 의 실제 코덱 — 번호를 믿지 말고 `ffprobe` 로 확인

> ⚠ **같은 벤더라도 개체마다 다르다.** `DC-S6286HRXLT` 에는 **`ptzAbsolute` 가 아예 없다** — `supportPTZ=on` 이라고 답하는데도 그렇다 `[실측 2026-07-31]`. 그 기기를 등록하면 `GET /api/ptz` 가 **501** 로 떨어진다. **경계는 벤더가 아니라 개체(모델·펌웨어)다.**

### 10-2. 배선되지 않은 것

| 항목 | 현재 | 왜 |
|---|---|---|
| IDIS **장비 프리셋 HTTP 라우트** | **501** — 드라이버에는 4개 메서드가 다 있다 | 장비가 **이름을 주면** "장비 이름과 로컬 이름 중 어느 쪽이 정본인가"라는 새 질문이 생긴다. 타입만 넓히면 두 이름이 조용히 갈린다 — 드라이버 추가가 아니라 레지스트리 재설계다 |
| IDIS **능력 프로브 라우트** | **없음** — `probeCapabilities()` 호출부 0건 | 요청이 없었다 |
| IDIS `centerPoint` | **프로브 의존** — 미지원 기기는 501 | 광학을 모르는 채 소프트웨어 센터링을 하면 조준이 조용히 빗나간다 |
| `centerBox`(박스 줌) | 실측 `intrinsics` 표가 있는 기기만 | 내장 표는 cam-001(Hucoms) 한 대의 곡선이라 다른 렌즈에 쓰면 화각이 조용히 그 값으로 보고된다 |
| 카메라 **점유 lease** | 코어 경로에만 있다 | `/api/ptz*` 는 여러 탭이 동시에 움직이면 서로 덮어쓴다 |
| **인증** | 없음 | `0.0.0.0:13030` 바인드 — 사내망의 누구나 실카메라를 움직일 수 있다 |

### 10-3. 하지 않는 것 (설계 판단)

- 줌 raw → 배율·화각 환산. 기기별 실측 화각표가 필요하고 그건 캘리브레이션의 산출물이다.
- IDIS 의 `intrinsics` 폴백. 줌 눈금의 뜻이 달라 화각이 약 5배 틀린다 `[실측 사고]`.
- IDIS RTSP URL 조립. `trackID=N` 의 N 을 믿을 근거가 없다.
- 벤더 프로토콜을 화면에서 직접 호출. 드라이버 계층의 몫이다.

## 12. 한눈에 보는 규칙 8가지

1. **제어와 영상은 별개 평면이다.** 실카메라는 제어 `:80`, 영상 `:554` 이고 **같은 카메라인지 사람이 확인해야 한다.**
2. **`kind` 는 프로토콜이지 실물/시뮬 구분이 아니다.** `simulator-1` 이 `kind=hucoms` 인 것이 그 증거다.
3. **휴컴스와 IDIS 는 틸트의 부호·원점이 반대이고 줌 눈금의 뜻이 다르다.** 변환은 `idisCoords.ts` 한 곳에만 있다.
4. **HTTP 200 은 성공이 아니다.** 휴컴스는 본문 `Error:` 로, IDIS 는 `returnCode=` 로 시작하는지로 판정한다.
5. **카메라는 "이동 완료"를 알려주지 않는다.** 명령 직후 읽은 값은 중간값이다 — 반드시 정착을 기다린다.
6. **보내기 전에 자르고, 잘린 축은 알린다.** 기기는 범위 밖 요청에도 성공이라 답하고 조용히 다른 데로 간다(IDIS 는 **오토플립**).
7. **못 닿은 것과 못 하는 것을 구분한다.** 전송·인증 실패는 능력을 낮추지 않고 던진다.
8. **카메라 정본은 DB `camera_info` 다.** 쓰기한 라우트는 반드시 `configStore.reloadCameras()` 를 부른다.
