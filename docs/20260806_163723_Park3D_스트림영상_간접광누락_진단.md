# Park3D 시뮬레이터 — `/stream` 영상이 `cam.captureJPG` 보다 어둡다

- 날짜: 2026-08-06
- 대상: 언리얼 Park3D 시뮬레이터 `192.168.0.125`
- 신고: "스트리밍으로 받은 화면이 언리얼 원본과 색·밝기가 전혀 다르다"
- 결론: **SettingManager 결함 아님.** 시뮬레이터의 두 출력 경로(`/stream` ↔ `cam.captureJPG`)가
  **서로 다른 렌더 결과**를 낸다. `/stream` 쪽에서 **간접광(스카이라이트/GI) 기여가 빠진** 모습이다.
- 수신처: Park3D(언리얼) 개발 담당 — 이 문서는 그쪽에 넘기기 위한 진단서다.

---

## 1. 한 장으로 보는 문제

같은 카메라(camId 2), **1초 안에** 두 경로로 뽑은 프레임이다. 프레이밍이 완전히 같다 —
카메라도 시각도 장면도 같고, **다른 것은 렌더 경로뿐이다.**

| 경로 | 이미지 | 상태 |
|---|---|---|
| `GET http://192.168.0.125:13602/stream` (MJPEG) | [stream_13602.jpg](assets/20260806_park3d_stream_lighting/stream_13602.jpg) | ❌ 어둡고 흰 차가 청동색 |
| `POST http://192.168.0.125:13510/rpc` `cam.captureJPG {camId:2}` | [captureJPG_13510.jpg](assets/20260806_park3d_stream_lighting/captureJPG_13510.jpg) | ✅ 언리얼 뷰포트 원본과 일치 |

**`cam.captureJPG` 는 이미 정답을 낸다.** 즉 시뮬레이터 안에 올바른 프레임을 만드는 경로가 이미 있고,
`/stream` 만 다른 경로를 탄다.

## 2. 중계 구간은 무죄다

SettingManager 의 MJPEG 중계는 **픽셀을 건드리지 않는다.**
`SettingMain/src/media/httpMjpeg.ts` 는 JPEG 의 SOI(`FFD8`)/EOI(`FFD9`) 로 바이트를 끊어
**원본 그대로** 흘려보낸다 — 디코드도, 재인코딩도, 색공간 변환도 없다.
(위 `stream_13602.jpg` 역시 SettingManager 를 거치지 않고 시뮬 포트에 직접 TCP 로 붙어 받은 것이다.)

두 JPEG 의 컨테이너 속성도 동일해서, 컨테이너 레벨 오해(풀레인지/리미티드레인지 등)도 아니다.

```
stream_13602.jpg    1280x720  yuvj420p  color_range=pc  color_space=bt470bg
captureJPG_13510.jpg 1280x720 yuvj420p  color_range=pc  color_space=bt470bg
```

## 3. 측정 — 무엇이 어떻게 다른가

두 이미지의 **같은 좌표** 패치 평균 RGB다.

| 패치 | `/stream` | `cam.captureJPG` | 차이 |
|---|---|---|---|
| 하늘 (밝은 곳) | 180 179 187 | 184 182 189 | **거의 없음** |
| 흰 차 지붕 | 194 189 184 | 202 200 198 | 거의 없음 |
| 흰 차 보닛 | 184 177 169 | 203 200 200 | 작음 |
| 아스팔트 (원경) | **47 36 29** | **86 80 86** | 절반 + 갈색 |
| 아스팔트 (근경) | **41 28 16** | **70 60 57** | 절반 + 갈색 |
| 주차선 (초록) | **25 17 10** | **44 43 48** | 절반 + 갈색 |

읽는 법이 핵심이다.

### 3-1. 노출(exposure) 차이가 아니다

노출이 낮았다면 **하늘까지 같은 비율로** 어두워져야 한다. 하늘은 180 ↔ 184 로 사실상 일치한다.
어두워진 것은 **중간톤과 그림자뿐**이다.

### 3-2. 선형/sRGB 감마 혼동도 아니다

"선형 버퍼를 sRGB 인 척 8비트로 구웠다"면 γ=2.2 다. 실제로 γ=2.2 를 되먹여 보면 **오버슛**한다
(평균 밝기 113 vs 정답 94). 밝기만 놓고 맞는 값은 **γ≈1.45** 였다.

### 3-3. 그런데 감마를 맞춰도 **색이 안 맞는다**

[stream_gamma1.45.jpg](assets/20260806_park3d_stream_lighting/stream_gamma1.45.jpg) — `/stream` 에 γ=1.45 를 먹인 것:

| 패치 | `/stream` ^(1/1.45) | `cam.captureJPG` |
|---|---|---|
| 아스팔트 (근경) | 69 56 **44** | 70 60 **57** |
| 주차선 (초록) | 41 34 **28** | 44 43 **48** |
| 하늘 | 201 200 208 | 184 182 189 (이번엔 오버슛) |

밝기는 얼추 맞지만 **그림자에서 파랑(B)이 계속 모자라** 갈색으로 뜬다. 반대로 하늘은 떠 버린다.
**단일 톤커브로는 설명도 보정도 되지 않는다.**

## 4. 해석 — 간접광(스카이라이트/GI) 누락

관측을 한 문장으로 묶으면 이렇다:

> **직사광(해)을 받는 면은 일치하고, 그늘·확산면만 어두워지면서 동시에 따뜻해진다.**

이건 **파란 하늘에서 오는 채움광(간접광/앰비언트)이 빠졌을 때** 나오는 모습이다.
햇빛 받는 면은 방향광이 지배하니 그대로고, 그늘은 원래 하늘빛으로 채워지는데 그게 사라지니
**어두워지는 동시에 남은 햇빛의 따뜻한 색만 남아 갈색이 된다.** 흰 차가 청동색으로 보이는 이유도 이것이다.

언리얼에서 이 증상의 전형적 원인은 `/stream` 이 뷰포트 최종 합성이 아니라
**`SceneCaptureComponent2D` 렌더 타깃**으로 뽑히면서 Lumen GI · SkyLight · 리플렉션 기여를
못 받는 경우다.

> **이 문단은 추정이다.** 밖에서 관측한 것으로는 "간접광 성분이 빠졌다"까지가 측정으로 뒷받침되는
> 사실이고, 그 원인이 SceneCapture 인지 다른 것인지는 **시뮬 코드를 봐야 확정된다.**

## 5. 요청 사항 (Park3D 담당자에게)

**가장 확실한 요청 한 줄:**

> `/stream` 도 `cam.captureJPG` 와 **같은 경로**로 프레임을 뽑아 주십시오.
> 그 경로는 이미 정답을 내고 있음이 위에서 증명됐습니다.

구조상 그게 어렵고 `SceneCapture` 를 유지해야 한다면 점검할 곳:

| 점검 항목 | 확인 내용 |
|---|---|
| `Capture Source` | `Final Color (LDR) in sRGB` 인가 (SceneColor HDR/Linear 아님) |
| Show Flags | `Global Illumination` · `Reflections` · `Ambient Occlusion` 이 켜져 있는가 |
| Lumen | SceneCapture 에서 Lumen GI/리플렉션이 활성인가 (기본값은 제한적이다) |
| SkyLight | `Real Time Capture` / Movable 여부 — 캡처 시점에 스카이라이트가 반영되는가 |
| PostProcess | 캡처 컴포넌트의 PostProcessSettings 가 뷰포트와 같은 값인가 |
| 렌더 타깃 포맷 | 8비트 타깃이면 sRGB 플래그가 켜져 있는가 |

## 6. 재현 방법

ffmpeg 와 Node 만 있으면 된다. 시뮬레이터를 움직이지 않는 **읽기 전용** 절차다.

```bash
# ① 스트림에서 첫 JPEG 프레임 1장 (13600 + camId 포트)
#    (multipart 헤더를 파싱하지 않고 SOI/EOI 로 끊는다)
# ② 같은 카메라를 RPC 로 캡처
curl -s -X POST http://192.168.0.125:13510/rpc \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"cam.captureJPG","params":{"camId":2}}' \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>require('fs').writeFileSync('capture.jpg',Buffer.from(JSON.parse(s).result.img_bytes,'base64')))"

# ③ 같은 좌표 패치의 평균 RGB 비교 (crop=w:h:x:y)
ffmpeg -v error -i stream.jpg  -vf "crop=80:60:600:600,scale=1:1" -f rawvideo -pix_fmt rgb24 - | od -An -tu1
ffmpeg -v error -i capture.jpg -vf "crop=80:60:600:600,scale=1:1" -f rawvideo -pix_fmt rgb24 - | od -An -tu1
```

①의 프레임 추출 스크립트는 이 저장소에 남기지 않았다 — 위 ②③ 만으로 차이가 재현된다.

## 7. SettingManager 쪽 판단 — 보정하지 않는다

우리 쪽에서 감마·색 보정을 넣어 덮을 수는 있으나 **하지 않기로 한다.**

1. 지금 중계는 **바이트 패스스루**다. 보정을 넣는 순간 프레임마다 디코드·재인코딩 비용이 붙고,
   MJPEG 를 ffmpeg 없이 처리하던 이점(지연 없음·중복 프레임 없음)이 사라진다.
2. **색이 틀어진 영상으로 VPD/LPD/LPR 검출을 돌리면 그쪽 정확도가 흔들린다.** 화면만 보기 좋게
   만들고 검출 입력은 그대로 두는 이중 경로는 더 나쁜 함정이다.
3. §3-3 에서 보듯 **단일 보정으로는 색이 맞지도 않는다.**
4. 근본 원인이 시뮬레이터에 있고, 그쪽에 이미 정답 경로가 있다.

## 8. 사용자 확인 방법

카메라 제어 화면에서:

- **「스냅샷 1장」 → 밝게 나온다** (`/api/snapshot` 이 `cam.captureJPG` 를 탄다 —
  `SettingMain/src/api/routes/mediaRoutes.ts:12`)
- **「시작」(스트림) → 어둡게 나온다**

이 두 가지가 동시에 관측되면 이 진단이 확정된다.

## 9. 영향도

| 대상 | 영향 |
|---|---|
| SettingManager 코드 | **없음.** 이번 진단으로 고친 코드는 한 줄도 없다 (이 문서 + 증거 이미지 3장뿐) |
| 화면 영상 품질 | 시뮬 카메라에 한해 어둡게 보인다. 실카메라(hucoms)는 무관 |
| 검출기(VPD/LPD/LPR) | **주의.** 스트림 프레임을 입력으로 쓰는 경로가 있다면 지금 어두운 프레임을 먹고 있다 — 시뮬 수정 전까지 시뮬 기반 검출 정확도를 신뢰하면 안 된다 |
| `cam.captureJPG` 기반 기능(스냅샷·센터링 등) | 없음. 정상 프레임을 쓴다 |

## 10. 남은 위험

- **camId 2 한 대만 측정했다.** 다른 카메라도 같은 경로를 쓸 것으로 보이지만 전수 확인은 아니다.
- 시뮬 장면에 움직이는 요소가 있어 두 프레임이 완전히 같은 시각은 아니다. 다만 밝기·색 차이가
  프레임 간 변동보다 훨씬 커서 판정에는 영향이 없다(하이라이트가 몇 LSB 안에서 일치하는 것이 그 증거).
