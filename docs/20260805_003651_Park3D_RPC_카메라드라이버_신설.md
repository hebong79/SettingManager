## 1. 개요 — 무엇을, 왜

웹 옵션 화면에서 `simulator-2` 「연결 테스트」를 누르면 다음이 떴다.

```
❌ 연결 실패 · 57ms · 카메라 HTTP 404
```

진단 결과, `192.168.0.125:13510` 은 **Hucoms CGI 카메라가 아니라 언리얼 Park3D JSON-RPC 서버**였다.
`config/config.json` 의 `simulator-2` 가 `kind:"hucoms"` 로 잘못 등록돼 있어 `HucomsClient` 가
`GET /cgi-bin/control/ptzf_status.cgi` 를 보냈고, UE 내장 HTTP 서버가
`errors.com.epicgames.httpserver.route_handler_not_found` 로 404 를 돌려준 것이다.

이 작업은 **네 번째 카메라 종류 `park3d-rpc` 를 신설**해 그 서버를 정식 프로토콜(JSON-RPC 2.0 `POST /rpc`)로 다룬다.

### 1-1. 다음에 같은 증상을 보는 사람을 위한 진단 논리 (이 문서의 핵심)

> **404 를 57ms 만에 받았다는 것은 "연결이 안 된다"가 아니라 "프로토콜이 틀렸다"는 뜻이다.**

- 호스트가 틀렸거나 방화벽에 막혔다면 응답이 오지 않고 **타임아웃(수 초)** 이 난다. 57ms 는 서버가 즉답했다는 뜻이다.
- 포트가 닫혀 있으면 `ECONNREFUSED` 지 HTTP 상태코드가 아니다. **상태코드가 왔다는 것 자체가 HTTP 서버가 살아 있다는 증거**다.
- 401/403 이면 인증 문제, 5xx 면 서버 내부 문제다. **404 는 "그 경로가 이 서버에 없다"** — 즉 주소는 맞고 **말을 거는 방식이 틀렸다**.

정리하면 이렇게 읽는다.

| 증상 | 실제 원인 계층 |
|---|---|
| 타임아웃(수 초) | 호스트·포트·방화벽 |
| `ECONNREFUSED` | 포트 닫힘 / 서비스 미기동 |
| **빠른 404** | **호스트·포트·방화벽 정상. 경로 = 프로토콜이 틀림** |
| 401 / 403 | 인증 |
| 5xx | 서버 내부 |

이번 건은 마지막에서 세 번째였고, 응답 본문의 `errors.com.epicgames.*` 가 "언리얼 HTTP 서버"라는 결정적 단서였다.
**응답 본문을 오류 메시지에 실어 주지 않으면 이 단서가 사라진다** — 그래서 새 드라이버는 서버 원문 200자를 오류에 싣는다(§3-3).

## 3. 신규 클래스 `Park3DRpcClient`

`SettingMain/src/devices/park3d/park3dRpcClient.ts` — `CameraDriver` 구현체.

### 3-1. 공개 표면과 RPC 매핑

```ts
export interface Park3DRpcClientOptions {
  cameraId: string;      // 이 저장소의 카메라 id (오류 문구용)
  baseUrl: string;       // controlUrl. 경로 접미사 금지 — `/rpc` 는 드라이버가 붙인다
  camId?: number;        // Park3D 카메라 번호. 1-based
  timeoutMs: number;
  fetchImpl?: typeof fetch;
}
```

| 메서드 | 호출하는 RPC | 비고 |
|---|---|---|
| `getPtz(): Promise<PtzRaw>` | `cam.getPTZ {camId}` | 응답 `{pan,tilt,zoom}`(도·배율 실수) → `Math.round(v*100)` 으로 raw 환산 |
| `goPtz(target, _speed?)` | `cam.setPTZ {camId, pan, tilt, zoom}` | 입력은 raw. `clampPtz` → zoom 자체 클램프 → `/100` 해서 도·배율로 전송 |
| `getSnapshot(): Promise<Buffer>` | `cam.captureJPG {camId}` | `img_bytes`(순수 base64) 디코드 후 **JPEG SOI(`FF D8`) 검증** |
| `listSlots(): Promise<Slot[]>` | (없음) | 항상 `[]` — Park3D 에 주차면 개념이 없다. 오류가 아니다 |
| `centerPoint` | — | **구현하지 않는다.** 속성 자체가 없다(§5-2) |

`readonly kind = 'park3d-rpc'`. 생성자는 `baseUrl` 이 비면 400 으로 던지고, 후행 슬래시를 제거한다.

**`speed` 인자는 의도적으로 무시한다.** Park3D `cam.setPTZ` 계약에 속도 파라미터가 없다.
없는 파라미터를 지어 보내면 서버가 조용히 버려서 "속도를 줬는데 왜 안 먹지"가 된다 — 무시하는 편이 정직하다.

### 3-2. 전송 형태

```
POST {baseUrl}/rpc
headers: { "content-type": "application/json" }   ← 이것 하나뿐. 인증 헤더 없음
body:    { "jsonrpc": "2.0", "id": 1, "method": "...", "params": {...} }
timeout: AbortSignal.timeout(timeoutMs)
```

### 3-3. 오류 분기 순서 — 왜 이 순서여야 하는가

`callRpc()`(`park3dRpcClient.ts:108-145`)는 본문을 `text()` 로 **1회만** 읽은 뒤 다음 순서로 판정한다.

```
① JSON 파싱 실패     → "응답을 해석할 수 없습니다: HTTP {status} … {원문 200자}"
② body.error 존재    → "Park3D RPC 오류 [{code}]: {message}"      ← 상태코드보다 먼저
③ !response.ok       → "Park3D RPC HTTP {status} … {원문 200자}"
④ 그 외              → body.result 반환
```

**②가 ③보다 먼저인 이유**: **이 서버는 오류도 HTTP 200 으로 보낸다.** 실측 확인된 사례다.

| 호출 | 실제 응답 |
|---|---|
| `cam.getPTZ {}` (camId 누락) | **HTTP 200** + `{"error":{"code":-32000,"message":"필수 파라미터 누락: camId"}}` |
| `cam.getPTZ {camId:99}` | **HTTP 200** + `{"error":{"code":-32000,"message":"카메라 없음: camId=99"}}` |

`res.ok` 를 먼저 보면 이 두 경우가 **정상 통과**하고 `body.result` 는 `undefined` 가 된다.
그러면 `getPtz()` 가 "PTZ 값 pan 을 주지 않았습니다"처럼 **엉뚱한 지점에서** 터지고, 진짜 사유(`-32000 필수 파라미터 누락`)는 사라진다.
반대로 ③을 빼면 이번 사건의 404(`route_handler_not_found`)가 `result: undefined` 로 조용히 통과해 먼 곳에서 TypeError 가 된다.
**둘 다 필요하고, 순서까지 필요하다.**

본문을 `text()` 로 읽는 것도 같은 이유다 — `json()` 은 스트림을 소비해 실패했을 때 원문을 다시 읽을 수 없고,
그러면 오류 메시지에 서버가 실제로 준 내용을 실을 수 없어 §1-1 의 진단이 불가능해진다.

### 3-4. 조용한 폴백을 만들지 않는다

`requireNumber()`(`:157`)는 `pan/tilt/zoom` 중 하나라도 유한수가 아니면 던진다. 0 으로 때우지 않는다.
0 폴백은 **카메라를 원점으로 보내는** 동작이며, 스키마 변화를 침묵시킨다.
`getSnapshot()` 의 SOI 검증도 같은 성격이다 — base64 디코드는 쓰레기 입력도 조용히 통과시킨다.

## 4. 단위 환산 — ⚠ 같은 숫자칸이 기기 종류에 따라 다른 뜻이다

> **가장 오해하기 쉬운 지점이다. 이 절만은 반드시 읽어야 한다.**

| 축 | Hucoms (`kind:"hucoms"`) | Park3D (`kind:"park3d-rpc"`) | 화면 표시의 정확성 |
|---|---|---|---|
| pan | 0~35999, **0.01°** (centi-deg) | 도 × 100 = **0.01°** (centi-deg) | ✅ 도 표시가 그대로 맞다 |
| tilt | -2000~9000, **0.01°** | 도 × 100 = **0.01°** | ✅ 도 표시가 그대로 맞다 |
| zoom | 0~65535, **불투명 raw**(물리적 의미 없음, `src/domain/ptz.ts:7`) | **배율 × 100** (100 = 1.0배, 3600 = 36배) | ⚠ **뜻이 다르다** |

pan/tilt 는 두 종류가 같은 단위라 `toView()` 의 도(°) 표시가 park3d-rpc 에서도 정확하다.

**zoom 은 다르다.** 제어 화면의 같은 `Z` 칸에 뜨는 `158` 이

- Hucoms 카메라에서는 → **의미 없는 눈금값 158**
- Park3D 카메라에서는 → **1.58배**

를 뜻한다. 화면은 이 차이를 표시하지 않는다(`web/control.js` 는 raw 를 그대로 보여준다 — D1 에 따라 손대지 않았다).

부수 효과 하나: `web/control.js:225-229` 의 `stepDelta` 는 step 입력 1을 raw 100 으로 환산한다.
Hucoms 에서는 65535분의 100 이라 미세 조정이지만, **Park3D 에서는 배율 1.0 만큼의 점프**(1배→2배→3배)다.
같은 버튼이 이 종류에서는 매우 거친 조작이 된다. (범위 밖 — 이번에 고치지 않았다.)

### 4-1. 왕복 양자화 (검증자 실측)

```
서버 실값 20.100000381469727°
 → getPtz()    round(2010.0000038…) = 2010 (raw)
 → goPtz(2010) 2010/100 = 20.1        ← 서버로 나가는 값
```

원래 값과 **다르다**. 다만 오차는 pan/tilt 3.8e-7 도, zoom 배율 0.00009 로 물리적으로 무의미하고,
**한 번 양자화된 뒤에는 고정점이라 반복해도 더 밀리지 않는다**(드리프트 없음 — 테스트로 고정됨).

> 화면에 보이는 raw 는 장비 실값이 아니라 **0.01 단위로 반올림된 값**이다.

## 5. 인증을 쓰지 않는다 (결정 D2')

### 5-1. 근거

사용자 지시: *"토큰 없이 동작할 수 있도록 만들어줘. (언리얼 시뮬레이터 서버는 토큰 없이 사용함)"*

그리고 **토큰 헤더 없이** 라이브 서버에 직접 호출한 실측 3건:

| 호출 | 결과 |
|---|---|
| `POST /rpc {"method":"cam.getPTZ","params":{"camId":1}}` | **200** + `{"result":{"pan":41.5,"tilt":20.100000381469727,"zoom":1.5799099206924438}}` |
| `GET /rpc/catalog` | **200** (79 메서드) |
| `GET /stream` | **200** `multipart/x-mixed-replace; boundary=park3dframe` |

이 서버는 무인증으로 열려 있다. 지금 서버가 요구하지 않는 인증을 미리 배선하는 것은 추측성 코드다(CLAUDE.md 2항).
그래서 `token` 설정 필드·`PARK3D_RPC_TOKEN` 환경변수 폴백·`X-Park3D-Token` 헤더·`hasToken` 공개 필드·마스킹 로직을 **하나도 만들지 않았다.**
`config.json` 에 옛 `token` 값이 남아 있어도 정규화에서 조용히 버려진다.

**서버가 나중에 인증을 켜면?** `POST /rpc` 가 401/403 을 돌려주고, §3-3 의 ③ 분기가
`Park3D RPC HTTP 401 … {서버 본문 200자}` 를 실은 `CameraDriverError` 로 **즉시** 드러낸다. 조용히 실패하지 않는다.
(HTTP 401 → 오류 메시지에 `401` 이 보인다는 것을 테스트로 고정해 두었다.)

### 5-2. ⚠ 형제 프로젝트 `SettingAgent` 와 다르다 — 오해 주의

**같은 서버를 쓰는데 두 프로젝트의 인증 정책이 다르다.**

| | 이 저장소 (SettingManager) | 형제 `AgentVLA/ParkAgent/SettingAgent` |
|---|---|---|
| 대상 서버 | `http://192.168.0.125:13510` | `http://192.168.0.125:13510` (**동일**, `config/tools.config.json:123`) |
| 인증 헤더 | **없음** | `X-Park3D-Token` (`src/viewer/sourceRegistry.ts:29`) |
| 토큰 출처 | — | `rpcTokenEnv: "PARK3D_RPC_TOKEN"` (`config/tools.config.json:126`), `resolveRpcToken()`(`src/config/toolsConfig.ts:296-301`) |

형제 쪽 주석은 *"토큰이 서버에 설정돼 있으면 루프백조차 검사하므로 미첨부 시 모든 호출이 401"* 이라고 적고 있다.
즉 **그쪽은 토큰이 켜진 서버도 다룰 수 있게 만들어 둔 것**이고, 지금 이 서버에는 토큰이 설정돼 있지 않아 양쪽 다 동작한다.
`SettingAgent` 코드를 참고할 때 "여기에도 토큰 배선이 빠졌다"고 오해하지 말 것 — **의도적으로 뺀 것**이다.
서버 운영자가 토큰을 켜는 순간 이 저장소는 401 로 즉시 실패하고, 그때 필드를 추가하면 된다(그 시점에는 필요성이 실측으로 확정된다).

### 5-3. `camId` 는 필수다 (1-based)

`requireCamId()`(`:148-154`)는 `camId` 가 양의 정수가 아니면 **400** 으로 던지고 `fetch` 를 부르지 않는다.
없을 때 1번으로 때우지 않는 이유는 하나다 — **엉뚱한 카메라를 움직이는 사고는 화면에 아무 흔적도 남기지 않는다.**
서버 자신도 `-32000 필수 파라미터 누락: camId` 로 거절한다.

정규화도 같은 태도다. `positiveInt()`(`normalize.ts:29-32`)는 클램프하는 기존 `int()` 와 달리
**유효하지 않으면 값을 만들지 않는다.** `camId: 0`·`-1`·`'abc'` 는 필드 자체가 생기지 않아 드라이버의 400 으로 이어진다.

## 6. 외부 계약 (입출력)

### 6-1. Park3D 서버 (아웃바운드)

```
POST http://192.168.0.125:13510/rpc
{"jsonrpc":"2.0","id":1,"method":"cam.getPTZ","params":{"camId":1}}
→ 200 {"result":{"pan":41.5,"tilt":20.100000381469727,"zoom":1.5799099206924438}}

{"jsonrpc":"2.0","id":1,"method":"cam.setPTZ","params":{"camId":1,"pan":41.5,"tilt":20.1,"zoom":1.58}}
{"jsonrpc":"2.0","id":1,"method":"cam.captureJPG","params":{"camId":1}}
→ 200 {"result":{"img_bytes":"/9j/4AAQ…","width":1280,"height":720,"format":"jpg","camId":1}}
```

`img_bytes` 는 `data:` 접두 없는 **순수 base64**(실측 디코드 확인). 드라이버는 `img_bytes` 만 읽는다.
영상은 같은 포트의 `GET /stream`(`multipart/x-mixed-replace; boundary=park3dframe`)을 그대로 중계한다.

### 6-2. 설정 파일 스키마 (`config/config.json`)

```jsonc
{
  "id": "simulator-2",
  "label": "UE-시뮬2",
  "kind": "park3d-rpc",                              // 신규 종류
  "controlUrl": "http://192.168.0.125:13510",        // ⚠ 경로 접미사 금지
  "username": "", "password": "",                    // 이 종류는 인증을 쓰지 않는다
  "streamUrl": "http://192.168.0.125:13510/stream",  // 제어와 **같은 포트**
  "timeoutMs": 5000,
  "camId": 1                                         // 신규 필드. park3d-rpc 필수, 1-based
}
```

**`controlUrl` 에 `/rpc`·`/stream` 을 붙이면 안 된다.** 드라이버가 `/rpc` 를 붙이므로
`/stream` 이 붙어 있으면 `/stream/rpc` 로 조립돼 404 가 난다(형제 프로젝트에서 실제로 겪은 사고).

### 6-3. REST 표면 (인바운드)

**새 라우트를 만들지 않았다.** 기존 라우트가 새 종류를 그대로 다룬다.

- `GET /api/settings` 응답의 카메라 객체에 `camId` 가 **값이 있을 때만** 실린다.
  키를 조건부로 만든 덕에 다른 카메라의 공개 키 집합(`test/server.test.ts:154`)은 넓어지지 않았다.
- `PUT /api/settings` 왕복에서 `kind`·`camId` 가 유지된다(HTTP 레벨로 검증됨).
- 옵션 화면은 `kind` 입력칸을 **추가하지 않았다**(기존 테스트가 `fieldKind` 부재를 강제한다).
  `kind`·`camId` 는 `config.json` 직접 편집으로만 바꾼다.

## 7. ⚠ 미해결 결함 1건 (심각도: 중간) — **사용자 판단 대기 중**

### 증상

park3d-rpc 에서 **줌이 잘려도 API 응답의 `limited` 가 비어 있다.**

| 위치 | 내용 |
|---|---|
| `src/devices/park3d/park3dRpcClient.ts:77` | 드라이버가 zoom raw 를 `[100, 3600]` 으로 클램프한다 |
| `src/api/routes/ptzRoutes.ts:25` | `limitedAxes(requested)` — 공유 `ZOOM_RANGE = [0, 65535]` 로만 판정 |
| `src/api/routes/ptzRoutes.ts:43` | nudge 의 `limited` — `nudge()` 결과가 안 움직였는지로 판정, 역시 공유 범위 기준 |
| `src/domain/ptz.ts:29` | `ZOOM_RANGE = [0, 65535]` — **Hucoms 의 범위다** |

검증자가 실제로 실행해 확인한 출력:

```
limitedAxes({pan:0,tilt:0,zoom:50})   = []     ← 실제 전송 zoom = 1  (raw 100 으로 잘림)
limitedAxes({pan:0,tilt:0,zoom:9999}) = []     ← 실제 전송 zoom = 36 (raw 3600 으로 잘림)
nudge({zoom:3600},'zoom',+500).zoom   = 4100   ← ptzRoutes 의 limited 판정 = []
                                                 실제 전송 zoom = 36 (카메라는 움직이지 않는다)
```

### 왜 문제인가

`ptzRoutes.ts:29` 스스로 *"잘린 축은 숨기지 않는다 — 착지가 어긋났다는 유일한 신호다"* 라고 못 박고 있다.
**park3d-rpc 는 그 원칙이 깨지는 유일한 종류다.** 특히 nudge 경로에서 줌이 이미 최대(36배)일 때
버튼을 눌러도 카메라는 안 움직이고 `limited` 도 비어 있어 **화면에 아무 신호가 없다** —
이 저장소가 과거에 겪었다고 주석에 남긴 "버튼이 동작하지 않는다" 증상과 같은 모양이다.

### 이것은 구현 실수가 아니다

**설계 계약의 빈틈**이다. 결정 D1("단위 변환과 클램프는 드라이버 안에 가둔다")은 상위 계층을 지켜 주는 대신,
`limitedAxes` 가 **기기별 실제 범위를 알 수 없게** 만들었다. 두 원칙이 이 지점에서 서로 모순한다.
D1 이 없었다면 `ZOOM_RANGE` 를 park3d 기준으로 바꿔야 했고 그건 Hucoms 를 깨뜨린다 — 즉 **대가를 치른 선택**이다.

### 완화 요인 (그래서 '높음'이 아니다)

응답의 `ptz` 는 `waitForSettle` 로 **장비에서 되읽은 값**이다. 사용자가 숫자칸을 유심히 보면
목표와 다르다는 것을 알 수 있다. 조용한 오동작이지 데이터 손상은 아니다.

### 선택지 (고칠지 여부는 사용자 판단)

1. `CameraDriver` 에 선택 메서드 `zoomRange?(): [number, number]` 를 두고 `ptzRoutes` 가 있으면 그것으로 판정 — 정공법이나 인터페이스를 넓힌다.
2. `goPtz` 가 잘린 축을 반환하도록 시그니처 변경 — 파급이 크다.
3. **지금은 고치지 않고 알려진 한계로 문서화** — 범위를 지키는 선택(현재 상태가 이것이다).
