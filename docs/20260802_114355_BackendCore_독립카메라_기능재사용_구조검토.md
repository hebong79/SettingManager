# BackendCore 독립 카메라 기능 재사용 구조 검토

## 질문

BackendCore에 등록되지 않은 카메라(예: 154 / 리얼카메라2)를 SettingMain에서 독립적으로 사용하면서, BackendCore가 가진 픽셀 센터링·캘리브레이션·번호판 호밍 기능만 가져다 쓸 수 있는지 검토한다.

## 결론

### 지금 상태에서는 불가능

현재 운영 중인 BackendCore의 HTTP API는 요청마다 `cameraId`나 카메라 접속 정보를 받아 임의 카메라를 처리하는 구조가 아니다. BackendCore 프로세스가 시작할 때 또는 `POST /api/cctv/active`로 전환할 때 만든 **활성 카메라 컨텍스트 1개**만 제어한다.

실제 확인:

```text
GET http://192.168.0.220/barocalory/api/ptz
→ HTTP 200

GET http://192.168.0.220/barocalory/api/health
→ HTTP 200, ok: true

GET http://192.168.0.220/barocalory/api/cctv/capabilities
→ cameraId: sim-cam-03
```

따라서 SettingMain에서 `리얼카메라2`를 골라도, 현 BackendCore API를 호출하면 BackendCore 내부 active device인 `sim-cam-03`에만 센터링·캘리브레이션·호밍이 적용된다.

## 코드 근거

| 근거 | 의미 |
|---|---|
| `baro_calory/apps/backend-core/src/server.mjs:193-197` | `buildDeviceContext(dev)`가 한 기기용 `client`, preview, discovery manager, calibration manager, API를 함께 생성한다. |
| `server.mjs:319` | 서버는 `let ctx = await buildDeviceContext(device)`로 활성 컨텍스트를 하나만 보유한다. |
| `server.mjs:417-428` | `POST /api/cctv/active`는 기존 컨텍스트를 다른 장비 컨텍스트로 교체하는 방식이다. 동시 다중 카메라 작업이 아니다. |
| `control-api.mjs:285-306` | `POST /api/center`는 body의 좌표만 받아 이미 묶여 있는 `client.centerPoint()`를 호출한다. body에 cameraId/host/계정이 없다. |
| `server.mjs:276-295` | discovery, calibration, VLA tour는 모두 같은 `devClient`로 만든 manager에 결합된다. |
| `control-api.mjs:102-110` | 장기 작업(호밍/캘리브레이션)은 활성 client를 점유하고, 중간 수동 이동을 거절한다. |

즉, **센터링 알고리즘만** 독립 함수로 호출되는 것이 아니다. 다음이 한 카메라 컨텍스트에 결합되어 있다.

```text
CameraDriver/client
+ PTZ 정착 대기
+ device intrinsics / centering gain
+ camera별 discovery·spot 저장소
+ calibration manager
+ plate-homing manager
+ 장기 작업 lock
+ detector/VLA 설정
```

## 그래도 재사용 가능한 부분

BackendCore는 완전히 카메라에 하드코딩된 것은 아니다.

- `createControlApi({ client, ... })`는 client를 주입받는다.
- `createDiscoveryManager({ client, cameraId, ... })`도 client를 주입받는다.
- `createCalibrationManager({ client, device, ... })`도 client를 주입받는다.

따라서 **코드 레벨에서는** Hucoms client를 새로 만든 뒤 위 manager를 조립하여 재사용할 수 있다. 그러나 현재 이 조립은 `server.mjs` 안에 있고, SettingMain TypeScript 프로젝트가 import 가능한 공용 패키지 API로 분리되어 있지 않다.

## 가능한 방법

### 권장: 카메라별 BackendCore Worker/인스턴스

리얼카메라2 전용 BackendCore 인스턴스를 별도 포트 또는 별도 서비스로 실행한다.

```text
BackendCore A (/barocalory, 기존 포트)
  └─ 기존 active device: sim-cam-03 또는 기존 카메라

BackendCore 154 (별도 포트/컨테이너)
  └─ active device: cam-154(리얼카메라2)

SettingMain
  ├─ 리얼카메라2 직접 영상/즉시 PTZ
  └─ BackendCore 154 worker → center / calibration / plate-homing
```

장점:

- 기존 BackendCore의 카메라와 154 카메라가 서로 active device를 뺏지 않는다.
- 각 카메라별 장기 작업 lock, calibration 결과, discovery 파일이 자연스럽게 분리된다.
- 기존 BackendCore API와 기능을 거의 그대로 쓴다.
- 154 카메라의 자격증명은 SettingMain 브라우저가 아닌 154 worker 서버에만 보관할 수 있다.

필수 작업:

1. `baro_calory`에 154 카메라 전용 config를 작성한다.
2. 그 config를 사용하는 BackendCore 프로세스/컨테이너를 별도 포트로 기동한다.
3. Nginx에서 예: `/barocalory-154/`로 reverse proxy 하거나 SettingMain에 worker base URL을 등록한다.
4. SettingMain 주차면 탐색 화면에서 `BackendCore 작업 채널`을 카메라별 worker URL로 선택한다.
5. worker의 `GET /api/cctv/capabilities`가 기대한 실제 device ID를 돌려줄 때만 center/calibration/homing 버튼을 활성화한다.

### 장기 권장: BackendCore 멀티카메라 Gateway

하나의 BackendCore 프로세스 안에서 `ctx` 하나 대신 `Map<cameraId, DeviceContext>`를 유지한다.

```text
POST /api/cameras/:cameraId/center
POST /api/cameras/:cameraId/calibration/start
POST /api/cameras/:cameraId/discovery/plate-home/start
GET  /api/cameras/:cameraId/status
```

각 요청은 해당 카메라의 context와 lock만 사용한다. SettingMain은 선택한 `cameraId`를 명시적으로 전달한다.

필수 리팩터링:

- `server.mjs`의 단일 `let ctx`를 `contexts: Map<string, DeviceContext>`로 교체
- calibration/discovery/VLA lock을 카메라별로 분리
- 현재 `/api/*` 단일 활성장비 경로와 새 `/api/cameras/:id/*` 경로를 병행해 하위호환 유지
- 카메라별 config와 credentials를 BackendCore 서버에 저장; SettingMain 브라우저에 전송 금지
- cameraId 인증/인가와 audit log 추가

장점: 단일 서비스/단일 UI에서 여러 대를 동시에 운영할 수 있다.

단점: 영향 범위가 크고, 동시 장기 작업·카메라 lock·파일 저장 위치·권한을 철저히 테스트해야 한다.

### 단기 임시안: active device를 매번 교체

`POST /api/cctv/active`로 리얼카메라2를 active로 바꾼 뒤 기능을 호출할 수 있다.

하지만 이는 **독립 사용이 아니다**.

- 기존 active camera 작업을 끊거나 409로 막을 수 있다.
- 다른 운영자가 쓰던 BackendCore 제어 대상이 바뀐다.
- 호밍/캘리브레이션 중 전환은 명시적으로 거절되며, 운영 충돌 위험이 있다.

따라서 154 카메라를 독립적으로 운용하는 목적에는 권장하지 않는다.

### SettingMain에서 알고리즘을 복제

SettingMain이 Hucoms direct client 위에 calibration/homing을 새로 구현할 수도 있다.

이 방법은 가능하지만 권장하지 않는다.

- BackendCore의 `createCalibrationManager`, `createDiscoveryManager`, detector/VLA 연동, lock 로직을 중복 구현해야 한다.
- 두 프로젝트의 보정·호밍 결과가 달라지는 이중 구현 위험이 생긴다.
- 향후 BackendCore 기능 개선이 SettingMain에 자동 반영되지 않는다.

## 권고안

154 카메라가 기존 BackendCore 카메라들과 독립적으로 센터링·캘리브레이션·호밍을 실행해야 한다면, **카메라별 BackendCore Worker**부터 시작하는 것이 가장 안전하고 빠르다.

운영 카메라 수가 늘고 한 UI에서 동시 작업이 필요해지면, 다음 단계로 BackendCore 멀티카메라 Gateway를 구현한다.

## 아직 확인하지 않은 항목

- 154 카메라의 실제 BackendCore device ID, host/port, 계정은 확인하거나 문서에 기록하지 않았다.
- 운영 서버에 별도 BackendCore worker를 배포할 권한/포트/Nginx 경로는 확인하지 않았다.
- 실제 PTZ 이동, calibration, plate-homing POST는 실행하지 않았다.
