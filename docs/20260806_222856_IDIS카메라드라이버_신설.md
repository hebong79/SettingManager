### 1-1. 왜 지금 이것이 필요했나

`baro_calory` 현장에서 IDIS 카메라(DC-S6261XT, DC-S6286HRXLT)를 다뤄 본 실측 자산이 이미

어디에도 드러나지 않는다**(같은 증상의 앞선 사고는 `docs/20260805_003651_Park3D_RPC_카메라드라이버_신설.md` §1-1).

### 1-2. 왜 벤더링(복사)이 아니라 재작성인가

`src/vendor/baro-profile` 은 상류를 그대로 복사하고 sha256 으로 고정한다. IDIS 는 그
기준에 맞지 않았다 `[코드]`:

1. 상류가 `.mjs` 이고 이 저장소는 `strict` TypeScript 에 **`checkJs` 가 꺼져 있다** — 벤더링하면
   드라이버 전체가 타입 검사 밖에 놓인다. `CameraDriver` 를 구현해야 하는 코드가 타입 검사를
   못 받으면 요구 2번이 무력해진다.
2. 상류는 `capabilities.mjs`·`camera-driver.mjs`·`@baro/profile` 에 의존한다 — **외부 의존 0 이
   아니다.** 벤더링하면 그 사슬을 전부 끌고 와야 하고 요구 1번과 정반대다.
3. 계약이 다르다(`getPtzPosition/goPtzPosition({panpos,…})` vs `getPtz/goPtz({pan,…})`).

**대신 두 벌이 된다는 위험을 인정하고 명시했다.** `src/devices/idis/README.md` 「상류와의
관계」 절이 "같은 기기에 대한 독립 구현이다. 한쪽에서 실측이 갱신되면 다른 쪽도 확인할 것"
을 담는다. **사실의 정본은 코드가 아니라 문서**(README 「근거의 구분」 절 + 설계서)라는 규약도
같이 적었다.

### 2-1. `contract.ts` 한 겹의 의미

이 한 파일이 **"폴더째 복사"라는 요구를 검증 가능한 사실로 바꾼다** `[코드 contract.ts:1~21]`.

- 나머지 8개 파일에는 `../` 로 시작하는 import 가 **하나도 없다.** 옮길 때 고칠 파일이 정확히
  1개다. 여러 파일에 흩어져 있으면 하나를 빠뜨렸을 때 빌드가 아니라 **런타임
  `ERR_MODULE_NOT_FOUND`** 에서 터진다.
- 그 파일이 요구하는 것은 다섯인데 **넷은 타입이고 런타임 값 의존은 `CameraDriverError`
  하나뿐**이다. 옮긴 곳에는 `constructor(message, statusCode, {cause})` 를 갖는 오류 클래스
  하나만 있으면 된다.
- **이것을 사람이 지키는 규약으로 두지 않았다.** QA 의 `T-ISO` 케이스가 서브트리 파일을 읽어
  `../` import 가 `contract.ts` 에만 있음을 기계로 증명하고, **역방향**(그 파일은 반대로 갖고
  있는가)과 파일 수 하한까지 단언한다 `[QA §3-C T-ISO]`.

### 2-2. 왜 `PtzRaw` 는 타입만 빌려 오는가 — 클램프를 자체로 갖는 이유

`domain/ptz.js` 의 `clampPtz`·`wrapPan` 은 **계약 범위**(tilt −2000..9000, zoom 0..65535)로
자른다. IDIS 에 보내기 전 잘라야 하는 것은 **이 기기의 와이어 범위**다. 계약 상수로 자르면
`zoom=65535` 가 그대로 나가고 기기가 조용히 1200 으로 클램프한다 `[실측]`. 그래서 좌표 클램프는
`idisCoords.ts` 가 자체로 갖는다 — 런타임 결합 0 이라는 요구와도 같은 방향이다.

### 2-3. 계획보다 커진 이유

계획 예상 ~735줄 → 실제 소스 1155줄 + README 67줄. 늘어난 420줄의 대부분은
`idisConstants.ts` 의 **§75 Return Code 전표 전문**과 **§0~§79 액션 목차**다 — 계획이 명시적으로
요구한 것이고, "매뉴얼의 나머지 60여 절을 감싸지 않되 **이름은 싣는다**"는 판단의 실체다.
목록조차 없으면 다음 사람이 매뉴얼을 처음부터 다시 읽는다.

## 3. 인터페이스 → (휴컴스, IDIS) — 요구 2번의 구조

### 3-1. 인터페이스는 이미 있었고, 그것을 정본으로 썼다

`src/devices/cameraDriver.ts` 의 `CameraDriver` 가 그 자리다 `[코드]`. **새 인터페이스를 만들지
않았고, 있는 것을 넓히지도 않았다.**

```
CameraDriver ┬─ HucomsClient      (kind='hucoms')        Hucoms HTTP CGI
             ├─ BackendCoreClient (kind='backend-core')  UE 시뮬레이터 코어
             ├─ Park3DRpcClient   (kind='park3d-rpc')    언리얼 JSON-RPC
             └─ IdisCameraClient  (kind='idis')          ← 이번 신설
```

**넓히지 않은 이유** — 이 계약에는 `capabilities` 개념이 없고, **도입하지 않았다**:

1. 저장소에 이미 능력 어휘가 **둘** 있다 — `CoreCapabilities`(코어 제공자 8능력)와
   `DevicePresetCapability`(장비 프리셋). 세 번째를 만들면 "이 기기가 X 를 할 수 있는가"의 답이
   세 군데에 생기고, 갈리는 순간 어느 쪽이 맞는지 판단할 근거가 없다.
2. `CameraDriver` 의 설계 의도가 이미 다른 방식이다 — "못 하는 기능은 지어내지 않고 던진다"
   `[코드 cameraDriver.ts:36~38]`. 능력 표현이 **메서드의 존재 여부와 예외**이며
   `bridgeCoreProvider` 가 정확히 그렇게 읽는다(`typeof ctx.driver.centerPoint === 'function'`
   `[코드 bridgeCoreProvider.ts:79]`).
3. 계약 표면 확장은 드라이버 4개 전부 + 코어 제공자 2개 + 적합성 스위트에 파급된다. 요청은
   드라이버 추가지 계약 개편이 아니다(CLAUDE.md 2·3번).

그래서 **능력 프로브는 idis 서브트리 안에만 있다**(`IdisCameraClient.probeCapabilities()` —
`CameraDriver` 계약 밖의 공개 메서드). 서브트리를 옮겼을 때 그쪽 프로젝트가 그대로 쓸 수 있게
남는 것이 덤이다.

### 3-2. 휴컴스와 IDIS — 같은 명령으로 되는 것과 안 되는 것

**"같은 메서드로 부른다"와 "같은 뜻으로 동작한다"는 다르다.** 아래가 그 차이의 전부다 `[코드]`.

| 계약 메서드 | 휴컴스(`HucomsClient`) | IDIS(`IdisCameraClient`) | 같은가 |
|---|---|---|---|
| `getPtz()` | `ptzf_status.cgi&action=getptzfpos` → `panpos/tiltpos/zoompos` | `webSetup.cgi?action=ptzAbsolute&mode=1` → `absPan/absTilt/absZoom` | **✅ 같다** — 계약 `PtzRaw` 로 나온다. 단 IDIS 는 값이 변환을 거친다(§4) |
| `goPtz(target)` | `goptzfpos` (GET) | `action=ptzAbsolute&mode=0` (**POST 폼 본문**) | **✅ 같다** — 호출부는 구분할 필요가 없다 |
| `goPtz(target, speed)` 의 **speed** | `panspeed/tiltspeed/zoomspeed` 로 실제 전달(기본 50) | **받되 버린다.** `ptzAbsolute` 에 속도 파라미터가 **없다** `[매뉴얼 §56]` | **❌ 다르다** — 속도를 준 호출자가 "느리게 갈 것"으로 타이밍을 짜면 어긋난다 |
| `getSnapshot()` | `/cgi-bin/image/jpeg.cgi` | `action=videoSnapshot&mode=1&streamIndex=N` `[매뉴얼 §24]` | **✅ 같다** — 둘 다 **JPEG SOI(`FF D8`) 바이트로 판정**하고 헤더를 믿지 않는다 |
| `listSlots()` | `[]` (주차면 개념 없음) | `[]` (같음) | **✅ 같다** — 오류가 아니라 빈 배열 |
| `centerPoint(point)` | **항상 있다.** 펌웨어가 `ptz_centering&action=setcenter` 로 처리 | **있지만 기기에 물어본다.** 첫 호출에서 `ptzMoveToPoint&mode=1` 프로브 → 없으면 **501 거절** | **⚠ 다르다** — 같은 벤더·같은 CGI 인데 DC-S6286HRXLT 에는 `ptzAbsolute` 가 아예 없었다 `[실측 2026-07-31]`. **경계는 벤더가 아니라 개체(모델·펌웨어)** 다 |
| 인증 | 매 요청 **쿼리스트링 평문**(`id=&passwd=`), 세션 없음 | **Digest**(RFC2617). 401 챌린지를 읽어 방식을 고른다 | **❌ 다르다** — IDIS 는 Basic 에 401 이었다 `[실측 DC-S6261XT]` |
| 전송 스택 | `fetch` + `AbortSignal.timeout` | **`node:http`/`node:https`** + 명시적 `setTimeout` | **❌ 다르다** — 이유는 §7-2(요청별 TLS)와 §6-2(연결 중 마감) |
| 클램프 | `clampPtz` (계약 범위) | `idisCoords` (**기기 와이어 범위**) | **❌ 다르다** — §4 |
| `intrinsics`(줌→화각) | 기본 곡선 폴백 있음 | **지어내지 않는다** — 줌 눈금의 뜻이 달라 폴백을 들면 화각이 약 5배 틀린다 `[실측 사고]` | **❌ 다르다** |
| 프리셋(계약 밖) | `HucomsPresetClient` 별도. 장비가 **이름을 주지 않는다**(`listing/naming: 'unsupported'`) | 서브트리가 `listPresets`(**이름 포함**)·`gotoPreset`·`setPreset`·`removePreset` 을 **전부 구현** `[매뉴얼 §50]` | **⚠ 구현은 있으나 배선하지 않았다** — §3-3 |

### 3-3. 장비 프리셋 라우트를 IDIS 로 넓히지 않은 이유 (비범위)

`/api/cameras/:id/device-presets` 는 `camera.kind !== 'hucoms'` 이면 **501** 이다
`[코드 devicePresetRoutes.ts:23,34]`. 이 파일은 **한 줄도 건드리지 않았고**, 그래서 IDIS 는
자동으로 501 이다.

넓히지 않은 이유는 타입 문제가 아니다. `listing:'unsupported'`/`naming:'unsupported'` 두
리터럴은 **레지스트리의 설계 전제**다 — `devicePresetRegistryStore` 는 "장비가 이름을 안 주니
우리가 저장한다"로 만들어져 있다 `[코드 domain/devicePresetRegistry.ts]`. **이름을 주는 장비가
들어오면 "장비 이름과 로컬 이름 중 어느 쪽이 정본인가"라는 새 질문이 생긴다.** 타입만 넓히면
두 이름이 조용히 갈린다. 이는 드라이버 추가가 아니라 레지스트리 재설계다.

**기능 자체는 서브트리 안에 완전히 있으므로 다음 단계는 배선과 정본 결정뿐이다.**

## 4. 좌표 규약 — 이 작업에서 가장 위험한 부분

계약 좌표는 이 서비스의 `PtzRaw`(= Hucoms 논리 좌표)다. 변환·클램프는 **`idisCoords.ts` 한
곳**에만 있다 `[코드]`.

| 축 | 계약 | IDIS 와이어 | 와이어→계약 | 계약→와이어 |
|---|---|---|---|---|
| pan | `0..35999` 무부호 | `absPan −18000..18000` `[매뉴얼 §56]` | `((absPan % 36000) + 36000) % 36000` | 감아서 `>18000` 이면 `−36000` |
| tilt | `−2000..9000`, **+ 가 아래**, 0=수평 | `absTilt`, **+ 가 위**, 0=수직아래 `[실측]` | `9000 − absTilt` | `9000 − tilt` 뒤 **`[0, 9000]` 클램프** |
| zoom | `0..65535` 불투명 raw | `absZoom` = **배율×100** | 항등(반올림) | 항등 뒤 **`[100, 1200]` 클램프** `[실측]` |
| centerPoint | `{x,y}` 1920×1080 픽셀 | `pointPan`·`pointTilt` `0..100000` `[매뉴얼 §58]` | (쓰기 전용) | `round(x / 1920 × 100000)` |

### 4-1. 틸트 — 부호와 원점이 둘 다 반대다

**매뉴얼은 범위만 말하고 원점을 말하지 않는다.** 원점은 실측으로만 닫혔다
`[실측 DC-S6261XT 2026-07-29]`:

- `absTilt = 0` 에서 카메라 **자기 다리**가 보인다(수직 아래).
- `absTilt = 9000` 에서 **사무실 수평 전경**이 나온다.
- 계약(Hucoms)은 **+ 가 아래**이고 0 이 수평이다 — **부호도 원점도 반대**다.

다행히 두 범위가 정확히 겹쳐 **`9000 − x` 한 식(자기역함수)** 으로 양방향이 닫힌다.

**독립 교차검증** `[실측]` — `absZoom=100` 에서 5°씩 움직여 상호상관으로 화면 이동을 재면
tilt 37.6 px/°, pan 29.6 px/° 다. 그대로 보면 두 축 화각이 어긋나지만(28.7° vs 64.9°),
위 규약대로 카메라가 수평에서 40° 내려가 있다면 팬의 화면 변위는 `cos40° = 0.766` 배라
38.6 px/° 가 되어 틸트와 **3% 안에서 일치**한다. **원점이 수평이었다면 이 일치가 나오지 않는다.**

### 4-2. 보내기 전에 자르는 이유 — 기기는 성공이라 답하면서 다른 데로 간다

`[실측]` 로 확인된 기기 동작:

| 보낸 값 | 기기의 답 | 실제 결과 |
|---|---|---|
| `absTilt = 12000` | `returnCode=0` | 9000 에서 클램프 |
| **`absTilt = −3000`** | **`returnCode=0`** | **오토플립 — 팬을 180° 돌려 `pan=18000, tilt=3000` 으로 "해결"한다** |
| `absZoom = 3000` | `returnCode=0` | 1200 (이 렌즈의 상한) |
| `absPan = −18000` | `returnCode=0` | 18000 (원이라 같은 방향) |

**오토플립이 특히 위험하다 — 성공 응답을 받고 정반대를 본다.** 계약이 허용하는 `tilt = −2000`
(수평 위 20°)이 그대로 나가면 `absTilt = 11000` 이 되어 이 갈래에 빠진다. 그래서 `tiltToWire`
가 **뒤집은 뒤 실측 도달 범위 `[0, 9000]` 으로 자른다.** 성공 응답을 받고 정반대를 보는 것보다
수평에서 멈추는 편이 예측 가능하다.

`idisConstants.WIRE_RANGE` 는 **선언 범위와 실측 도달 범위를 따로 담는다** — 클램프는 실측
쪽을 쓴다. 매뉴얼의 tilt 하한은 −9000 인데 실측 하한은 0 이고, 그 차이가 곧 오토플립이다.

### 4-3. 팬은 자르지 않고 **감는다**

±180° 는 원이라 −18000 과 +18000 이 같은 방향이다 `[실측]`. 자르면 반대쪽으로 도는 경로가
막힌다. `panToContract` 는 modulo 로 접고, `panToWire` 는 접은 뒤 `>18000` 이면 `−36000` 한다.
QA 가 **계약 전 구간 36000개**를 왕복시켜 항등을 확인했다 `[QA T-C3]`.

### 4-4. 줌 — 숫자는 통과하지만 뜻이 다르다

Hucoms `zoom` 은 불투명 raw `0..65535` 이고 IDIS `absZoom` 은 **배율×100** 이다. 숫자 범위가
계약 안에 들어가므로 **항등 통과는 계약 위반이 아니다.** 그러나 **"0 = 광각"이 아니라
"100 = 광각"** 이다.

이 차이를 무시하고 Hucoms 기본 화각 곡선을 폴백으로 들면 **화각이 약 5배 틀린다** `[실측 사고]`.
그래서 이 드라이버는 **`intrinsics` 를 절대 지어내지 않는다.**

**감수한 결과(비범위)**: `limitedAxes()` 는 계약 상수 `0..65535` 로 판정하므로
`/api/ptz/absolute` 가 `zoom:3000` 요청에 `limited: []` 를 답하면서 드라이버는 1200 으로 자른다
— **"잘린 축은 숨기지 않는다"는 약속이 이 기기에서 깨진다** `[코드 ptzRoutes.ts:30]`.
`nudge` 델타도 같은 문제다. 기기별 도달범위(`deviceRanges`) 도입은 도메인·라우트·화면에 걸친
별건이라 이번 범위 밖으로 두었다(설계 확인 필요 #4, 미결).

## 5. 미구현 액션 판정 — 경로가 둘이고, 9000 이 두 뜻이다

### 5-1. 두 경로를 한 값으로 합치는 자리가 `idisReply.ts` 하나다

같은 벤더의 기기가 **없는 액션에 두 가지로 답한다** `[실측]`:

| 경로 | 모습 | 실측 기기 |
|---|---|---|
| (가) 정직 | `returnCode=9000` (Unknown API) | DC-S6261XT |
| (나) **거짓 성공** | **HTTP 200 + 무관한 설정 덤프** | DC-S6286HRXLT |

**(나) 때문에 HTTP 상태도, 본문의 유무도 성공 판정이 될 수 없다.** 유일한 신뢰 신호는
**본문이 `returnCode=` 로 시작하는지**이며 `[코드 idisReply.ts:21~23]`, 그 판정이 코드 전체에
**딱 한 군데**만 있다. 선행 공백·개행은 허용한다.

`classifyReply()` 가 응답 하나를 다섯 갈래로 나눈다 `[코드 idisReply.ts:103~112]`:

| 분류 | 트리거 | 일반 호출 | **능력 프로브** |
|---|---|---|---|
| `answer` | `returnCode=0` | 파싱 결과 반환 | 있음 |
| `param` | 301 · 302 · 304 | 400 던짐 | **있음** ← 기기가 액션을 알아들었다는 증거 |
| `unknown-action` | `returnCode=` 아님 · 9000 · 310 · 308 | 501 던짐 | 없음 |
| `auth` | 900 · 901 · 903 · 306 · 307 | 던짐 | **던짐**(능력을 낮추지 않는다) |
| `error` | 그 밖 · `returnCode` 가 정수가 아님 | 502 던짐 | 없음(안전한 쪽) |

**`param` 을 '있음'으로 읽는 것이 참조구현과 다른 자리다.** §58·§59 는 **Write 전용**이라
지원 기기에서도 `mode=1` 프로브가 `returnCode=0` 이 **아닐 수 있다**. 참조구현은
`returnCode !== 0` 을 전부 "없음"으로 읽어 **지원 기기에서 거짓 음성**을 낸다. 다만
**어느 코드가 실제로 오는지는 `[미확인]`** 이라 나머지 갈래는 안전한 쪽('없음' → 501 거절)에 두었다.

### 5-2. ⚠ `mode=9000` 과 `returnCode=9000` 은 다른 네임스페이스다

**`MODE.SYSTEM_RESTART = 9000`**(§74 Mode Code)과 **`RETURN_CODE.UNKNOWN_API = 9000`**(§75
Return Code)은 숫자만 같고 뜻이 정반대다.

> **섞으면 "이 액션이 구현돼 있나"를 물어보려다 카메라를 재부팅시킨다.**

방어를 셋 두었다 `[코드 idisConstants.ts:11~30]`:

1. 이름을 갈라 두고 상수에 경고 주석을 박았다.
2. **`9000` 이라는 숫자 리터럴을 코드 어디에도 직접 적지 않는다.**
3. `MODE.SYSTEM_RESTART` 는 이 드라이버가 **보내지 않는다** — 혼동을 막기 위해 이름만 싣는다.

QA 가 여기에 못을 두 개 박았다 `[QA T-R2 · T-M6/M7]`: `returnCode=9000` 이
`MODE.SYSTEM_RESTART` 와 **안 섞임**을 별도로 단언하고, **어떤 요청에도 `mode=9000` 이 나가지
않음**을 확인한다.

### 5-3. 값 디코딩 — `+` 를 공백으로 접지 않는다

`parseQueryReply` 는 값을 `decodeURIComponent` 로 푼다 `[매뉴얼 §0]`. 풀지 않으면 프리셋 이름의
공백·한글이 `door%20A` 로 화면에 나간다. 실패하는 이스케이프(`%zz`)는 **원문을 남긴다** —
던져서 응답 전체를 버리는 것보다 낫다.

**`+` 는 접지 않는다.** 매뉴얼이 말하는 것은 form 인코딩이 아니라 URI 인코딩(공백은 `%20`)이고,
접으면 이름에 정말로 `+` 가 든 프리셋이 깨진다. 이 판단은 `[미확인]` 이며 실기에서 프리셋
이름에 `+` 를 넣어 저장·조회하면 닫힌다(§11-8).

## 6. 능력 프로브 — 전송 실패와 기능 부재를 구분한다

### 6-1. 왜 구분해야 하는가 (실기 사고 근거)

> **자체서명 인증서 하나 때문에 `snapshot:false`·`presets:false` 가 "실측 결과"로 저장돼
> 멀쩡한 카메라가 영구히 불구가 될 뻔한 사고가 실제로 있었다** `[실측]`.

케이블 하나 빠진 것이나 비밀번호 오타 하나가 "이 카메라는 아무것도 못 한다"로 기록되면
**고장난 카메라와 구분되지 않는다.** 그래서 `probeCapabilities()` 는 두 갈래를 능력으로 읽지
않고 **그대로 던진다** `[코드 idisCamera.ts:255~293]`:

- **전송 실패** → `IdisTransportError`(`transport: true` 표식, statusCode 502)
- **인증·권한 실패** → `IdisAuthError`

`IdisAuthError.statusCode` 는 **401 이 아니라 502** 다. 그 401 은 **우리와 카메라 사이**의
것이고, 그대로 브라우저에 내보내면 **사용자 자신의 세션이 끊긴 것처럼 보인다.**

### 6-2. 마감 타이머가 별도인 이유

`req.setTimeout` 은 **소켓 유휴 타임아웃**이라 TCP 연결 수립 중에는 걸리지 않는다. 도달 불가
주소에서 설정값과 무관하게 OS 기본(실측 5초)까지 붙잡히면서 **오류 메시지는 설정값이 지난 것처럼
거짓말했다** `[실측]`. 그래서 연결+응답 전체를 **명시적 `setTimeout` 하나**가 덮는다
`[코드 idisTransport.ts:105~109]`.

QA 가 도달 불가 주소(350ms)와 **응답을 끝내지 않는 서버** 두 갈래를 1200ms 안에서 확인했다
`[QA T-T5]`.

### 6-3. 프로브의 첫 줄은 "정말 이 벤더인가"

`modelInformation` `[매뉴얼 §4]` 을 먼저 부른다. **`type:"flexwatch"` 로 등록된 기기가 실은
IDIS 였고 모든 호출이 실패해 능력이 전부 false 로 나온 사고**가 있었다 `[실측 2026-07-31]`.
실패하면 능력을 좁히는 대신 "카메라 종류(kind) 설정을 확인하세요" 로 502 를 던진다.

⚠ **이 호출을 POST 로 보낸다** — 매뉴얼 §4 원문이 `Method: POST` 이기 때문이다. 그런데 다른
Read 액션은 GET 이다. **프로브의 첫 줄이라 이것이 틀리면 모든 프로브가 벤더 확인 실패로
떨어지는데, 목(mock)은 GET/POST 를 가리지 않아 절대 드러나지 않는다** `[QA §7-6]`. 실기 확인
항목이다(§11-6).

### 6-4. 상한에 낙관, 프로브가 좁힘

선언 상한은 6능력 전부 `true` 다. **`false` 를 미리 박지 않는다** — 참조구현은 실측기 한 대의
사실(`pixelCentering`/`boxZoom` 없음)을 **벤더 전체의 상한**으로 옮겨 적었고, 그러면
`ptzMoveToPoint` 를 가진 모델에서 **있는 기능을 스스로 버린다.** 상한에 비관을 두면 멀쩡히 되는
기기가 프로브 전까지 거부된다.

`relativeMove` 만 프로브하지 않는다 — 실제로 확인하려면 **카메라를 움직여야 하고**,
`ptzCapability` 의 `supportPTZ` 는 **자칭이라 믿을 수 없다**(이 벤더는 픽셀 센터링이 없는데도
`supportPan=on` 이라고 답한다 `[실측]`). 프로브는 전부 `mode=1`(읽기)만 쓴다 — `mode=0` 으로
프로브하면 **카메라가 실제로 움직인다.**

### 7-1. 무엇이 바뀌었나

### 7-2. `insecureTls` 를 설정·DB·UI 로 올린 것은 **계획을 뒤집은 결정**이다

설계 「확인 필요 #1」의 기본안은 **"올리지 않는다"** 였다(실측기는 평문 HTTP 80 이고, 자체서명
HTTPS 기기를 만나기 전에 열을 만드는 것은 추측성 코드 — CLAUDE.md 2번). **사용자 결정으로
뒤집혀** `CameraConfig` + DB 열 + UI 체크박스까지 올라갔다.

왜 요청별 TLS 여야 하는가: 프로세스 전역 `NODE_TLS_REJECT_UNAUTHORIZED` 는 **이 서비스 전체**
(검출기·코어 포함)의 검증을 끈다. 그래서 `fetch` 가 아니라 `node:http(s)` 를 쓰고
`rejectUnauthorized` 를 **요청마다** 넘긴다 `[코드 idisTransport.ts:75]`.

**`streamIndex` 는 올리지 않았다** — 요청이 없었고 실측기에서 1 이 동작한다. 드라이버 옵션으로만
존재한다.

**키 노출 규칙이 `camId` 선례보다 한 단계 좁다** `[코드 normalize.ts:77 · configCameras.ts:33]`:

```
kind === 'idis' && 값이 참   → 키를 만든다
그 밖                        → 키 자체가 없다
```

`camId` 는 값 유효성만 보지만, `insecureTls` 는 **`false` 가 기본**이라 값만 보면 모든 카메라에
`insecureTls:false` 가 붙어 **공개 응답의 키 집합이 넓어진다.**

### 7-3. 마이그레이션을 `addInsecureTls()` 별도 함수로 둔 이유

`upgradeToV2()` 의 additions 배열에 끼워 넣지 않았다. 그 함수의 이름·주석이 **"v2 에 더해진 열
넷"** 이라고 못 박고 있어 v5 열을 섞으면 문서가 거짓이 된다. **`dropCamCompany()`(v4)가 이미
같은 선례**다 — 판마다 자기 함수를 갖고, **판 번호가 아니라 열이 있는지로 판단해 멱등하다.**

`ADD COLUMN` 에 CHECK 를 붙일 수 없다는 SQLite 제약이 `insecure_tls` 에도 재현된다. 운영 DB
에는 이 열에 CHECK 가 없고, 대신 `upsertCamera` 가 `? 1 : 0` 으로 좁혀 넣는다 — **저장소 계층이
제약을 대신한다**는 이 파일의 기존 규약과 같다.

### 7-4. `verifyCameraKindConstraint` — **왜 표 재작성을 하지 않았나**

DB 파일은 세 모습뿐이다 `[코드 database.ts:162~201]`:

| 상태 | 모습 | `kind='idis'` 삽입 | 조치 |
|---|---|---|---|
| **(가)** ALTER 유래 (= 운영 DB) | `kind` 에 **CHECK 자체가 없다** | **된다** | 없음 |
| **(나)** 이 판의 `SCHEMA_SQL` 이 만든 파일 | CHECK 목록에 `'idis'` 있음 | 된다 | 없음 |
| **(다)** **옛 판의 `SCHEMA_SQL` 이 만든 v3/v4 파일** | 옛 목록의 CHECK 가 표 정의에 박혀 있다 | **거부(SQLITE_CONSTRAINT)** | **감지 후 명시적 오류** |

`CREATE TABLE IF NOT EXISTS` 는 이미 있는 표의 정의를 바꾸지 않으므로 `SCHEMA_SQL` 을 고쳐도
(다)는 그대로다. **그리고 `verifySchema` 는 이것을 잡지 못한다** — 그쪽은 표·뷰 이름과 **열
이름만** 대조하고 제약은 보지 않는다.

**고치지 않고 던지는 이유 — 연쇄 삭제 위험이 실재한다:**

> `migrate()` 는 `BEGIN`…`COMMIT` 안에서 돌고 **`PRAGMA foreign_keys` 는 트랜잭션 안에서
> 무효(no-op)** 다. 그 상태로 `DROP TABLE camera_info` 를 하면 SQLite 가 암묵 `DELETE FROM` 을
> 수행하고 `preset_info.cam_id … ON DELETE CASCADE` 가 발동해
> **프리셋 전부 → `slot_setup` 전부**가 연쇄 삭제된다.

커미셔닝 산출물(사람이 찍은 좌표·주차면)을 다루는 코드에서, **(다)라는 드문 상태 하나** 때문에
그 위험을 감수하지 않는다. 안전하게 하려면 트랜잭션 **밖에서** `foreign_keys=OFF` 를 걸고 별도
트랜잭션을 여는 구조 변경이 필요하다.

부수 근거 둘: ① `verifySchema` 의 명시적 철학("검사만 하고 고치지 않는다 — 보정까지 하면 대조가
두 번째 마이그레이션 엔진이 된다")과 같다. ② **실패 시점이 옮겨진다** — 가드가 없으면 사용자가
옵션 화면에서 IDIS 카메라를 저장하는 순간 해독 불가능한 `SQLITE_CONSTRAINT` 를 만나고, 가드가
있으면 **서버 기동 시** 한국어 문장으로 나온다.

**술어가 `user_version` 이 아니라 `sqlite_master.sql` 문자열**이라 멱등하고 (가)·(나)에서는
아무 일도 하지 않는다. 판 번호로 갈랐던 자리가 바로 v2 열 넷을 통째로 빠뜨린 자리였다.

**구현 중 드러난 함정 2개** `[QA §4-4]`:

- `sqlite_master.sql` 은 **적은 그대로**를 담아 주석도 들어 있고, 우리 스키마의 주석에 `kind`
  라는 낱말이 있다. **주석을 안 걷으면 매칭이 엉뚱한 CHECK 를 읽는다.** 그래서 먼저 걷는다.
- 정규식이 열 구분자(콤마)를 넘지 않게 `[^,]*?` 로 묶는다 — 같은 표의 `cam_type`·`intrinsics`
  CHECK 를 섞어 읽지 않기 위해서다. QA 가 뒤쪽 열에 CHECK 를 심은 픽스처로 오판하지 않음을
  확인했다.

### 7-5. QA 가 고친 기존 결함 — `openDatabase()` 의 DB 핸들 누수

**이번 작업 범위 밖이었으나 검증 자체를 막아서 고쳤다** `[QA §4-1]`.

- **위치** `src/db/database.ts:38~48`(수정 전)
- **증상** `migrate()` 가 던지면 **핸들이 닫히지 않는다.** Windows 에서는 그 파일을 지우지도
  옮기지도 못한다 — `Error: EBUSY: resource busy or locked, unlink '…\old-schema.db'`
  (QA 첫 실행에서 실제로 5건이 이 오류로 깨졌다)
- **이번 변경이 만든 결함은 아니다**(`verifySchema` 도 던진다). 그러나 **새 가드가 이 경로를
  일상적으로 도달 가능하게 만들었고**, 하필 그 상황이 "사람이 DB 파일을 손봐야 하는" 상황이라
  **파일이 잠기면 손쓸 방법까지 막힌다.**
- **조치** `try/catch` 로 감싸 실패 시 `db.close()` 후 재던짐. 4줄이고 성공 경로는 동일하다.
  회귀 시험("던진 뒤에도 그 파일을 지울 수 있다")을 `idisDatabase.test.ts` 에 남겼다.

### 10-2. 원인 — 개발 부산물 「추론(근거 강함) · 리더 확인」

**`nodemon` 이 `src/` 를 감시하다가 `SCHEMA_VERSION` 이 5 로 올라간 시점에 재기동하면서 판만

파일 mtime 21:36 이 구현 작업 도중이라는 것, 그리고 `camera_info` 정의가 여전히 (가)
상태(ALTER 유래, `kind` CHECK 없음)라는 것이 이 해석과 맞는다.

> **"정상적으로 v4 파일을 올리는 사용자"가 겪는 일이 아니다** — §10-5 가 그 증거다.
> **개발 중 판 번호가 코드보다 먼저 나가서 생긴 상태**다.

### 10-3. ⚠ 재발 방지 — 이 상태는 **스스로 낫지 못한다**

**개발 중 `SCHEMA_VERSION` 을 올리는 순간부터, 마이그레이션 함수를 다 쓰기 전에 nodemon 이
재기동하면 같은 일이 생긴다.** 그리고 한 번 그렇게 되면 자동으로 회복되지 않는다:

```
migrate():
  if (current < SCHEMA_VERSION) {  ← 판이 이미 5 면 여기 안 들어간다
     … addInsecureTls() …          ← 그래서 영원히 실행되지 않는다
  }
  verifySchema(db);                 ← 판과 무관하게 **항상** 돈다
```
`[코드 database.ts:72~99]`

**다음에 스키마 판을 올릴 때의 순서 규칙** — 마이그레이션 함수(`addXxx()`)와 `SCHEMA_SQL` 의
열을 **먼저** 쓰고 `SCHEMA_VERSION` 을 **마지막에** 올린다. 반대로 하면 그 사이의 재기동 한
번이 파일을 갇힌 상태로 만든다.

### 10-4. 이 사건이 **조용히 넘어가지 않은 이유** — `verifySchema` 설계가 잡았다

`verifySchema()` 는 **판을 올렸든 안 올렸든 항상 돈다.** 그래서 이 상태가 조용히 열려 한참
떨어진 자리에서 `undefined` 로 새어 나오는 대신, **서버 기동 시 한국어 오류 한 줄로 즉시**
드러났다.

`database.ts:95~96` 의 주석이 **이 실패 모드를 이미 예고하고 있었다**:

> "판을 올렸든 안 올렸든 **항상** 확인한다. 판이 이미 최신이라 위를 통째로 건너뛴 파일이
> 이번 사고의 모습이었다 — **판만 맞고 열은 없었다.**"

같은 실패가 `camera_info.kind` 에서 한 번 났었고, 그때 얻은 교훈으로 만든 안전망이 이번에
자기 값을 증명했다. **가드는 잡기만 하고 고치지는 못한다** — 그것은 결함이 아니라
`verifySchema` 의 명시적 철학("검사만 하고 고치지 않는다")이며, 대응은 사람이 하는 §10-5 다.

### 10-5. 실제 복구 — 권고안 A 로 처리했고 데이터는 온전하다 「리더 실측 2026-08-06 22:40」

## 11. 실기 미검증 목록 — ⛔ "동작 확인 완료"가 아니다

**실기 IDIS 카메라는 한 대도 없다. 이 작업의 모든 검증은 목(mock) 기반이다.**
설계 §7 의 5건이 그대로 열려 있고, QA 가 검증 중 4건을 더했다 `[QA §7]`.

**설계 단계부터 열려 있던 것:**

1. **틸트 원점과 부호** — `9000 − x` 는 **DC-S6261XT 한 대의 실측**이다. 다른 모델에서 같다는
   근거가 없다.
2. **줌 상한 1200** — 이 모델의 광학 x12 이고 **모델마다 다르다**.
3. **§4-B 분류표의 `[미확인]` 행** — `301`/`304`/`900`/`310`/`308` 을 기기가 실제로 돌려주는가.
   특히 `ptzMoveToPoint&mode=1` → `304` 는 **지원 기기가 있어야만** 확인된다.
4. **`videoSnapshot` 의 Content-Type** — §25 는 `image/webp` 라 적어 놓고 Data 는 JPEG 라고
   적는 모순이 있다(그래서 바이트로 판정한다).
5. **RTSP `trackID=N` 의 실제 코덱** — 번호를 믿지 말고 `ffprobe` 로 확인할 것 `[실측 교훈]`.

**검증 중 새로 드러난 것:**

6. **`modelInformation` 이 정말 POST 인가.** 매뉴얼 §4 원문은 POST 인데 다른 Read 액션은 GET
   이다. **프로브의 첫 줄이라 틀리면 모든 프로브가 벤더 확인 실패로 떨어진다** — 목에서는 절대
   드러나지 않는다.
7. **Digest 챌린지가 정말 `qop="auth"`·`algorithm=MD5` 인가.** 그 밖이면 구현이 **던진다**
   (조용히 MD5 로 계산하지 않는다 — 잘못된 response 를 보내면 401 만 돌아와 원인이 인증 방식
   이라는 사실이 어디에도 드러나지 않는다). 실기가 `MD5-sess`·`SHA-256` 을 쓰면 즉시 연결
   불가이고 그때 `digest.ts` 를 넓혀야 한다.
8. **`+` 를 공백으로 접지 않는 판단.** 프리셋 이름에 `+` 를 넣어 저장·조회하면 닫힌다.
9. **`insecure_tls` 가 필요한 실제 모델이 있는가.** TLS 계층 자체는 자체서명 서버로 닫혔지만,
   **그 기기의 인증서를 Node 가 거절하는 이유가 자체서명인지**(만료·SAN 불일치일 수도 있다)는
   실기 문제다.

## 12. 미해결 — 설계 판단이 필요한 2건

### 12-1. `portPairWarning` 이 IDIS 에 **근거 없는 "제어 + 10"** 경고를 띄운다

계획 T-UI2 는 "IDIS 는 park3d 전용 포트 경고 대상이 아니므로 **빈 문자열**"을 기대했다.
**그 기대는 성립하지 않는다** `[QA §5 — 함수 본문을 떼어 내 실제로 평가]`:

| 입력 | 결과 |
|---|---|
| `('http://h:80', 'rtsp://h:554/trackID=1', 'idis')` | `''` |
| `('http://h:80', 'http://h:8080/stream', 'idis')` | `''` |
| **`('http://h:8000', 'http://h:8080/stream', 'idis')`** | **`' ⚠ 제어 8000 의 영상 포트는 8010 입니다 …'`** |
| **`('https://h:8443', 'http://h:8080/stream', 'idis')`** | **`' ⚠ 제어 8443 의 영상 포트는 8453 입니다 …'`** |

**빈 문자열이 나오는 경우도 규칙 때문이 아니라 우연이다** — 이것이 QA 가 구현자 보고보다 한
걸음 더 들어간 자리다:

1. IDIS 제어는 보통 80/443 인데 `new URL().port` 가 **기본 포트를 지워** `controlPort = 0` 이
   되고 함수가 `if (!controlPort || !streamPort) return ''` 에서 빠져나간다.
2. IDIS 영상은 보통 `rtsp://` 라 첫 관문 `/^https?:\/\//` 에서 빠져나간다.

둘 중 **하나라도 어긋나면**(비기본 포트로 연 IDIS + MJPEG 중계) `kind === 'park3d-rpc'` 분기를
지나 **"영상 = 제어 + 10"** 이라는 **UE 시뮬레이터 직결 전용 규칙**으로 떨어진다. IDIS 에는
그런 규칙이 없다 — **화면이 사용자에게 없는 규칙을 지키라고 시킨다.**

**고치지 않았다.** "IDIS 의 올바른 포트짝 규칙은 무엇인가"에 답해야 하는데 답이 "규칙이 없다"
이고, 그러면 폴백 갈래를 kind 별로 갈라야 한다 — 이는 **UI 경고 규칙의 계약 변경**이고
`hucoms`·`backend-core` 의 기존 동작에도 영향이 간다.

**대신 느슨하게 덮지 않았다.** `toBe('')` 같은 관대한 단언 대신 **틀린 문구를 문자열 그대로**
박았다. 누가 고치는 순간 이 시험이 깨지고, **그때가 결함 해소 시점**이다. IDIS 와 hucoms 의
반환값이 **같음**도 단언해, 이것이 IDIS 전용 분기의 문제가 아니라 **폴백 한 갈래를 공유하기
때문**임을 못박았다.

> **판단 필요**: 폴백 갈래를 `hucoms`·`backend-core` 로 좁히고 그 밖의 종류에는 `''` 를
> 돌려줄 것인가.

### 12-2. `POST` 와 `PUT` 이 같은 값을 **다른 이름**으로 읽는다 — 이번 작업이 만든 결함이 아니다

| 본문 | 저장된 `insecure_tls` |
|---|---|
| `POST {cam_uuid, kind:'idis', insecure_tls:true}` | **0** (무시됨) |
| `POST {cam_uuid, kind:'idis', insecureTls:true}` | 1 |
| `PUT {insecure_tls:true}` | 1 |

`[QA §4-3 — 라이브 서버에 실제로 쏴서 확인]`

원인은 두 경로가 다른 정규화를 지나기 때문이다 `[코드]`:

- `POST /api/db/cameras` → `normalizeCamera({...body, id})` → **camelCase `r.insecureTls`**
- `PUT /api/db/cameras/:id` → `merged(current, patch)` → **snake_case `patch.insecure_tls`**

> **리더 확인 결과: 기존 `camId` / `park3d_cam_id` 도 정확히 같은 비대칭이다.**
> `normalizeCamera` 는 `camId`(camel)를 읽고 `merged()` 는 `park3d_cam_id`(snake)를 읽는다
> `[코드 normalize.ts:76 · dbRoutes.ts:234]`. **이번 작업이 만든 결함이 아니라 저장소 전반의
> 관례 문제**이며, `insecureTls` 는 그 관례를 **그대로 따랐을 뿐**이다.

**고치지 않은 이유:** 넓힐지(POST 도 snake 를 읽기) 좁힐지는 **계약 판단**이고, 고치려면
`camId` 를 포함한 모든 필드를 함께 손대야 한다 — 요청은 IDIS 드라이버 추가지 REST 본문 계약
정리가 아니다(CLAUDE.md 3번 외과적 변경).

**지금은 사고가 안 난다** — 화면의 「+ 기기 추가」는 `{cam_uuid, kind, label}` 만 보내고 나머지는
전부 PUT 으로 채운다(그 사실도 시험으로 고정했다). 현재 동작을 `[기록]` 케이스로 사실대로 고정만
해 두었다.
