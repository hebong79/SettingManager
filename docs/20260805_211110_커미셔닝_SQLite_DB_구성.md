## 2. 드라이버 — `node:sqlite` (설치 없음)

Node **22.5+** 의 내장 모듈을 쓴다. `better-sqlite3` 같은 네이티브 패키지를 넣지 않으므로
이 서비스의 **런타임 의존성 0 원칙이 그대로 유지된다.** 실제 환경(Node v24.16.0)에서 한글
왕복까지 확인했다.

- `package.json` 의 `engines.node` 를 `>=20` → **`>=22.5`** 로 올렸다.
- Node 가 "실험적 기능" 경고를 한 줄 찍는다. 기능은 정상 동작한다.
- **번들러 우회 1건** — `src/db/sqlite.ts`. `node:sqlite` 는 vitest 가 쓰는 Vite 판의 내장
  목록에 아직 없어서, 정적 `import` 를 두면 `sqlite` 라는 npm 패키지를 찾다 실패하고
  **테스트가 아예 수집되지 않는다.** `createRequire` 로 런타임에 부르면 번들러가 볼 명세자가
  없어 그 경로를 타지 않는다. 타입은 `import type` 으로 따로 받는다(컴파일 때 지워진다).

## 3. 스키마 — 문서 7표 → 6테이블 + 1뷰

```
place_info ──< camera_info ──< preset_info ──< slot_setup ──< parking_slot (1:1)
                                                     └──────< parking_evnt (1:N)
                                              floor_ROI = slot_setup 의 VIEW
```

### 문서와 다른 자리 (해석 7건 — 전부 `src/db/schema.ts` 머리말에 있다)

| # | 해석 | 왜 |
|---|---|---|
| 1 | **`floor_ROI` 는 VIEW** | 1번은 5번의 진부분집합이고 둘 다 "전체 슬롯 갯수만큼"이다. 같은 값을 두 자리에 저장하면 반드시 어긋나고, 어긋났을 때 어느 쪽이 맞는지 판단할 근거가 없다 |
| 2 | `pos`·`ptz` **를 3열로 편다** | 한 칸에 문자열로 넣으면 "줌이 8000 이상인 슬롯"조차 질의할 수 없다 |
| 3 | **이미지는 경로만** | JPEG 를 BLOB 으로 넣으면 DB 가 금방 수백 MB 가 되고 슬롯 한 줄 읽는 질의까지 무거워진다 |
| 4 | `parking_evnt` 에 **`event_id`** | 문서에 키가 없다. 같은 슬롯으로 여러 줄이 쌓이므로 대리키 없이는 한 줄을 가리킬 수 없다 |
| 5 | **`cam_uuid` = SettingManager 기기 id** | 이 서비스의 기기 id 는 `real-camera-1` 문자열이고 문서의 `cam_id` 는 정수다. 잇는 자리가 필요하다 |
| 6 | **`marked_x`·`marked_y` 를 더한다** | 문서의 `slot_setup` 에 "사람이 찍은 픽셀"을 담을 칸이 없다. `slot3d_front_center` 는 3D 에서 **계산된** 점이라 다른 값이다. 그 클릭 좌표가 호밍의 출발점이므로 없으면 커미셔닝이 성립하지 않는다 |
| 7 | ROI·박스류는 **JSON 문자열 + `json_valid`** | 점 개수까지는 스키마가 검사할 수 없다 — 저장소 계층의 몫이다 |

### 안 채운 칸은 **NULL 로 둔다**

`ptz_pan` 이 NULL 이면 *"아직 번호판 센터라이징을 안 했다"* 는 뜻이다. 0 으로 채우면
"원점을 보고 있다"는 거짓말이 되고, **덜 끝난 슬롯을 골라낼 수 없게 된다**(`listUncentered()`).

### 무결성 세 가지

| PRAGMA/제약 | 없으면 |
|---|---|
| `PRAGMA foreign_keys = ON` | SQLite 는 기본이 **꺼짐**이다 — 없는 카메라를 가리키는 프리셋이 조용히 들어간다 |
| `ON DELETE CASCADE` | 프리셋을 지웠는데 슬롯이 남아 유령을 가리킨다 |
| `UNIQUE (cam_id, preset_id, preset_slotidx)` | 한 구도에 같은 순번의 주차면이 둘 생긴다 |
| `PRAGMA user_version` | 옛 코드가 새 파일을 열어 모르는 열을 무시한 채 쓴다 → **판이 높으면 던진다** |

## 4. 저장소 계층

| 파일 | 내용 |
|---|---|
| `src/db/sqlite.ts` | 내장 모듈 로딩 한 곳(번들러 우회) |
| `src/db/schema.ts` | DDL + `SCHEMA_VERSION` |
| `src/db/database.ts` | `openDatabase` · `migrate` · `transaction` · `DatabaseError` |
| `src/db/setupRepository.ts` | 장소·카메라·프리셋·슬롯 CRUD + `floorRoi()` + `listUncentered()` |
| `src/db/parkingRepository.ts` | 상태·이벤트(문서 6·7번) |

**SQL 이 이 폴더 밖으로 새지 않는다.** 라우트나 코어가 문자열 질의를 들기 시작하면 스키마를
바꿀 때 어디까지 고쳐야 하는지 아무도 모르게 된다.

### `upsertSlot` — 주지 않은 칸은 건드리지 않는다

커미셔닝은 여러 단계가 같은 줄을 조금씩 채우는 일이다(ROI → 3D → 검출 → 센터라이징 → 스냅샷).
매번 전체를 요구하면 앞 단계 결과가 지워진다. `null` 을 **명시로** 주면 그때는 지운다.

### `ParkingRepository.record` — 상태와 이력을 한 트랜잭션에

따로 부르게 두면 하나만 성공했을 때 *"지금은 비었는데 나간 기록이 없는"* 상태가 되고,
그 불일치는 나중에 어느 쪽이 맞는지 판단할 방법이 없다.

## 5. JSON 내보내기 — 왜 변환 코드가 없는가

정본은 SQLite 다. 그런데 backend-core 와는 **파일을 복사해 주고받는 경로**가 있었고
(`discovery-<기기id>.json`·`spots-<기기id>.json`), 그것을 잃지 않기로 했다(F1).

여기서 좋은 성질을 하나 썼다 — **DB 저장소가 backend-core 모양 그대로 답하게 만들었다.**

```
DiscoveryDbStore.load()  →  backend-core 파일과 같은 객체
                         ├─ REST 응답이 이 모양이다 (계약 불변)
                         └─ 파일로 쓰면 그대로 discovery-<id>.json  (내보내기)
```

`backendCoreExport.ts` 가 하는 일은 그 결과를 디스크에 쓰는 것뿐이다.
**형식 변환기가 따로 없으므로 내보내기와 실제 동작이 어긋날 자리가 없다.**
(`bridgeStores.test.ts` 의 마지막 검사가 "내보낸 파일 === 저장소가 답하는 것"을 고정한다.)

가져오기(JSON → DB)는 만들지 않았다 — 지금 쓰는 곳이 없다.

### id 두 벌을 잇는 자리

| 밖(backend-core 어휘) | DB |
|---|---|
| 프리셋 `p-3` | `preset_info.preset_id = 3` (카메라 안에서 1부터) |
| 점 `pt-2` | `slot_setup.preset_slotidx = 2` (프리셋 안에서 1부터) |
| 스팟 `spot-7` | `slot_setup.slot_id = 7` (**전체 슬롯 통번**) |

**DB 로 옮기면서 얻은 것이 그 통번이다.** JSON 파일에는 없던 개념이고, 문서의 목적 첫 줄이
정확히 이것을 요구한다 — *"프리셋내 주차면들을 만들고 전체 슬롯 인덱스에 매핑한다."*
그래서 점·스팟 응답에 `slotId` 를 실어 보낸다(기존 필드는 그대로 두고 더하기만 했다).

## 6. 계약 변경 1건 — 주차면은 프리셋에 속한다

문서 모델에서 모든 슬롯은 (카메라, 프리셋)에 속한다. 그래서 `POST /api/core/slots` 가
어느 구도의 주차면인지 정해져야 한다.

| 상황 | 답 |
|---|---|
| 프리셋이 정확히 하나 | 그 프리셋에 저장한다 |
| 프리셋이 없음 | **409** — "먼저 프리셋을 만드십시오" |
| 프리셋이 둘 이상 | **409** — "어느 구도의 주차면인지 정해야 합니다" |

아무거나 고르지 않는 이유: 그 슬롯은 나중에 **엉뚱한 구도의 점으로 읽힌다.** 픽셀 좌표는
어느 구도에서 찍었는지를 알아야만 의미가 있다.

| 디스크 | `setup.db`(+`-wal`·`-shm`) 와 두 JSON 이 나란히 남는다 |

### 작업 중 잡은 것 2건

**① 번들러가 `node:sqlite` 를 못 찾음** — 서버 테스트 4개가 통째로 수집 실패했다.
Vite 설정으로 외부화를 두 번 시도했으나 둘 다 안 먹었고, **소스에서 bare specifier 를 없애는**
방법(`createRequire`)으로 해결했다. 우회를 한 파일에 가두고 이유를 거기 적었다.

**② `DatabaseError` 가 500 으로 샘** — 프리셋 없이 주차면을 저장하면 409 여야 하는데 500 이
나왔다. `server.ts` 의 오류→상태코드 매핑에 이 클래스가 없었다. 매핑을 더했다.

## 8. 영향도

### 바뀐 것

| 대상 | 변경 | 조치 |
|---|---|---|
| 브리지 탐색·주차면 저장 위치 | JSON 파일 → **SQLite** | REST 응답 모양은 불변. 기존 JSON 파일이 있어도 **읽지 않는다**(가져오기 미구현) |
| `ServerDeps` | `storeDir` → **`db?: DatabaseSync`** | 없이도 서버는 뜬다 — 그 능력들만 꺼진다 |
| `src/store/discoveryStore.ts`·`spotStore.ts` | 클래스 제거, **형식 정의(타입 + `normPtz`)만** 남김 | 내 변경으로 죽은 코드가 됐으므로 함께 정리 |
| `POST /api/core/slots` | 프리셋 없으면 **409** | §6 |
| `package.json` | `engines.node` `>=22.5` | Node 22.5 미만에서는 기동하지 않는다 |
| `.gitignore` | `setup.db`(+WAL) · `discovery-*.json` · `spots-*.json` | 현장 좌표·계정이 들어간다 |

### 안 바뀐 것

`config.json` 이 **여전히 카메라의 정본**이다. `camera_info` 는 커미셔닝 산출물 쪽의 표이고,
브리지가 프리셋을 만들 때 그 기기의 줄이 없으면 `cam_uuid` 만으로 만들어 둔다(연결 정보는
비어 있다). **둘 중 무엇이 카메라의 주인인가는 이번에 정하지 않았다** — 정하려면 옵션 화면·
정규화·드라이버까지 함께 움직여야 한다.

그 밖에 `src/devices/**`·`src/media/**`·`domain/ptz.ts`·원격 코어·API 계층은 불변이다.

### 보안

`camera_info.password` 는 문서에 있는 칸이라 그대로 두었다. **DB 파일이 곧 자격증명 사본**이
되므로 `.gitignore` 에 넣었고, 내보내는 두 JSON 에는 계정이 실리지 않는다.

## 9. 남은 일

| 항목 | 왜 지금 안 했나 |
|---|---|
| REST 노출(`/api/db/*` · 최종 셋업 파일 다운로드) | F4 에서 범위 밖으로 정했다 |
| JSON → DB **가져오기** | 쓰는 곳이 없다. 기존 JSON 을 이어받아야 하면 그때 만든다 |
| `config.json` ↔ `camera_info` 주인 정하기 | 옵션 화면·정규화·드라이버가 함께 움직여야 한다 |
| 이미지 파일의 실제 저장 위치 규약 | 지금은 경로 문자열만 받는다 — 누가 어디에 쓰는지는 미정 |
| 문서 6·7번의 실사용 | *"셋팅에이전트 완성후 카메라 제어 Agent 에서 사용예정"* — 소비자가 생기면 질의를 늘린다 |
