## 2. 기능 추가

### 2.1 옵션 페이지 재구성 — 선택 기반 편집

전에는 등록된 카메라 전부를 카드로 나열했다. 이제 **콤보박스에서 고른 기기 하나만** 아래 편집 폼에 뜬다. 페이지는 한쪽 컬럼만 쓴다(`<main class="narrow">`, 660px).

| 카드 | 내용 |
|---|---|
| 시뮬레이터 | 시뮬레이터 URL + 저장 |
| 기기 (장치) | 카메라 콤보 · 「이 기기를 활성으로」 · 새 기기 ID/타입 + 「+ 기기 추가」 |
| 기기 편집: `<id>` | 이름·타입·제어 URL·계정/비밀번호·영상 URL·타임아웃 + 「이 기기 적용」·「연결 테스트」·「되돌리기」·「삭제」 |

저장 버튼이 카드마다 따로여서 **누른 카드의 내용만** 저장된다. 저장 안 한 편집이 있으면 머리글에 「저장 안 됨」 배지가 뜨고, 다른 기기로 옮길 때 확인을 묻는다 — 조용히 버리지 않는다.

### 2.2 기기 추가 · 삭제 · 연결 테스트

| API | 동작 |
|---|---|
| `POST /api/cameras` | ID·타입만으로 등록. 중복 409, 안전하지 않은 ID 400 |
| `DELETE /api/cameras/:id` | 삭제. **그 기기의 프리셋도 함께 삭제** |
| `POST /api/cameras/:id/test` | 연결 테스트 |

설계 판단 네 가지:

- **연결 테스트는 저장 없이 현재 폼 값으로** 한다(`body.camera` 를 받아 메모리 사본에만 병합). URL·계정을 고치는 중에 「적용」 전에 확인하는 것이 실제 용도다. **카메라를 움직이지 않고 PTZ 읽기만** 한다.
- **연결 실패는 예외가 아니라 결과다.** `200 { ok:false, error, elapsedMs }` 로 답한다 — 요청 처리는 정상이었고, 실패는 사용자가 봐야 할 정보다.
- **삭제 시 프리셋 동반 삭제.** 남기면 없는 기기를 가리키는 프리셋이 되고, 같은 ID 로 다른 기기를 등록하는 순간 **남의 좌표로 이동하는 프리셋**이 되살아난다.
- **마지막 1대는 삭제 불가(409)**, 활성 기기를 지우면 남은 첫 기기로 활성이 옮겨 간다. 카메라 0대 설정은 다음 기동에서 로드 자체가 실패한다.

기기 ID 는 경로·URL 에 그대로 들어가므로 `^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$` 로 제한한다.

### 2.3 영상 경로 — 스킴이 경로를 가른다

설정 필드 `rtspUrl` → **`streamUrl`**(영상 URL)로 바꾸고 세 경로로 갈랐다. 옛 이름은 별칭으로 계속 읽는다.

| 스킴 | 처리 | 구현 |
|---|---|---|
| `rtsp://`·`rtsps://` | ffmpeg 로 MJPEG 전사 | `rtspFrames` |
| `http://`·`https://` | **연속 MJPEG 를 그대로 중계** | `httpMjpegFrames` (신규) |
| 비움 | 스냅샷 폴링 | `snapshotFrames` |

`httpMjpeg.ts` 는 **multipart 헤더를 파싱하지 않는다.** JPEG 의 SOI/EOI 로 끊으면 boundary 이름이 무엇이든(`baroframe`·`baroworldboundary`) 같은 코드로 동작하고, 파트 헤더는 SOI 앞 바이트라 `splitJpegFrames` 가 알아서 버린다. ffmpeg 를 거치지 않아 지연도 중복 프레임도 없다.

### 2.4 PTZ 정착(settle) 대기

`waitForSettle` 을 넣어 `/api/ptz/absolute` · `/api/ptz/nudge` · `/api/presets/:id/goto` 가 **이동이 멈춘 뒤의 좌표**를 답한다. 상세는 §3.3.

## 3. 결함 4건 — 재현 · 원인 · 조치

### 3.1 옛 필드명으로 보낸 입력이 조용히 버려짐

**증상** — "브라우저 URL 창에 직접 치면 되는데, 옵션창에서 설정하면 안 된다."

**재현**
```
저장 전: http://192.168.0.22:8091/
PUT {"cameras":[{"id":"simulator-1","rtspUrl":"http://192.168.0.22:8092/"}]}
저장 후: http://192.168.0.22:8091/    ← 입력이 사라짐
```

**원인** — `rtspUrl` → `streamUrl` 개명 시 옛 이름을 **읽기 전용 별칭**으로만 처리했다. 병합이 `{...camera, ...change}` 라 기존 `streamUrl` 이 남아 있고, 정규화의 `streamUrl || rtspUrl` 에서 기존 값이 이겨 **새 입력이 버려진다**. 브라우저에 옛 화면이 열려 있으면(재기동 전에 로드된 탭) 그 화면이 옛 이름으로 보내므로 "저장했는데 안 바뀐다"가 된다.

**조치**
- `promoteLegacyFields()` — 갱신에서도 `rtspUrl` 을 `streamUrl` 로 승격한 뒤 병합. 둘 다 오면 새 이름 우선, 빈 값이면 실제로 비워짐.
- 정적 파일 `cache-control` 을 `no-cache` → **`no-store`**. 서버를 고친 뒤 브라우저가 옛 화면을 들고 설정을 되돌리는 것을 막는다.

### 3.2 UTF-8 이 아닌 본문이 조용히 손상되어 저장됨

**증상** — 카메라 콤보박스의 한글이 `�ùù���` 로 깨짐.

**원인** — **작업자(AI)의 검증 명령이 원인이었다.** Git Bash 콘솔이 CP949 라 `curl -d '{"label":"시뮬레이터"}'` 가 CP949 바이트로 나갔고, Node 의 `Buffer.toString('utf8')` 이 잘못된 바이트를 **조용히 U+FFFD 로 치환**해 그대로 `config.json` 에 저장됐다. 화면 코드나 저장 로직의 결함은 아니었다.

**조치** — 받는 자리에서 끊는다. `readJsonBody` 가 디코드 결과에 U+FFFD 가 있으면 **400 으로 거부**한다. 깨진 한글이 설정 파일에 영구히 남는 경로를 없앴다.

### 3.3 이동 중간값을 최종 좌표로 보고함

**증상** — 시뮬레이터에서 PTZ 버튼을 눌러도 표시가 안 바뀌거나 모자라게 움직임.

**재현 (UE 시뮬 192.168.0.22:8083)**

| 시점 | pan |
|---|---|
| 요청 전 | 1296 |
| nudge +200 직후 응답 | **1446** ← 이동 중 |
| 2초 후 실제 | **1496** |

**원인** — 카메라는 "이동 완료" 신호를 주지 않는다. UE 시뮬은 PTZ 를 애니메이션으로 움직이므로 명령 직후 읽기가 **중간값**을 준다. 그 값을 기준으로 다음 상대 이동을 계산하면 목표가 계속 뒤로 밀린다. 실카메라는 슬루가 빨라 증상이 드러나지 않았다.

**조치** — `waitForSettle`
- 연속 두 번 읽은 값이 허용오차(pan·tilt 0.1° = 10cd, zoom 10 raw) 안일 때까지 250ms 간격 폴링
- 팬은 0/36000 심을 **순환 거리**로 계산 — 없으면 심 근처에서 정착 판정이 영원히 안 난다
- 상한(10초) 초과 시 **던지지 않고** `settled: false` 로 알린다. 마지막 좌표도 쓸모 있는 정보이고, 던지면 화면이 "어디에 있는지조차" 못 보여준다
- `nudge` 는 **기준 자세도 정착값**으로 읽는다

**검증 (실 시뮬, 연속 3회 pan +200)**
```
1회차 → pan 1696 | settled True
2회차 → pan 1896 | settled True
3회차 → pan 2096 | settled True
3초 후 실제 위치: 2096   ← 표시값과 일치
```

### 3.4 제어와 영상이 서로 다른 카메라 (가장 오래 걸린 건)

**증상** — "시뮬레이터와 통신이 안 되는 것 같다. 팬·틸트 버튼 동작 안 함."

**조사** — 통신은 정상이었다. 3축 모두 정확히 착지했고(pan 3096 / tilt 3000 / zoom 5000), 테스트 시작 시점 좌표가 이전에 둔 값이 아니라 **사용자가 누른 버튼이 모두 반영된 값**이었다. 즉 명령은 갔고 카메라도 움직였다 — **화면만 안 바뀌었다.**

**원인** — UE 시뮬은 카메라 **4대**이고 제어/영상 포트가 1:1 짝이다.

| 제어 | 영상 | 상태(2026-07-31) |
|---|---|---|
| 8081 | 8091 | 살아 있음 |
| 8082 | 8092 | 살아 있음 |
| 8083 | 8093 | **영상 서버 미기동** |
| 8084 | 8094 | 영상 서버 미기동 |

설정이 **제어 8083 / 영상 8091** 이었다 — 8083 번을 조종하면서 **8081 번 화면**을 보고 있었다. 숫자는 바뀌는데 그림은 절대 안 바뀌니 "버튼이 안 먹는다"로 보인다. 8093 이 무응답이라 8091 로 바꾼 것이 원인이고, **다른 카메라의 영상이라는 점을 알리지 않은 것**이 결함이다.

**결정적 증명** — 8081 번을 pan 0→12000 으로 움직이자 8091 스트림의 프레임이 바뀌었다(md5·크기 모두 변화). 8091 = 8081 의 영상. (8081 은 원위치 복구했다.)

**조치**
- 설정을 짝이 맞는 쌍(제어 8081 / 영상 8091)으로 교정
- 옵션 페이지에 **포트 짝 경고**: 제어·영상이 같은 호스트의 http 인데 `영상 = 제어 + 10` 이 아니면 경고를 띄운다
  > ⚠ 제어 8083 의 영상 포트는 8093 입니다 — 8091 는 다른 카메라의 영상일 수 있습니다.

**검증 (end-to-end)**
```
이동 전 프레임: 5fd99ff50301  174324 bytes
SettingManager 로 PAN +6000 → 응답 pan 6000, settled True
이동 후 프레임: cdb8f1477e42  147602 bytes
화면이 실제로 바뀜: YES
```

## 4. RPC 통신 모듈 — 만들지 않았다 (근거)

"시뮬레이터는 동작 방식이 다르니 RPC 로 하자"는 요청을 받고 baro_calory 를 조사했다. **PTZ 에는 RPC 가 필요 없다.**

근거는 `baro_calory/packages/cctv-client/src/scene-control-client.mjs` 첫 줄이다.

> Scene-control RPC client — 시뮬레이터의 **"씬 편집" 평면**(주차면 조회 · 차량 스폰/설정/삭제 · 번호판 교체). **카메라 PTZ(Hucoms CGI)와 별개의 관심사**라 별도 클라이언트로 둔다. 전송은 UE sim 이 노출하는 JSON REST(`/scene/*`, scene-admin 포트) — Hucoms 와이어가 아니다.

| 평면 | 프로토콜 | 상태 |
|---|---|---|
| 카메라 PTZ | **Hucoms CGI** (실카메라와 동일) | 구현·동작 확인 |
| 씬 편집 (차량·주차면) | RPC (`/scene/*` JSON REST) | 미구현 |

**실측이 이를 뒷받침한다** — `192.168.0.22:8083/cgi-bin/control/ptzf_status.cgi` 가 `panpos = 296` 으로 정상 응답하고, `goptzfpos` 로 3축이 정확히 착지한다. 시뮬은 PTZ 에서 실카메라와 **같은 방식**이다(Hucoms CGI 모사).

RPC 가 필요해지는 시점은 따로 있다 — **주차면 목록을 시뮬 씬에서 직접 읽거나, 차량을 배치·삭제**하는 기능이다. 지금은 backend-core 경유(`/api/simulator/slots`)라 baro_calory 백엔드가 떠 있어야 한다. 시뮬에 직접 붙는 `/scene/*` 클라이언트는 **별도 작업**이다.

## 7. 영향도 분석

### 7.1 이 저장소

| 변경 | 영향 |
|---|---|
| `rtspUrl` → `streamUrl` 개명 | 설정 스키마 변경. **옛 이름은 읽기·쓰기 모두 별칭으로 지원**하므로 기존 `config.json` 은 그대로 열린다 |
| 정적 파일 `no-store` | 매 요청 재전송. 파일이 작아 실측 영향 없음 |
| 정착 대기 도입 | 이동 API 응답이 **느려진다**(이동 시간만큼). 대신 응답 좌표가 최종값이다 |
| UTF-8 거부 | CP949 등으로 보내는 클라이언트는 400. 브라우저는 항상 UTF-8 이라 영향 없음 |
| 기기 삭제 시 프리셋 동반 삭제 | `presets.json` 이 함께 갱신된다 |
| `.gitignore` 에 `config.json` 추가 | **실제 접속 정보가 커밋되지 않는다.** 새 머신은 `config.example.json` 을 복사해 채운다 |

### 7.2 외부

| 대상 | 영향 |
|---|---|
| baro_calory | 코드 변경 없음. `/api/ptz`·`/api/snapshot`·`/api/simulator/slots` 만 소비 |
| UE 시뮬레이터 | **실제로 움직인다.** 검증 중 8081·8083 을 이동시켰고 8081 은 원위치 복구했다 |
| 실카메라 | 읽기만 했다. **이동 명령은 실행하지 않았다**(운영 중인 물리 카메라라 별도 승인 필요) |
| SettingAgent | 코드 변경 없음. 포트가 다르다(13020 vs 13030). 같은 실카메라를 동시에 조작하면 서로 흔들 수 있음 |

### 7.3 남은 한계

1. **동시 조작 보호 없음.** 여러 탭·다른 도구가 같은 카메라를 동시에 움직이면 서로 덮어쓴다(설계서 §10 의 lease 미구현).
2. **인증 없음.** 지금 `server.host` 가 `0.0.0.0` 이라 사내망에 열려 있다. 같은 망의 누구나 카메라를 움직일 수 있다.
3. **장비 내장 프리셋(1~255) 미지원.** 프리셋은 SettingManager 자체 저장소만 쓴다.
4. **시뮬 씬 제어(RPC) 미구현.** 주차면은 backend-core 경유로만 조회된다(§4).
5. **8083·8084 는 영상이 없다.** 시뮬 쪽에서 8093·8094 MJPEG 서버를 켜야 4대를 다 쓸 수 있다.
