## 2. 누가 무엇의 주인인가 — 이 작업의 핵심 결정

config 와 DB 가 **같은 카메라를 각자 들고 있게** 됐다. 한쪽이 다른 쪽을 통째로 덮으면
반드시 사고가 난다. 그래서 **칸 단위로 주인을 갈랐다**(`src/db/cameraSync.ts`).

| 칸 | 주인 | 왜 |
|---|---|---|
| `url` · `user_id` · `password` · `rtsp_url` · `cam_name` | **config.json** | 실제로 카메라에 붙는 값이다. 드라이버가 이걸로 접속하므로 "어느 주소로 붙었나"에 답할 곳이 하나여야 한다 |
| `place_id` · `cam_type` · `cam_company` | **DB** | 커미셔닝의 분류다. config 는 **처음 등록될 때만** 심고 그 뒤로는 손대지 않는다 |

**아래쪽을 config 가 계속 밀어 넣으면 어떻게 되는가** — 옵션의 장소 탭에서 카메라를 옮겨
놓아도 다음 기동에 조용히 되돌아간다. 화면에서 한 일이 이유 없이 사라지는 것이 가장
추적하기 어려운 실패다. 그래서 `place_id` 는 **DB 가 기준**이고, `config.json` 의 값은
그 기기가 처음 등록될 때 쓰는 **씨앗**이다. 이 규칙을 `config.example.json` 주석과
`types.ts` 주석 양쪽에 적어 두었다.

**DB 에만 있고 config 에 없는 카메라는 지우지 않는다.** 기기를 config 에서 잠시 뺐다고
그 카메라로 찍어 둔 프리셋·주차면까지 사라지면 안 된다(외래키가 CASCADE 다).

config 에만 있는 장소는 **만들어 둔다** — 외래키가 걸려 있어 없는 장소를 가리키면 카메라가
아예 안 들어간다. 이름은 `장소 7` 처럼 임시로 붙고, 옵션의 장소 탭에서 고친다.

## 3. 옵션 서브탭

```
[ 서비스 설정 ] [ 장소 (place_info) ] [ 카메라 (camera_info) ] [ 프리셋 (preset_info) ]
```

- **서비스 설정** — 기존 카드 전부(코어 구현·BackendCore·기기·기기 편집). 한 줄도 바꾸지 않았다.
- **장소** — 추가·이름변경·삭제. 쓰는 카메라가 있으면 **409 로 막고 누가 쓰는지 말한다**
  (`FOREIGN KEY constraint failed` 는 무엇을 고쳐야 하는지 알려 주지 않는다).
- **카메라** — `cam_name`·`cam_type`·`cam_company`·`place_id` 만. **접속 정보는 여기 없다**(§2).
  삭제하면 그 카메라의 프리셋·주차면이 함께 사라진다고 확인창이 말한다.
- **프리셋** — 추가·수정·삭제. `preset_id` 는 그 카메라 안에서 1부터 자동. 삭제 응답에
  **함께 사라진 주차면 개수**(`removedSlots`)가 실린다.

화면 코드는 `web/optionsDb.js` 로 **파일을 나눴다.** `options.js` 는 `config.json` 을,
이쪽은 SQLite 를 다룬다 — 한 파일에 섞으면 "이 값을 고치면 어디가 바뀌는가"를 코드에서
읽어 낼 수 없다.

## 4. 테이블 뷰어 (`/dbtable`)

**읽기 전용이다.** 고치는 것은 옵션의 DB 탭에서 한다 — 사람이 슬롯 좌표를 직접 고치기
시작하면 그 값이 무엇으로 측정된 것인지 아무도 모르게 된다.

| 기능 | 동작 |
|---|---|
| 테이블 선택 | 7개(6테이블 + `floor_ROI` 뷰). 뷰는 「(뷰)」로 표시 |
| 텍스트 검색 | 부분 일치. 열을 안 고르면 **모든 열**을 훑는다(숫자 열도 `CAST` 로) |
| 기간 검색 | 시간 열이 있는 테이블에서만. 날짜만 줘도 **그날 전체**가 잡힌다 |
| 조건 검색 | 열 + 비교(`=` `!=` `<` `<=` `>` `>=` `LIKE` `IS NULL` `IS NOT NULL`) + 값 |
| 페이지 | 50·200·500·2000, 전체 개수와 함께 답한다 |

**화면이 열 이름을 지어내지 않는다.** `GET /api/db/tables` 가 준 목록(서버가
`PRAGMA table_info` 로 SQLite 에게 직접 물은 것)으로 콤보와 표 머리를 그린다 —
스키마가 바뀌면 화면 코드를 고치지 않아도 따라온다.

**시간 열이 없는 테이블에서는 기간 입력을 잠근다.** 조용히 무시하면 "걸렀는데 왜 다
나오지"가 되고, 서버도 그런 요청은 400 으로 거절한다.

### 안전 — 식별자는 바인딩할 수 없다

값은 전부 바인딩 파라미터로 나가지만 **테이블·열 이름은 SQL 문법의 일부라 바인딩이 안 된다.**
그래서 화이트리스트 말고는 막을 방법이 없고, 그것이 `src/db/tableQuery.ts` 의 전부다.

| 대상 | 대조 상대 |
|---|---|
| 테이블 | `VIEWABLE_TABLES` 7개 |
| 열 | 그 테이블의 `PRAGMA table_info` 결과 |
| 비교 연산자 | 정해진 9개 |

테스트가 다섯 방향의 주입 시도를 못 박는다 — 테이블 이름(`sqlite_master`,
`preset_info; DROP TABLE …`), 열 이름, 연산자, 정렬 열, 그리고 **값에 든 따옴표는 그냥
값이라는 것**(`'; DROP TABLE preset_info; --` 로 검색하면 0줄이 나오고 표는 멀쩡하다).

## 5. 새 REST 라우트 13개

| 경로 | 용도 |
|---|---|
| `GET /api/db/tables` · `POST /api/db/query` | 뷰어 |
| `GET·POST /api/db/places` · `PUT·DELETE /api/db/places/:id` | 장소 |
| `GET /api/db/cameras` · `PUT·DELETE /api/db/cameras/:id` | 카메라 분류 |
| `GET·POST /api/db/presets` · `PUT·DELETE /api/db/presets/:camId/:presetId` | 프리셋 |

전부 MCP 라우트 카탈로그에 등재했고, **하나도 카메라를 움직이지 않는다**(테스트가 고정).
DB 가 열려 있지 않으면 503 이다 — 서버는 DB 없이도 뜬다.

## 7. 영향도

### 계약 변경 1건

**공개 카메라의 키 집합에 `place_id` 가 늘었다.** `/api/settings`·`/api/cameras` 응답이
한 칸 넓어졌고, 키 집합을 정확히 단정하던 테스트 2건을 갱신했다. 기본값 1 이 정규화에서
채워지므로 **"없는 카메라"는 생기지 않는다.**

### 안 바뀐 것

- 옵션의 **서비스 설정 탭은 한 줄도 바뀌지 않았다** — 기기 편집·연결 테스트·코어 구현 그대로.
- 카메라 드라이버·PTZ·코어·API 계층 불변. `place_id` 는 접속에 쓰이지 않는다.
- 런타임 의존성 여전히 0.

### 남은 일

| 항목 | 왜 |
|---|---|
| 뷰어에서 CSV·JSON 내려받기 | 요청에 없었다. 지금은 화면에서 본다 |
| 조건 여러 개(AND/OR 조립) | 서버는 `conditions[]` 로 이미 여러 개를 받는다 — **화면만 1개**를 보낸다 |
| 정렬 열 고르기 | 서버는 `orderBy` 를 받는다. 화면은 기본 정렬(시간 최신순 / 첫 열)만 쓴다 |
| `place_id` 로 화면 거르기(장소별 카메라 목록) | 분류가 생겼을 뿐 아직 소비하는 화면이 없다 |
