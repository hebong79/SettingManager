# 카메라 비밀번호 삭제 · 프리셋 열쇠(preset_id·cam_id) 수정

- 일시: 2026-08-06 10:30
- 요청
  1. `camera_info` 에서 비밀번호가 있으면 `****` 로 표시하고, 계정 비밀번호를 **삭제하고 저장**할 수 있게
  2. 프리셋 탭의 `preset_id`·`cam_id` 를 **수정 가능**하게 (표시 순서는 `preset_id` → `cam_id`)

## 1. 비밀번호 — "안 건드림"과 "지움"을 가른다

### 문제

`dbRoutes.merged()` 는 `password` 가 빈 문자열이거나 없으면 **기존 값을 지켰다.**
화면이 비밀번호를 되돌려받지 않으므로(`publicCamera` 가 `hasPassword` 만 준다) 이름만 고친
저장 한 번에 자격증명이 지워지는 것을 막는 규칙이고, 이것 자체는 옳다.

부작용이 하나 있었다 — **한 번 넣은 비밀번호를 화면에서 지울 방법이 없다.**
빈 문자열이 "안 건드림"을 뜻하는 이상, 같은 값으로 "지움"을 표현할 수 없다.

### 설계

값 하나에 뜻을 둘 담지 않고 **세 갈래**로 나눈다.

| 보내는 값 | 뜻 |
|-----------|-----|
| 필드 없음 · `""` | 기존 값 유지 (기존 규칙 그대로) |
| `null` (명시) | **지운다** → DB 에는 `''`(NOT NULL 이므로) |
| 그 밖의 문자열 | 바꾼다 |

### 변경

- **[dbRoutes.ts](../SettingMain/src/api/routes/dbRoutes.ts)** — `merged()` 안의 한 줄을
  `password(patch, current)` 함수로 뽑고 `null` 분기를 더했다.
  `PUT /api/db/cameras/:id` 와 `POST …/test` 가 같은 함수를 지나므로, 지운 상태로 연결 테스트도 된다.
- **[options.html](../SettingMain/web/options.html)** — 비밀번호 칸 아래 `camPasswordClear` 체크박스(「비밀번호 삭제」).
- **[optionsDb.js](../SettingMain/web/optionsDb.js)**
  - `renderEditor()`: 저장돼 있으면 `placeholder = '****'`, 없으면 `'(없음)'`.
    **값이 아니라 placeholder 다** — 별표를 `value` 로 채우면 저장할 때 그 별표가 그대로 비밀번호가 된다.
  - `applyPasswordClear()`: 「삭제」를 켜면 입력칸을 비우고 잠근다(지우면서 새 값을 넣는 뜻은 없다).
  - `draft()`: 체크됨 → `password: null`, 아니면 입력했을 때만 문자열.

## 2. 프리셋 열쇠 수정 — 주차면이 함께 따라온다

### 문제

`preset_id`·`cam_id` 는 읽기 전용 칸이었다. 그런데 이 둘은 단순한 값이 아니라 **열쇠**다.

```
preset_info  UNIQUE (cam_id, preset_id)
slot_setup   FOREIGN KEY (cam_id, preset_id) REFERENCES preset_info(cam_id, preset_id) ON DELETE CASCADE
```

스키마에 `ON UPDATE CASCADE` 가 **없다.** 그래서 `preset_info` 만 갱신하면 그 프리셋의
주차면 전부가 없는 부모를 가리키게 되고, 외래키가 `FOREIGN KEY constraint failed` 로 막는다.
주차면은 커미셔닝의 산출물(사람이 찍은 픽셀·ROI·센터라이징 결과)이라 **버릴 수 없다.**

### 설계

한 트랜잭션 안에서 `slot_setup` 과 `preset_info` 를 **함께** 옮긴다.
두 갱신 사이에는 외래키가 반드시 한 번 깨지므로 그 순간만 `PRAGMA defer_foreign_keys = ON`
으로 검사를 미룬다. 커밋에서 다시 검사되므로 짝이 안 맞으면 통째로 되돌아가고,
이 PRAGMA 는 커밋·롤백에서 **스스로 꺼진다**(§4 ③ 에서 실측).

거절하는 자리 셋:

| 상황 | 응답 |
|------|------|
| 옮겨 갈 `(cam_id, preset_id)` 가 이미 있다 | 409 — 덮어쓰면 그쪽 주차면까지 뒤섞인다 |
| 옮겨 갈 `cam_id` 의 카메라가 없다 | 400 |
| `preset_id` 가 1 미만·정수 아님 | 400 |

### 변경

- **[setupRepository.ts](../SettingMain/src/db/setupRepository.ts)** — `movePreset(from, to): number` 신설.
  옮긴 주차면 수를 돌려준다. 같은 자리면 아무것도 하지 않고 `0`.
- **[dbRoutes.ts](../SettingMain/src/api/routes/dbRoutes.ts)** — `PUT /api/db/presets/:camId/:presetId`:
  경로는 **지금 있는 자리**, 본문의 `cam_id`·`preset_id` 는 **옮겨 갈 자리**.
  이동과 나머지 값 갱신을 `transaction` 으로 한 덩어리로 묶는다 — 옮긴 뒤 이름 저장이 실패하면
  프리셋이 사람이 찾을 수 없는 번호로 가 있게 된다. 응답에 `movedSlots` 를 더했다.
- **[options.html](../SettingMain/web/options.html)** — 표 머리를 `preset_id` → `cam_id` 순으로 바꾸고,
  이동 규칙을 안내 문구에 더했다.
- **[optionsDb.js](../SettingMain/web/optionsDb.js)** — `loadPresets()`:
  - `preset_id` 는 숫자 입력칸
  - `cam_id` 는 **콤보**(등록된 카메라 목록). 없는 번호를 손으로 적으면 외래키에 막혀 저장이 통째로 실패하므로 고를 수만 있게 했다
  - 이동이 일어나면 토스트가 `주차면 N개 함께 옮김` 을 말한다
- **[routeCatalog.ts](../SettingMain/src/mcp/routeCatalog.ts)** — MCP 로 노출되는 라우트 설명에 이동 규칙 추가.

> **표시 순서 주의:** 요청 문장의 "preset_id 가 제일 앞, cam_id 가 다음"에 맞춰 순서를 **바꿨다**.
> 기존 화면은 `cam_id` 가 먼저였다. 원래 순서가 좋다면 되돌리기는 `options.html` 의 `<thead>` 한 줄과
> `loadPresets()` 의 `row.append` 두 줄이다.

## 3. 유닛 테스트

### `test/dbRoutes.test.ts` (+9건)

`describe('비밀번호는 지울 수 있다')`
1. `null` 명시 → `hasPassword:false`, DB 에 `''`
2. `''`·미전송 → 기존 값 유지 (**기존 규칙의 회귀 방지**)
3. 지운 뒤 다시 넣기

`describe('프리셋의 preset_id·cam_id 를 고칠 수 있다')`
4. `preset_id` 변경 → `movedSlots:2`, 슬롯이 따라오고 **`marked_x` 가 살아 있다**(옮긴 것이지 새로 만든 것이 아니다)
5. `cam_id` 변경 → 다른 카메라로 이동
6. 열쇠 + 이름 동시 변경
7. 이미 쓰는 번호 → 409, **그리고 아무것도 바뀌지 않는다**(이름·슬롯 전부 원위치)
8. 없는 카메라 → 400
9. 같은 번호 재전송 → `movedSlots:0`, 이름만 변경

### `test/optionsDbUi.test.ts` (+3건, 기존 1건 갱신)

- `****` 는 placeholder 이고 `value` 에 별표를 넣지 않는다(정규식으로 못 박음)
- 「비밀번호 삭제」가 `null` 을 보낸다
- 프리셋 표가 `preset_id` → `cam_id` 순이고 **둘 다 save 를 부른다** (HTML 머리와 JS 그리는 순서를 각각 확인)
- 기존 `if (password) …` 단정문을 새 분기문에 맞춰 갱신

### 파일 DB(WAL)에서의 지연 외래키 실측

테스트는 `:memory:` 라 WAL 파일 DB 의 동작이 검증되지 않는다. 실제 파일로 따로 확인했다.

| 확인 | 결과 |
|------|------|
| ① 지연 없이 슬롯만 옮기면 | `FOREIGN KEY constraint failed` — **PRAGMA 가 실제로 일한다는 증명** |
| ② 지연 사용 | 슬롯 2건 + 프리셋이 함께 이동, `marked_x` 100·200 보존 |
| ③ 커밋 뒤 `PRAGMA defer_foreign_keys` | `0` — 스스로 꺼졌고, 이어진 위반 시도는 다시 막혔다 |
| ④ 이동 중 예외 | 롤백으로 전부 원위치 |

## 5. 영향도 분석

| 대상 | 영향 |
|------|------|
| `POST /api/db/cameras/:id/test` | `merged()` 를 함께 쓴다 → 비밀번호를 지운 상태로도 연결 테스트가 된다(의도) |
| `configStore.reloadCameras()` | 카메라 쓰기 뒤 호출은 그대로. 지운 비밀번호가 즉시 드라이버에 반영된다 |
| `config.json` 경로(`normalize.ts`) | **무관.** 카메라 정본은 DB 이고 이 변경은 DB 라우트에만 있다 |
| `slot_setup` 하위 (`parking_slot`·`parking_evnt`) | `slot_id` 로 매달려 있고 `slot_id` 는 바뀌지 않는다 → **영향 없음** |
| `preset_info.id`(대리키) | 이동해도 그대로다 — 삽입 순서를 잃지 않는다 |
| MCP 도구 사용자 | `PUT …/presets/:camId/:presetId` 응답에 `movedSlots` 가 추가된다(기존 `preset` 필드는 그대로라 하위 호환) |
| 기존 화면 | 프리셋 표의 열 **순서가 바뀐다**(cam_id ↔ preset_id) |
| 카메라 삭제 | 변경 없음. 여전히 `ON DELETE CASCADE` 로 프리셋·주차면이 함께 사라진다 |

## 6. 남은 위험

- **되돌릴 수 없다.** 프리셋을 옮기면 옛 번호로 자동 복귀하는 길은 없다(반대로 다시 옮기면 된다).
  주차면이 함께 가므로 데이터 손실은 없지만, 커미셔닝 중인 카메라의 번호를 바꾸면
  진행 중인 다른 창의 화면이 옛 번호를 들고 있을 수 있다.
- 스키마에 `ON UPDATE CASCADE` 를 넣는 편이 근본적이지만, 그러려면 `slot_setup` 을 재생성해야 하고
  (SQLite 는 제약만 바꾸지 못한다) 판 올림·마이그레이션이 따른다. 이번 요청 범위 밖이라 하지 않았다.
