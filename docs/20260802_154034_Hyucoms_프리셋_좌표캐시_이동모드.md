# Hucoms 장비 프리셋 좌표 캐시와 이동 모드

## 개요

2026-08-02 현재 구현은 Hucoms 장비 프리셋 번호와 사용자가 학습한 PTZ raw 좌표를 기존 로컬 소프트웨어 프리셋과 분리해 관리한다. `real-camera-2`(.154)의 초기 항목은 `#1 EV1`, `#2 EV2`이며, 그 외 번호는 장비 이름 조회 없이 `#1~#10` 이름 없는 generic 항목으로 보완한다(장비 capability의 최대 번호가 10보다 작으면 그 범위까지만 표시한다).

정본은 `SettingMain/config/device-preset-registry.json`이다. 이는 런타임에 생성·갱신되는 별도 레지스트리이며 `PresetStore`/`presets.json`, `SlotStore`/`slots.json`, BackendCore discovery 저장소와 섞지 않는다.

## 변경 클래스·함수

- `SettingMain/src/domain/devicePresetRegistry.ts`
  - `parseDevicePresetRegistry`: version/camera/번호/name/PTZ 형식을 검증하고 손상 입력을 거부한다.
  - `seededEntries`, `toDevicePresetViews`: `real-camera-2` seed와 generic fallback을 병합하고 `seeded|generic`, `learned|unlearned` flag를 파생한다.
  - `upsertLearnedEntry`: `(cameraId, number)` 항목의 유한 raw `pan/tilt/zoom`와 `learnedAt`을 갱신한다.
- `SettingMain/src/store/devicePresetRegistryStore.ts`
  - `DevicePresetRegistryStore.load/list/get/learn`: 별도 JSON을 읽고, 최초 seed를 보충하며 학습 좌표를 저장한다.
  - `commit`: `${path}.tmp`에 기록 후 rename하고 성공 뒤 메모리 상태를 교체한다. `pending` queue로 프로세스 내 lost update를 막는다.
  - 기본 경로는 `DEFAULT_DEVICE_PRESET_REGISTRY_PATH = SettingMain/config/device-preset-registry.json`이다.
- `SettingMain/src/clients/hyucomsDirectPresetClient.ts`
  - `goPreset(number)`, `getPtz()`, `goPtz(ptz)`, `getCapability()`를 격리된 native `node:http`/`node:https` 경계에서 제공한다. timeout, 64KiB 응답 상한, 2xx, LF-only parser, URL/비밀번호 redaction을 이 어댑터 내부에 둔다.
- `SettingMain/src/api/server.ts`
  - `GET /api/cameras/:cameraId/device-presets` 조회와 `POST /api/cameras/:cameraId/device-presets/:number/go` 사용자 명시 mutation을 연결한다.
  - `devicePresetBusy` cameraId lock, capability/번호/expectedMode 검증, `requireDirectPresetMover`, `toDevicePresetEntryView`를 적용한다.
  - 새 장비 프리셋 route에서 `BackendCoreClient`를 생성·호출하지 않는다. 파일 상단의 기존 BackendCore 경로는 discovery 기능에만 남아 있다.
- `SettingMain/src/index.ts`: registry load 후 서버 의존성으로 주입한다.
- `SettingMain/web/api.js`, `control.js`, `index.html`, `app.css`: 장비 프리셋 select, flag/좌표 출력, confirm·loading·오류 처리와 기존 로컬 preset UI 분리를 구현한다.

## 로직 의도와 사용자 계약

1. capability 응답은 장비가 목록/이름을 제공하지 않음을 명시하고, UI는 `#1 EV1 · seeded · unlearned`, `#3 (이름 없음) · generic · unlearned`처럼 표시한다.
2. 좌표가 없을 때 선택 버튼 상태는 `프리셋 이동`이다. 사용자가 확인 후 POST하면 서버는 직접 `gopreset(number)` 1회 실행 → `getptzfpos`를 settle 정책으로 조회 → 안정된 최종 raw 좌표와 시각을 registry에 영속한다.
3. 좌표가 있으면 버튼 상태는 `좌표 이동`이다. 이후 POST는 저장된 raw 값을 그대로 사용해 직접 `goptzfpos(panpos, tiltpos, zoompos, panspeed=0, tiltspeed=0, zoomspeed=0)` 1회 실행하고, 좌표를 자동 재학습하지 않는다.
4. 조회(GET), 화면 진입, 자동 실행은 장비 이동을 일으키지 않는다. 중복 클릭은 UI에서 잠그고 서버 camera lock 충돌은 `409 CAMERA_BUSY`로 끝낸다. stale `expectedMode`도 `409`로 재조회시킨다.
5. `Sub/HyucomsAPI/hyucoms_api/client.py`의 직접 소스가 `go_preset(number)` → `preset_control.cgi?action=gopreset&number`, `get_ptzf_position()` → `ptzf_status.cgi?action=getptzfpos`, `go_ptzf_position()` → `action=goptzfpos`와 위 six query key를 정의한다. TypeScript adapter는 이 계약을 그대로 사용하며 임의 파라미터나 BackendCore 우회를 추가하지 않는다.

## 입출력·외부 계약

- 레지스트리 항목: `{ number, name: string|null, seeded: boolean, ptz: {pan,tilt,zoom}|null, learnedAt: string|null }`; 최상위 `{ version: 1, cameras }`.
- 조회 응답: `{ cameraId, entries, capability }`; 각 entry에는 파생 `flags`가 포함된다.
- 실행 body는 비어 있거나 `{ expectedMode: "learn"|"coordinate" }`만 허용한다. 성공 응답 mode는 `learned` 또는 `coordinate`다.
- capability 밖 번호, 비-Hucoms 카메라, 미지원 장비, malformed body는 장비 호출 전에 거부한다. raw 응답/인증정보는 API로 노출하지 않는다.

## 영향도·의존성

- 영향 파일은 위 `SettingMain/src`, `SettingMain/web`, `SettingMain/config` 경로와 `SettingMain/test/devicePresetRegistryStore.test.ts`, `hyucomsDirectPresetClient.test.ts`, `server.test.ts`이다.
- 공유 타입은 `src/domain/ptz.ts`의 `PtzRaw`/축 범위와 `src/clients/cameraDriver.ts`의 `DevicePresetCapability`, `CameraDriverError`다. 정착 조회는 `src/clients/waitForSettle.ts`를 재사용한다.
- 기존 로컬 preset API와 저장 포맷은 변경하지 않는다. SettingAgent 등 형제 프로젝트에는 파일·import·계약 변경이 없다. BackendCore discovery는 기존 경로로만 남으며 새 route가 이를 생성하지 않는다.
- config 파일은 런타임 write 대상이므로 배포 시 `SettingMain/config` 쓰기 권한과 백업/운영 정책이 필요하다. rename 성공 전에는 메모리 상태를 바꾸지 않는다.

## 테스트와 실제 QA 결과

QA 보고서 기준 `SettingMain/`에서 `npm run typecheck`, `npm run test`(11 files, 206 tests, 실패/skip 0), `npm run build`, `git diff --check`가 통과했다. mock HTTP는 gopreset 번호, getptzfpos, goptzfpos query와 첫 학습 순서 `gopreset:1 → getptzfpos → getptzfpos`, 다음 실행의 cache 좌표 `goptzfpos:3844:1188:10711 → getptzfpos → getptzfpos`를 검증했다.

2026-08-02 15:38 KST에는 실행 중인 기존 서버(PID 21548)를 유지한 채 `GET /api/cameras/real-camera-2/device-presets`와 정적 GET만 수행했다. 응답은 capability 255, #1 EV1/#2 EV2 seeded·unlearned, #3~#10 generic·unlearned였다. `gopreset`, `goptzfpos`, set/clear preset POST는 실카메라에 전송하지 않았고, 브라우저 클릭/리로드 E2E도 수행하지 않았다.

다음 검증은 아직 공백이다: 학습 후 재기동 reload E2E, settle timeout/조회 오류의 504 및 commit 0회, 전용 busy 동시성 테스트, 실제 브라우저 DOM 이벤트. 또한 기존 PTZ mutation과 공통 lock 통합은 구현 범위 밖이다. 이 항목들은 성공으로 간주하지 않는다.
