## 2. 화면 — 평면 3개 → 탭 3개

### 2-1. 왜 합쳤나

세 화면(`/discovery`·`/calibration`·`/vehiclebox`)이 **같은 것을 각자 세 벌** 갖고 있었다:
카메라 선택 · 능력 조회 · 영상 뷰포트 · 시작/정지/스냅샷 버튼.

탭마다 카메라를 따로 고르게 두면 사람이 **지금 어느 카메라를 보고 있는지 잃는다** —
탭을 옮겼는데 다른 카메라의 결과를 보면서 같은 카메라의 것이라고 믿게 된다.

```
/parking
┌─────────────────────────────────────────────┐
│ 대상 카메라 [카메라 ▼] [활성으로 선택]  코어: … │  ← 탭 밖 (3탭 공용)
├─────────────────────────────────────────────┤
│ [주차면 탐색] [캘리브레이션] [차량 3D]         │
├──────────────────────┬──────────────────────┤
│  (탭 패널)            │  카메라 뷰 (공용)      │
└──────────────────────┴──────────────────────┘
```

`GET /api/core/capabilities` 를 **한 번** 부르고 세 패널이 그 결과를 나눠 읽는다.

### 2-2. 껍데기와 패널의 계약

`parking.js` 가 껍데기이고, 패널 셋은 이 표면만 내놓는다.

| 훅 | 언제 | 없으면 |
|---|---|---|
| `onCapability(caps)` | 카메라·능력이 바뀔 때 | 능력 게이트가 없는 패널(차량 3D) |
| `onCameraChange()` | 기기를 바꿀 때 | — |
| `onActivate()` / `onDeactivate()` | 탭 전환 | — |
| `onViewportClick(event)` | 영상 클릭 | **클릭이 그 탭에 안 간다** |
| `onFrame()` | `img` 로드마다 | 오버레이를 다시 안 그림 |

#### 클릭 센터링이 탐색 탭에만 있는 이유

캘리브레이션 패널은 `onViewportClick` 을 **아예 내놓지 않는다.** 스윕이 카메라를 점유한
동안 사람이 조준을 끼워 넣으면 그 샘플이 조용히 오염되고, 오염된 줄 모르는 채 발행까지 간다.
**플래그로 끄면 언젠가 켜지지만, 없는 것은 켜지지 않는다.**

#### 비활성 패널은 타이머를 끈다

캘리브레이션 폴링이 탐색 탭에서도 돌면 20분짜리 스윕 중에 세 배로 두드린다.
`onDeactivate()` 가 그 경계다.

#### 차량 3D 는 탭을 떠날 때 오버레이를 지운다

세 탭이 `img#stream` 하나를 나눠 쓴다. 남겨 두면 **캘리브레이션 스윕 화면 위에 차량
큐보이드가 얹힌 채로** 보이는데, 그건 어느 탭의 그림도 아니다.

### 2-3. 옛 화면 3개는 삭제했다

`discovery.html/js` · `calibration.html/js` · `vehiclebox.html/js` 를 지웠다(`/discovery` 등은 404).

**설계서에는 "남긴다"고 썼는데 뒤집었다.** 같은 화면 정의가 두 곳에 있으면 어느 쪽이
이겼는지 사람이 알 수 없고, 이 저장소는 이미 그 이유로 카메라 편집 폼을 한 곳으로 모았다
(`options.js` 주석). 북마크가 깨지는 비용보다 정본이 갈리는 비용이 크다.

### 2-4. 고친 결함 하나

`api.js` 의 탐색 경로가 **`cameraId` 를 싣지 않았다.** 서버는 없으면 *활성* 기기로 떨어지는데,
화면에서 고른 기기와 활성 기기는 다를 수 있다 — 그러면 A 를 보면서 **B 의 탐색 데이터를 고친다.**
옛 화면에도 있던 문제이고, 카메라 선택을 전면에 내세운 새 화면에서는 더 두드러지므로 함께 고쳤다.

## 3. 번호판 호밍 신설

### 3-1. 무엇을 만드나

점마다 **판이 읽히는 PTZ**(`closeupPtz`)를 찾아 저장한다. **번호를 읽지 않는다** —
읽는 것은 그 자세로 가서 프레임을 떠 LPR 에 넘기는 별도 단계다.

```
와이드 프리셋으로 복귀
  → 스냅샷 → 차량 세그멘테이션 → 마킹점이 든 차량 하나를 고정   ← 표적 확정
  → 마킹점으로 조준
  → [줌 한 단계 → 스냅샷 → 판 검출 → 실루엣 안쪽 판만 후보]
       · 잠금 전: 후보가 정확히 하나면 잠근다
       · 잠금 후: plateTrack 으로 같은 판인지만 재확인(VPD 생략)
     → 판 중심으로 재조준 → 폭이 targetPx 이상이면 그 자세를 확정
```

### 3-2. 이 기능의 핵심은 "옆차로 옮겨타지 않기"

줌인하다 보면 화면 중앙에 번호판이 여럿 들어온다. **"가장 가까운 판"을 고르면 옆차의
판이 더 선명할 때 그쪽으로 옮겨탄다.** 그러면 잡은 성공했다고 말하면서 엉뚱한 주차면의
조준을 저장한다 — 이 기능이 낼 수 있는 최악의 결과다.

막는 방법이 두 단계다.

| 단계 | 수단 | 판정 |
|---|---|---|
| 잠그기 **전** | 차량 세그멘테이션 마스크. 광축이 관통하는 차량을 고정하고 **그 실루엣 안쪽** 판만 후보 | 후보가 **정확히 하나**일 때만 잠근다 |
| 잠근 **후** | `plateTrack` — 중심거리 ≤64px · 폭비 0.65~2.25 · 종횡비 0.65~1.55 · IoU ≥0.18 | 하나라도 더 맞으면 `ambiguous` 로 fail-closed |

**잠근 뒤 VPD 를 생략한다.** 고줌에서 차량은 화면 밖으로 잘려 마스크가 깨지고, 깨진 마스크로
"실루엣 안쪽"을 물으면 정답인 판이 밖으로 판정된다.

**잠금 전에는 줌만 바꾼다.** 옆으로 재조준하면 옆차를 표적으로 삼을 수 있다.

### 3-3. VPD 세그멘테이션 — 가장 큰 결손이었다

`vpdClient.ts` 는 검출 경로(`/det/imgupload`)를 쓰고 **마스크를 버렸다**. 주석이 이렇게 남아 있었다:

> `masks` 는 세그먼트 경로(`/seg/imgupload`)에서만 의미가 있고 검출 경로에서는 비어 온다 —
> 지금 쓰는 곳이 없으므로 **버린다**. 필요해지면 그때 계약을 다시 보고 싣는다.

**라이브로 확인했다** (2026-08-07, `192.168.0.125:9081`, 시뮬레이터 스냅샷 1장):

```
POST /vpd/api/v2/seg/imgupload → 201
  {success:true, id, bboxes:[4건], masks:[[[84,562],[84,566],…]×417, …×4],
   confidences:[0.95,0.93,0.87,0.78], classes:['car'×4]}

POST /vpd/api/v2/det/imgupload → 201
  masks: []          ← 주석이 맞았다
```

`VpdSegClient` 를 신설했다. `VpdClient`(검출)는 **손대지 않았다** — 다른 모델이고 다른 용도다.

### 3-4. 지킨 규율 (캘리브레이션 잡과 동일)

| 규율 | 근거 |
|---|---|
| 즉시 반환하고 뒤에서 돈다 | 점 12개면 9분 — HTTP 요청 하나로 못 붙든다 |
| **유언장을 첫 이동 전에** 남긴다 | 프로세스가 죽으면 `finally` 의 복귀도 같이 죽는다 |
| **언제나 와이드로 되돌린다** — 실패·취소·시간초과 전부 | 카메라를 고배율로 버려 두는 것이 최악 |
| 복귀 실패는 `cameraStranded` 로 **사람에게 알린다** | 조용히 넘기면 아무도 모른다 |
| 복귀에 **성공했을 때만** 유언장을 찢는다 | 실패하면 남겨 다음 기동이 대신 되돌린다 |
| `parking`(복귀 중)도 busy 로 센다 | 그 동안에도 카메라는 움직인다 |
| 캘리브레이션과 **동시 실행 금지** | 물리 카메라가 하나뿐 — 서로의 이동을 자기 측정으로 읽는다 |
| 못 하면 501/409 + **사유** | 조용한 폴백 금지 |

### 3-5. 조준은 어디에 저장되나 — **새 표를 만들지 않았다**

`slot_setup.ptz_pan/tilt/zoom` 이 스키마가 처음부터 이 값을 위해 둔 칸이다:

> 번호판 중심으로 센터라이징·줌인한 결과. 아직 안 잡았으면 NULL 이다 — 0 으로 채우면
> "원점을 보고 있다"는 거짓말이 되고, 덜 끝난 슬롯을 골라낼 수 없다. — `schema.ts`

**실패한 재호밍은 `null` 을 넣어 옛 값을 지운다.** 남겨 두면 그 조준이 이번에 확인된 것처럼
보이는데 실제로는 다른 차의 것일 수 있다. **빈 칸이 틀린 값보다 낫다.**

### 3-6. 능력 광고 — 못 하면 무엇을 채워야 하는지까지 말한다

| 조건 | 사유 |
|---|---|
| `driver.centerPoint` 없음 (park3d-rpc) | "픽셀 센터링을 지원하지 않아 호밍을 돌릴 수 없습니다" |
| 탐색 저장소 미배선 | "조준을 저장할 곳이 없습니다" |
| LPD 미설정 | "번호판 검출기(LPD)를 쓸 수 없습니다: … `detectors.lpd.baseUrl` …" |
| VPD 미설정 | "차량 세그멘테이션(VPD)을 쓸 수 없습니다: … **마스크가 없으면 옆차 드리프트를 막을 수 없어 호밍을 켜지 않습니다**" |

**반쪽 배선으로 켜지 않는다.** LPD 만 있으면 후보 고르기가 "가장 가까운 판"으로 퇴화한다.

### 3-7. 과정 다시보기

결과만으로는 **무엇을 고쳐야 하는지 알 수 없다** — 점을 잘못 찍은 것인지, 옆차와 겹친
것인지, 검출기가 못 본 것인지가 전부 다른 처방이다.

```
GET /api/core/discovery/presets/:presetId/points/:pointId/home-trace?cameraId=
GET /api/core/home-frame/:cameraId/:presetId/:pointId/:step        → image/jpeg
```

- 프레임은 `config/home-frames/<cameraId>/<presetId>/<pointId>/step-N.jpg`
- **카메라 id 가 경로에 들어간다** — 점 id 는 프리셋 안에서만 1부터라, 빼면 카메라 B 의
  호밍이 카메라 A 의 프레임을 지운다(상류가 실제로 겪은 사고)
- 재호밍은 옛 기록을 **덮지 않고 지운다** — 6스텝 위에 3스텝을 얹으면 4~6번이 남아
  이번에 보지도 않은 그림이 근거처럼 보인다
- **프레임 URL 은 저장소만 만든다.** 화면이 조립하면 서버 검증과 어긋난다
- 경로 조각은 `[\w.-]+` 만 통과. 위반은 **403**(404 로 뭉개면 "없다"와 "주면 안 된다"가 구별되지 않는다)

## 6. 주변 파일 영향

### 영향받는 것

| 대상 | 영향 |
|---|---|
| `/api/core/capabilities` 응답 | `plateHoming` 이 이제 **켜질 수 있다.** 화면이 `ok:false` 만 가정하고 있었다면 다시 봐야 한다 |
| `slot_setup.ptz_*`·`lpd_obb` | 호밍이 **쓴다.** 다른 곳에서 이 칸을 쓰고 있었다면 충돌한다 — 현재 쓰는 곳 없음(확인) |
| `config/home-frames/` | 새 디렉터리. 점마다 최대 10장 JPEG 가 쌓인다 — **용량 관리 대상** |
| MCP 라우트 카탈로그 | `home-trace`·`home-frame` 은 **등록하지 않았다** (아래) |

### 영향 없는 것

- `src/devices/**` — 드라이버 불변
- `src/calibration/**` · `src/centering/**` — 호밍이 **import 하지 않는다**(세 컴포넌트 독립 규약 유지)
- `src/detectors/vpdClient.ts` — 검출 경로 그대로. 세그는 별도 클래스
- `RemoteCoreProvider` — 불변. `core.provider: remote` 면 지금까지와 똑같이 backend-core 로 간다

### MCP 카탈로그

`home-trace` 는 **등록했다**(읽기 전용·카메라 미이동). `home-frame` 은 **일부러 뺐다** —
`image/jpeg` 라 `/api/stream` 과 같은 이유로 MCP 대화에 실을 수 없다. `home-trace` 응답의
`frameUrl` 이 그 주소를 알려 주므로 필요하면 사람이 브라우저로 연다.

드리프트 스캔 테스트는 `pathname === '…'` 리터럴만 훑으므로 정규식 라우트인 이 둘은
애초에 잡지 않는다(기존 `discovery/presets/...` 계열도 마찬가지다). 등록은 스캔이
요구해서가 아니라 **에이전트가 호밍 결과를 읽을 수 있어야 해서** 했다.

## 8. 남은 것

### 현장 확인 절차 (A5 성공 기준)

```
1. /options → 코어 구현을 bridge 로 바꾼다            ← 지금 remote 다
2. /parking → hucoms 기기 선택 (park3d-rpc 는 centerPoint 가 없어 호밍 불가)
   · 대상 카메라 뱃지가 "코어: bridge" 인지 확인
   · 호밍 카드의 [시작] 이 **활성**인지 확인 (회색이면 툴팁에 사유가 있다)
3. 탐색 프리셋을 만들고 와이드 화면에서 주차면 점을 3개 찍는다
4. 호밍 [시작] → 진행률·현재 점·결과표를 본다
5. 성공한 점의 closeup PTZ 로 카메라를 보내 **번호판이 읽히는지 눈으로 확인**   ← 진짜 기준
6. 실패한 점은 [과정 보기] 로 스텝 프레임을 넘겨 보며 사유를 확인한다
```
