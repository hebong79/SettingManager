# SettingManager 개발 오케스트레이터

**실행 모드: 에이전트 팀 (4인)** — 팀원이 `SendMessage`로 실시간 조율하고, `TaskCreate`/`TaskUpdate`로 진행을 공유하며, 산출물은 `_workspace/` 파일로 전달한다.

CLAUDE.md 5대 규칙(설계 → 유닛테스트 → 동작확인 → 한글문서화 → 영향도분석)을 파이프라인으로 실행한다.

## 4인 팀

| 단계 | 에이전트 | 서브에이전트 타입 | 산출물 |
|---|---|---|---|
| 1. 설계 | `architect` | `Plan` | `_workspace/01_architect_plan.md` |
| 2. 구현 | `developer` | `general-purpose` | 소스 + `_workspace/02_developer_changes.md` |
| 3. 검증 | `qa-tester` | `general-purpose` | 테스트 + 실행결과 + `_workspace/03_qa_report.md` |
| 4. 문서·영향도 | `documenter` | `general-purpose` | `docs/yyyyMMdd_hhmmss_*.md` + `_workspace/04_doc_impact.md` |

**모든 Agent 호출에 `model: "opus"`를 명시한다.** 하네스 품질은 에이전트의 추론 능력에 직결된다.

검증자가 `Explore`가 아닌 `general-purpose`인 이유: 테스트를 **실제로 실행**해야 하는데 읽기 전용 타입은 러너를 돌릴 수 없다.

## Phase 0: 컨텍스트 확인

작업 시작 전 실행 모드를 판별한다.

| 상황 | 모드 | 행동 |
|---|---|---|
| `_workspace/` 없음 | **초기 실행** | Phase 1부터 전체 |
| `_workspace/` 있음 + 부분 수정 요청 | **부분 재실행** | 해당 에이전트만 재호출. 각 에이전트 정의의 "재호출 시 행동"을 따른다 |
| `_workspace/` 있음 + 새 입력/새 주제 | **새 실행** | 기존 `_workspace/`를 `_workspace_prev_{yyyyMMdd_HHmmss}/`로 이동 후 전체 |

이어서 확인한다:
1. `SettingMain/package.json` 존재 여부 → **없으면 부트스트랩이 계획 1번**이 된다(`settingmanager-stack` 스킬)
2. 기존 `docs/*.md` 설계서 — 있으면 먼저 읽는다
3. `memo/memo.md` — 있으면 읽어 이전 맥락을 잇는다(CLAUDE.md 메모 정본 규칙)
4. 작업 범위: 이 저장소 내부인가, 형제 `SettingAgent`와의 연동을 포함하는가

## Phase 1: 팀 구성 및 작업 할당

1. `TeamCreate`로 4인 팀 구성 (architect, developer, qa-tester, documenter)
2. `TaskCreate`로 의존성 있는 작업 생성: 설계 → 구현 → 검증 → 문서. **구현↔검증은 양방향 의존**(통과까지 루프)
3. `_workspace/` 생성. 파일명 컨벤션 `{단계번호}_{에이전트}_{산출물}.md`

작업이 3단계 이하로 작으면 팀을 만들지 않고 리더가 직접 처리해도 된다 — 다만 **설계·검증·문서 규칙은 건너뛰지 않는다**. 팀 오버헤드를 줄이는 것이지 규칙을 면제하는 게 아니다.

## Phase 2: 파이프라인 실행

1. **설계자** → `01_architect_plan.md`. 각 단계에 검증 가능한 성공 기준이 붙어 있는지 리더가 확인한다. `확인 필요:` 항목이 있으면 사용자에게 먼저 묻는다.
2. **구현자** → 소스 + `02_developer_changes.md`. 계획 결함 발견 시 설계자와 합의 후 진행.
3. **검증자** → vitest 작성·**실행** → `03_qa_report.md`. 실패 시 구현자에게 보고하고 **통과까지 구현↔검증 루프**.
4. **문서화** → 01~03 + 실제 코드를 종합해 `docs/yyyyMMdd_hhmmss_*.md` + `04_doc_impact.md`.

**점진적 검증**: 모듈이 여러 개면 전체 완성을 기다리지 않는다. 각 모듈 완성 직후 검증자를 호출해 경계면을 즉시 교차 비교한다(초기 불일치가 후속 모듈로 전파되는 것을 막는다).

## Phase 3: 종합 및 보고

리더가 사용자에게 보고한다:
- 변경 요약 (파일 경로 포함)
- **테스트 결과 — 통과/실패/스킵을 그대로.** 실패를 숨기거나 "대체로 통과" 같은 표현으로 뭉개지 않는다
- 생성된 문서 경로
- 영향도 요약 (특히 형제 프로젝트 파급)
- 미완·미검증 항목과 사유

`_workspace/`는 사후 감사용으로 보존한다.

마지막에 피드백 기회를 제공한다: "결과나 팀 구성에서 바꾸고 싶은 점이 있나요?" 피드백이 있으면 `harness` 스킬로 하네스를 갱신한다.

## 데이터 전달 프로토콜

| 용도 | 방식 |
|---|---|
| 조율·진행 공유 | `TaskCreate`/`TaskUpdate` |
| 실시간 소통·결함 보고 | `SendMessage` |
| 산출물 | `_workspace/` 파일 |

최종 산출물(소스·`docs/`)만 정식 경로에 쓰고, 중간 파일은 `_workspace/`에 둔다.

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| 에이전트 실패/무응답 | 1회 재시도. 재실패 시 그 산출물 없이 진행하되 **보고서에 누락을 명시**한다 |
| 검증 실패 | 테스트를 느슨하게 고치지 않는다. 구현을 고치고 재실행. 통과까지 루프 |
| 루프 3회 초과 | 중단하고 사용자에게 실패 원인과 선택지를 보고한다. 무한 루프 금지 |
| 계획 vs 구현 상충 | 코드로 사실을 확인하고, 상충 정보는 삭제하지 말고 **출처를 병기**해 기록 |
| 계약 불명확 | 추측으로 확정하지 않는다. `확인 필요:`로 올리고 사용자에게 묻는다 |
| 부트스트랩 미완 | 기능 구현을 강행하지 않는다. 부트스트랩 검증(typecheck+test 실행) 통과 후 진행 |

## 테스트 시나리오

**정상 흐름 — "SettingAgent 상태를 조회하는 클라이언트 만들어줘" (초기 실행)**
1. Phase 0: `_workspace/` 없음 → 초기 실행. `SettingMain/package.json` 없음 → 부트스트랩 필요
2. 설계자: 1) 부트스트랩 → 검증: `npm run typecheck`·`npm run test` 통과, 2) `clients/settingAgentClient.ts` → 검증: 모킹 응답에서 상태 파싱, 타임아웃 시 `UNKNOWN` 강등. 응답 shape 미확정이면 `확인 필요:`
3. 구현자: 부트스트랩 파일 + 클라이언트 구현
4. 검증자: `test/settingAgentClient.test.ts` 작성·실행. **실제 `settingsRoutes.ts` 응답 shape과 클라이언트 파싱을 동시에 읽고 교차 비교**
5. 문서화: `docs/20260731_HHMMSS_SettingAgent클라이언트_구현.md` + 영향도
6. 리더: 통과 3/3, 문서 경로, 형제 프로젝트 영향 없음 보고

**에러 흐름 — 검증에서 경계면 불일치 발견**
1. 검증자가 실제 API는 `{ items: [...] }`를 반환하는데 클라이언트가 배열을 기대함을 발견 (`tsc`는 통과했음)
2. 파일:라인 + 기대값/실제값을 구현자에게, 계약 문제이므로 설계자에게도 `SendMessage`
3. 구현자가 unwrap 수정 → 검증자 재실행 → 통과
4. 문서화가 이 불일치와 수정을 문서에 기록 (숨기지 않는다)
5. 3회 루프에도 실패했다면 중단하고 사용자에게 원인·선택지 보고
